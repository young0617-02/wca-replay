# 数据处理协议（DPA）草案

> **草案性质**：本文件是提交律师审阅的草案，不是法律意见，不可直接签署、不可对外承诺，也不构成合规结论。
> **需要律师确认的条款**：第 2 条角色定性（受托处理者/独立控制者）、第 5 条数据最小化义务边界、第 7 条子处理者与跨境、第 8 条数据主体删除请求与不可变举证包的冲突、第 9 条泄露通知时限、第 12 条责任与赔偿上限、第 14 条适用法律与争议解决。员工个人信息处理的合法性基础另见《04-告知同意模板-草案.md》，同样需要律师确认。
> **必须由业务方填空的字段**：客户与供方主体信息、处理目的、数据主体范围、部署形态与处理地点、子处理者与跨境情形、留存期限、泄露通知时限、审计频率、赔偿上限、适用法律与争议地。

## 1. 定义

1.1 “客户数据”：客户为本协议目的向系统提供的考勤打卡、排班、请假、加班审批/审批台账、出差、更正、组织架构等数据及其派生记录。
1.2 “举证包”：系统导出的、可验签与可重放的证据包，包含分级结论、条文出处、输入副本、审计记录与签名材料。
1.3 “规则包”：用于计算分级结论的规则定义、条文引用与口径说明；数值结论由规则引擎计算，语言模型仅用于意图归类与叙述。
1.4 “子处理者”：受供方委托、接触客户数据的第三方。

## 2. 角色与关系（需律师确认）

2.1 客户就其员工个人信息而言为个人信息处理者；供方按客户指示处理，原则上为受托处理者。
2.2 若供方对处理目的、方式或结论口径具有独立决定权，角色可能变化，需律师按实际部署与商务模式确认。
2.3 双方应就员工个人信息处理的合法性基础、告知方式与内部制度衔接作出书面约定。

## 3. 处理范围（附件一）

| 数据类别 | 典型字段 | 规则用途 | 默认是否进入举证包 |
| --- | --- | --- | --- |
| 员工主数据 | `emp_id`、`pseudonym`、`job_code`、`org_id`、`region_code`、`worktime_regime`、`contract_approved_flex`、`normal_hourly_cents` | 判定特殊工时、城市档位、组织范围与人员定位 | 是，整文件打包；`pseudonym`、`normal_hourly_cents` 默认保留 |
| 打卡 | `emp_id`、`event_ts`、`punch_type`、`device_id` | 计算工时、休息与同日排序 | 是 |
| 排班 | `emp_id`、`work_date`、`planned_start`、`planned_end`、`rest_minutes` | 计算应出勤与休息 | 是 |
| 请假 | `emp_id`、`leave_kind`、`start_ts`、`end_ts`、`approved`、`paid` | 调休抵扣与审批判断 | 是；`paid` 默认保留，可在受控开关下裁剪 |
| 出差 | `emp_id`、`start_ts`、`end_ts`、`destination` | 当前不参与结论，仅登记 | 是；`destination` 默认保留 |
| 更正 | `emp_id`、`claimed_ts`、`claimed_type`、`reason`、`approved` | 更正审批与质量门禁 | 是；`reason` 可进入质量结论 |
| 组织 | `org_id`、`parent_id`、`org_name` | 组织范围展开与展示 | 是 |
| 审批台账 | `emp_id`、`doc_no`、`regime`、`valid_from`、`valid_to`、`job_codes`、`region_code`、`attachment_sha256`、`recorded_at` | 特殊工时与审批覆盖判断 | 是；文号与附件哈希可见 |
| 导出产物 | 分级结论、`findings`、`conclusions_final.csv`、`responsibility.json` | 结论与责任追溯 | 是；工作日期、人员、结论、条号、说明可见 |

3.1 敏感程度判断（薪酬、行踪、假别、审批人身份、组织归属）需业务方与律师逐项确认，本草案不作定性。
3.2 处理目的：`[[处理目的]]`。数据主体范围：`[[数据主体范围]]`。员工规模量级：`[[员工人数规模]]`。

## 4. 处理目的与方式

4.1 供方仅为实现 `[[处理目的]]` 处理客户数据，不得用于模型训练、广告、转售或与本协议无关的用途。
4.2 处理链路：导入校验 → 规则引擎计算 → 生成分级结论与条文出处 → 导出举证包 → 客户或指定接收方验签与重放。
4.3 部署形态：`[[部署形态]]`；处理地点：`[[处理地点]]`。若为客户内网部署，应约定数据不出域、远程运维与日志回传边界。

## 5. 数据最小化与字段控制

| 控制项 | 当前事实（见事实来源） | 本协议建议约定 |
| --- | --- | --- |
| 默认输入裁剪 | 默认不裁剪任何输入字段 | 客户可选择启用受控裁剪；未启用时双方确认已知悉包内含上述字段 |
| 金额与录入人 | 导出产物已移除 `amount_cents_input`、`amount_entered_by`；数据库与复核台仍保留 | 包内不得重新引入；库内访问另行约定权限 |
| 问答记录 | `question_log` 按 run 关联，导出只收本 run 记录 | 历史未关联行不进入任何包 |
| 数据库主键 | `file_id` 为数据库分配序号，不进入投影；包内来源定位用 `rel_path` 与 `line_no` | 包内不得出现数据库自增主键或其他仅内部使用的标识 |
| 可裁剪字段 | 当前仅 `leave:paid` 可在显式开关下裁剪，并记录 `omitted_fields` | 新增可裁剪字段须经客户书面确认并重新验证 |
| 投影字段缺失 | 投影字段缺失时导出直接报错，不静默降级 | 不得以“字段缺失”换取更小包体 |
| 假名化与加密 | `emp_id`、`pseudonym`、`confirmed_by` 假名化与包内字段级加密尚未实现 | 如客户要求，须另立变更并开新版本，不得在冻结版上改 |

## 6. 安全措施

6.1 访问控制按组织与角色限定；写操作强制 CSRF 校验；审批台账写入在服务端校验权限。
6.2 举证包支持 Ed25519 签名、输入摘要、工件摘要与结论摘要；验签区分“包内自洽”与“外部公钥 pin”。
6.3 包处理具备路径穿越防护与资源上限（条目数、单文件大小、总字节、嵌套深度），拒绝符号链接与硬链接。
6.4 具体安全标准、漏洞修复时限与审计配合方式：`[[安全联系人]]`、`[[审计频率]]`。

## 7. 子处理者与跨境（需律师确认）

7.1 子处理者名单：`[[子处理者名单]]`；新增或变更须提前通知客户并取得同意方式：`[[子处理者变更同意方式]]`。
7.2 跨境情形：`[[跨境情形]]`；如涉及跨境，应明确机制、评估与合同条款，由律师确认。

## 8. 数据主体权利协助（需律师确认）

8.1 供方在客户要求下协助响应访问、更正、删除、复制与解释请求。
8.2 举证包为可验签、可重放的证据材料，历史包一经交付即难以静默改写；数据主体删除请求与历史包、审计链的冲突处理须由律师确认，并在《02-数据留存与删除策略-草案.md》中落实。

## 9. 数据泄露通知

9.1 供方发现客户数据泄露、丢失或被未授权访问时，应在 `[[泄露通知时限]]` 内通知客户，并提供已知范围、影响与处置建议。
9.2 通知渠道与升级联系人：`[[安全联系人]]`。

## 10. 审计与合规证明

10.1 客户可按 `[[审计频率]]` 要求供方提供安全说明、验签记录与删除记录；现场审计范围与费用另行约定。
10.2 供方可提供举证包验签与重放结果作为技术证明，但该结果不替代法律意见或合规认证。

## 11. 留存、删除与返还

11.1 各类数据留存期限：`[[留存期限]]`；删除触发与执行方式见《02-数据留存与删除策略-草案.md》。
11.2 协议终止时，供方按 `[[返还或删除方式]]` 返还或删除客户数据，并出具删除证明；法律要求保留的除外。

## 12. 责任、赔偿与保险（需律师确认）

12.1 责任分配、赔偿上限：`[[赔偿上限]]`；保险安排：`[[保险安排]]`。
12.2 因一方违反本协议导致数据主体索赔的，双方按过错分担；具体条款由律师拟定。

13.2 终止后的数据返还、删除、举证包处置与过渡协助应在本协议或附件中明确。
