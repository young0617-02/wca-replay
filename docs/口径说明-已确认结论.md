# 已确认结论：三个字段怎么读（0.4.17）

> 一句话：**要数“确认成立”，请数 `decision=APPROVED`；不要用 `final_conclusions` 或 `signed` 代替。**
> 本页只解释当前 0.4.17 的实际行为，不改变任何包、签名或判定结果。

## 一、三个字段各是什么意思

| 字段 | 在哪里 | 实际含义 | 不能用来判断什么 |
|---|---|---|---|
| `counts.final_conclusions` | `manifest.json` | 本 run 中**已有人工处置**的结论条数。三条决定（`APPROVED`、`REJECTED`、`NEEDS_MORE_DATA`）都算 1 条 | 不能当作“确认成立”的条数 |
| `human_confirmations` / `human_confirmed_findings` | `responsibility.json` | 已登记的人工决定清单/条数。每条都带 `decision` 字段，说明是“通过”“拒绝”还是“存疑” | 不能因为字段名叫 `confirmed` 就认为全部是“确认通过” |
| `signed` / `signed_by` | `responsibility.json` | `signed: true` 只表示**本 run 存在至少一条“交付登记”事件**；`signed_by` 是登记交付的人，不是确认人 | 既不表示结论被认可，也不表示有人做过决定，更不是密码学签名 |

补充：包的密码学签名在 `manifest.signature`（Ed25519，仅 v3 签名包），和 `responsibility.json` 里的 `signed` 是两件不同的事。

## 二、正确的数法

| 你要回答的问题 | 正确的数法 |
|---|---|
| 有多少条结论“确认成立”？ | 数 `conclusions_final.csv` 中 `decision=APPROVED` 的行 |
| 有多少条被拒绝？ | 数 `decision=REJECTED` 的行 |
| 有多少条要求补证/存疑？ | 数 `decision=NEEDS_MORE_DATA` 的行 |
| 有多少条还没人处置？ | 看 `manifest.counts.unsigned_pending` |
| 这个包有没有人登记交付？ | 看 `responsibility.json` 的 `signed` / `signed_by` |

在本轮实测中，同一批 39 条 finding：

- 未做任何决定：`final_conclusions=0`，`unsigned_pending=39`；
- 做 1 条 `APPROVED`：`final_conclusions=1`，`unsigned_pending=38`；
- 做 1 条 `REJECTED`：`final_conclusions=1`，`unsigned_pending=38`；
- 做 1 条 `NEEDS_MORE_DATA`：`final_conclusions=1`，`unsigned_pending=38`。

三种决定对 `final_conclusions` 的影响完全一样。判断“是否确认成立”，只能看 `decision` 列。

## 三、`REJECTED` 的原始示例

以下示例来自演练库，确认人与交付登记人均为演练身份，仅用于说明字段行为，不代表真实签署。

复核人提交 `REJECTED` 后，包内 `conclusions_final.csv` 的实际数据行是：

```csv
rule_id,emp_id,work_date,period_key,severity,decision,confirmed_by,confirmed_at,note
OT-D01,T-STD,2025-11-28,,REVIEW,REJECTED,auditor,2026-11-09T11:27:21.457662+08:00,实测：REJECTED
```

同一包的 `responsibility.json` 实际片段是：

```json
"human_confirmations": [{"confirmed_at": "2026-11-09T11:27:21.457662+08:00", "confirmed_by": "auditor", "decision": "REJECTED", "emp_id": "T-STD", "note": "实测：REJECTED", "period_key": null, "rule_id": "OT-D01", "severity": "REVIEW", "work_date": "2025-11-28"}]
"human_confirmed_findings": 1
"signed": true
"signed_by": [{"actor": "human:auditor-drill", "seq": 7, "ts": "2026-11-09T11:27:21+08:00"}]
```

这条记录里：

- 结论被**否定**（`decision=REJECTED`）；
- 但仍计入 `final_conclusions=1` 和 `human_confirmed_findings=1`；
- `signed=true` 与这条否定无关，它只来自那次交付登记。

## 四、`signed: true` 到底是什么意思

代码里的判定条件只有一条：

```text
本 run 的 audit_event 中存在 action = 'evidence.sign' 的记录  →  signed = true
```

`evidence.sign` 是“交付登记”，由导出时登记“谁登记了这次交付”产生。它**不是**密码学签名，也**不提供**签名信任根。

最直接的实测证据：只登记交付、**一条决定都没做**时，包里是：

```text
human_confirmations = []
signed = true
```

所以：

- `signed: true` 可以出现在“零确认”的包里；
- `signed: true` 不代表“结论被认可”；
- `signed: true` 不代表“有人做过决定”；
- 真正的包签名请查 `manifest.signature`（仅 v3 签名包），不是这个字段。

## 五、给客户的建议表述

对客户或评审方，建议这样写：

> 本包共 N 条机器结论；其中人工确认成立 X 条（`decision=APPROVED`），
> 人工否定 Y 条（`REJECTED`），要求补证 Z 条（`NEEDS_MORE_DATA`），
> 尚未处置 W 条（`unsigned_pending`）。
> `final_conclusions` 是“已有人工处置”的合计（X+Y+Z），不等于“确认成立”。
> `signed=true` 只表示已登记交付，不代表任何结论被认可。

不要直接写：

- “已确认结论 N 条”（除非 N 只统计 `APPROVED`）；
- “包已签署，结论已确认”（`signed` 不是签名，也不是确认）；
- “人工确认了全部结论”（把 `REJECTED/NEEDS_MORE_DATA` 混进了确认数）。

## 六、适用版本与后续
