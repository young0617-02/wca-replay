# Ed25519 举证包签名方案（v1）

> 目标：把“包内可复核”提升为“包外可用固定公钥证明来源”。签名不替代 replay；它证明“这份 manifest、输入字节与链头由一个持有私钥的人签过”，不证明结论一定正确。

> **v3 发布前修订（2026-11-03）**：签名对象新增 `inputs_digest`，把 `inputs/` 全部文件（含 `inputs/manifest.json`）纳入签名。v3 尚未签发过任何真实包，因此直接修订 v3 定义，不新开 v4；检查记录见 `reports/判据修订.md` REV-42。
>
> **v3 再次发布前修订（2026-11-04）**：新增 `manifest.producer`（version/commit/python/rule_pack_version），让包能说明“用哪个版本代码导出”。该字段被 `manifest_checksum` 覆盖，v3 签名因此间接覆盖它；schema 仍为 `wca-evidence-package-v3`，不新开 v4。修订前仍无已对外签发的 v3 包，检查记录见 `reports/判据修订.md` REV-47。
>
> **v3 工件绑定修订（2026-11-04，盲跑反馈）**：新增 `artifact_sha256`、`artifacts_digest`、`verify_script_sha256`；签名 payload 从 7 字段扩展为 9 字段（新增 `artifacts_digest` 与 `verify_script_sha256`）。旧 v3 包没有这两个字段，仍按旧 7 字段验签，但**缺少工件绑定字段的新 v3 包不再给完整验收**。记录见 REV-48。

## 1. 签什么

签名对象是 canonical JSON（key 排序、UTF-8、无空格、保留中文）序列化后的字段。
**0.4.3 起（0.4.4/0.4.5/0.4.6 延续）新 v3 包为 10 字段**：

```json
{
  "schema": "wca-evidence-package-v3",
  "rule_pack_version": "...",
  "input_fingerprint": "...",
  "conclusion_digest": "...",
  "inputs_digest": "...",
  "manifest_checksum": "...",
  "audit_chain_head": "...",
  "artifacts_digest": "...",
  "verify_script_sha256": "...",
  "evidence_digest": "..."
}
```

修订前旧 v3 包没有最后三个字段中的相应项，继续按旧 7/9 字段载荷验签；新包缺
`artifacts_digest`/`verify_script_sha256` 时按 `ARTIFACT BINDING FAIL` / `VERIFY SCRIPT FAIL`
失败关闭，缺 `evidence_digest` 时按 `EVIDENCE DIGEST FAIL` 失败关闭。

- `audit_chain_head` 取导出时 `verify_chain()` 的 `head_hash`；验签时用包内审计链重算出的实际头哈希，不信任 manifest 声称值。
- `inputs_digest` 覆盖包根 `inputs/` 下**实际存在的所有普通文件（递归）**，**包含 `inputs/manifest.json` 本身**；目录不计入。每个条目为 `[relative_path, sha256]`：
  - `relative_path` 以包根为基准，统一用 `/`；反斜杠先归一为 `/`，去掉空段与 `.` 段，出现 `..` 直接拒绝；
  - **不做小写化**：`Foo.CSV` 与 `foo.csv` 是不同路径；规范化后路径重复直接拒绝；符号链接拒绝；
  - `sha256` 为 64 位小写十六进制；
  - 条目按 `relative_path` 的 UTF-8 字节序升序排列；
  - 对排序后的列表做 canonical JSON（同 key 排序、无空白、UTF-8）再 SHA-256，得到 `inputs_digest`。
- `manifest_checksum` 覆盖 manifest 除自身与 `signature` 外的全部字段（含 `producer`、`artifact_sha256`、`artifacts_digest`、`verify_script_sha256`、`inputs_digest`、`evidence_digest`、`projection_fingerprint`、`conclusions_sha256`）；`signature` 排除以避免“先校验和再签名”的循环。
- `artifact_sha256` 是包根工件的逐文件 SHA-256 映射；`artifacts_digest` 是该映射按 UTF-8 路径字节序排序后的 canonical JSON SHA-256；`verify_script_sha256` 是包内 `verify.py` 的字节哈希。三者都进 `manifest_checksum`，新 v3 包还把后两者直接放进签名 payload。
- `evidence_digest` 覆盖**全部 finding 的 evidence 块**：按 `(emp_id, work_date, period_key, rule_id, rule_version)` 排序，每条绑定 `rule_id/rule_version/emp_id/work_date/period_key` 与规范化 evidence；evidence 固定字段 `tables/window({kind,key,start,end})/rules/aggregation`，缺失标量写 `null`、列表写 `[]`，表路径统一 `/`。它进入 `manifest_checksum` 与新包签名 payload，但**不进入** `conclusion_digest`。只补一条 evidence 注释时，只有 `evidence_digest` 变化，`conclusion_digest` 与 `input_fingerprint` 不变。
- `input_fingerprint` 是内容与范围指纹（输入文件内容/引用范围/规则参数）；`inputs_digest` 是包内 `inputs/` 实际文件字节（含 `inputs/manifest.json`，已不含 `run_id` 与 DB `file_id`；文件名由 `rel_path` 推导）。两者分工不同：前者证明“这次跑了哪些内容与范围”，后者证明“包内输入字节未被替换”。同一批输入跨 run/跨库导包，`inputs_digest` 应稳定一致；0.4.4 起 `QUAL-01/02` 的 `line_refs` 与 `OFF-01` 的 `conflicts.sources` 只写 `rel_path+line_no`，`conclusion_digest` 也不再因 DB `file_id` 变化；旧 0.4.3 的 `01bd4403…` 含 `file_id`，仅属历史包。
- `producer` 是版本指纹块：`version`（`wca-0.4.6` → `0.4.6`）、`commit`（完整 40 位 git commit）、`python`（导出时解释器版本，仅记录）、`rule_pack_version`。它不是独立签名字段，但被 `manifest_checksum` 覆盖，故 v3 签名保护它；改任一值并重算 checksum 仍会导致签名失败。
- `projection_fingerprint` 是**规则/引擎实际读取字段**的规范化摘要，由 `src/projection.py` 计算；字段清单/排序/时间/空值规则见 `docs/数据最小化方案.md`。它不直接进入签名 payload，但被 `manifest_checksum` 覆盖，因此仍受签名保护。
- `conclusions_sha256` 是 `conclusions_final.csv` 的字节哈希，v3 包必填；`verify.py` / `replay` 重算并输出 `ARTIFACT OK/FAIL`。
- 不同语言只要按上述路径规范化、排序和 canonical JSON 规则实现，就能算出同一字节串。

## 2. 放哪

`manifest.signature`：

| 字段 | 含义 |
|---|---|
| `alg` | 固定 `"Ed25519"` |
| `key_id` | `ed25519:` + 公钥 SHA-256 十六进制 |
| `created_at` | ISO 8601，带 `+08:00` |
| `public_key_b64` | 32 字节 Ed25519 公钥，标准 Base64 |
| `signature_b64` | 64 字节签名，标准 Base64 |

`inputs_digest` 与 `evidence_digest` 不放进 `signature` 块，而是顶层 manifest 字段；签名 payload 引用它们，`manifest_checksum` 也覆盖它们。`evidence_digest` 还必须由包外 `--expect-evidence-digest`/单包 anchor 文件锚定（威胁模型见 §4）。

私钥绝不进包。签名私钥从 `--signing-key` 文件、`WCA_SIGNING_KEY_FILE` 或 `WCA_SIGNING_KEY_B64`（裸 seed Base64）读取；文件优先。

## 3. 版本策略

- v1/v2：内容检查口径不变；但**无签名包拿不到 `RESULT OK`**——默认输出 `RESULT PARTIAL`（exit 2），不能作为完整验收；只有显式 `--require-signature` 才 `RESULT FAIL`（exit 1）。
- 新导出：有签名密钥（`--signing-key` / `WCA_SIGNING_KEY_FILE` / `WCA_SIGNING_KEY_B64`）时自动写 `wca-evidence-package-v3` + `signature`；无密钥时仍是 v2 无签名包（`wca-verify` 最多 `RESULT PARTIAL`，exit 2）。
- schema 声称 v3 但无 `signature` 或缺 `inputs_digest`：直接 FAIL。
- schema v2 本就没有 `inputs_digest`：`INPUTS DIGEST NOT CHECKED`（版本缺失，不是不一致），且不参与 `RESULT OK` 门禁。
- 旧 v2/v3 包若缺 `artifact_sha256`/`artifacts_digest`/`verify_script_sha256`，独立验算器按失败关闭；
  它们只能作为历史回放/参考，不能当完整验收。v3 定义修订不生成 v4。

## 4. 验证语义

- **信任依据是发行 wheel 的 `wca-verify`**，不是包内 `verify.py`。`wca-verify` 自己重算 checksum、链、输入摘要、工件哈希、findings 摘要与签名，**不执行包内代码**。包内 `verify.py` 只保留为便利脚本，不能作为独立验收。
- `wca-verify` / `wca replay` 只要看到 `manifest.signature` 就必须验签；验签失败直接 FAIL，不降级。
- `--public-key <file-or-base64>` 可重复传入，作为外部固定公钥（pin）。包内公钥只能证明“包内自洽”；**外部 pin 只表示“与供给公钥副本匹配”，不代表来源身份已核验**。来源身份必须由双方通过独立渠道核验 key_id 后，在交付记录里另行声明。工具输出统一为：
  - `SIGNATURE OK / package self-check (NOT source trust)`
  - `SIGNATURE OK / pinned (key matches supplied pin; independent key_id verification not done)`
- **`RESULT OK` 门禁**：内容检查通过 + 签名 pin 命中 + 外部锚点通过 + 外部 package_sha256 通过 + 外部 artifacts_digest 通过 + 外部 evidence_digest 通过；任一外部项缺失/未通过 → `RESULT PARTIAL`（exit 2），不匹配 → `RESULT FAIL`（exit 1）。`--anchor-file <单包 anchor.json>` 可一次提供 `anchor/package_sha256/artifacts_digest/evidence_digest`，显式参数优先、文件兜底。组合式 `anchor.json` 的 `packages` 是**数组**（每项含 `role/file/sha256/anchor/…` 的单包记录），不是 key → 记录的映射；该文件不能直接用于单包验算。环境变量 `WCA_EXPECT_ANCHOR`（锚点）与 `WCA_EXPECT_EVIDENCE_DIGEST`（证据定位摘要）；包 SHA/`artifacts_digest` 只能显式参数或单包 anchor 文件。优先级：显式参数 > 环境变量 > 文件。
- **威胁模型**：签名者可信时，`evidence_digest` 由签名覆盖；签名者可能作恶或私钥失窃时，签名本身不再可信，**必须**用包外 `--expect-evidence-digest`（或单包 anchor 文件的 `evidence_digest`）锚定，不能只看包内 manifest。
- 未 pin 但签名有效：`RESULT PARTIAL`，不能算完整验收；pin 不匹配：`SIGNATURE FAIL`。
- `--require-signature`：v1/v2 缺签名也 FAIL；v3 缺签名始终 FAIL。
- **工件绑定**：`artifact_sha256` 逐文件哈希、`artifacts_digest` 清单摘要、`verify_script_sha256` 包内脚本哈希；缺失/不符 → `ARTIFACT FAIL` / `VERIFY SCRIPT FAIL`；额外文件 → `EXTRA FILE FAIL`。`wca-verify` 与 `wca replay` 都执行。
- **发现摘要**：`wca-verify` / `wca replay` 从 `findings.csv` 按公开规范化算法反算 `conclusion_digest`；不一致 → `FINDINGS DIGEST FAIL`。这独立于工件哈希：即使攻击者同步更新工件哈希/清单摘要/checksum 并重签，findings 语义仍要对上。
  **覆盖范围**：只覆盖 `rule_id`、`rule_version`、`emp_id`、`work_date`、`period_key`、`severity`、`metric`、`citations`、`explanation` 九个规范字段；`source_rel_path`、`source_line_no`、`severity_label` 不进摘要，由 `artifact_sha256["findings.csv"]` 负责。**单个 `FINDINGS DIGEST OK` 不等于整张表未变**，必须同时 `ARTIFACTS OK`。
  `metric` 只保留数值与计量口径（如 `counting_scope`）；`evidence` 不在 canonical 九字段内。
  `rule_version` 是单条规则版本，不等于 rule pack 版本；v5 包内的 100 条 v4 + 16 条 v5 是规则级标签，分布写入 `manifest.counts.rule_versions`。
  **覆盖边界（必须与已确认结论分开理解）**：`conclusion_digest` 只覆盖 findings 的上述九个规范字段，**不覆盖“已确认结论”**。`conclusions_final.csv`（人工确认后的最终结论）由 `artifact_sha256["conclusions_final.csv"]`、`artifacts_digest` 与包签名绑定；改确认结论会被 `ARTIFACT FAIL` 发现，而不是靠 `conclusion_digest`。因此不能把“`FINDINGS DIGEST OK` + 签名有效”理解为“确认结论也在 `conclusion_digest` 内”。
- **证据定位摘要**：`wca-verify` / `wca replay` 从 `findings.csv` 的 `evidence_json` 重算 `evidence_digest`；不一致 → `EVIDENCE DIGEST FAIL`。0.4.3 起新包必须声明该字段；新版本包缺失即失败关闭。无 `producer` 或 `producer.version < 0.4.3` 的旧包输出 `EVIDENCE DIGEST NOT CHECKED`，且**即使其余四项外部门禁齐全也不得给 `RESULT OK`**；这是历史兼容分档，不是“检查通过”。
- **两层分工**：`inputs_digest` + 签名 + 工件绑定管**原始字节与来源**；`projection_fingerprint` + `conclusion_digest` 管**规则字段能复算结论**。`wca-verify` 不跑引擎，只验证字节层/工件/发现摘要；`wca replay` 导入后重算投影指纹，缺失/不一致输出 `PROJECTION FAIL`。旧 `input_fingerprint` 语义不变，旧包继续按旧三元组判定。
- **包外锚点**：四段旧格式完全不变；第五段可选 `projection_fingerprint`，五段时校验包内投影字段。裁剪包必须用五段；未裁剪包没有投影字段，传五段按失败关闭处理。**不传 `--expect-anchor`**：输出 `ANCHOR NOT CHECKED` + `RESULT PARTIAL`（exit 2），不再给完整通过；`--expect-triple` 只是 legacy 比对。`--expect-package-sha256` / `--expect-artifacts-digest` 可选，失败关闭。
- **输入摘要**：`wca-verify` / `wca replay` 从包内实际文件重算 `inputs_digest`：
  - 与 `manifest.inputs_digest` 不一致：`INPUTS FAIL`，`RESULT FAIL`；
  - 一致且签名有效：`INPUTS SIGNED OK (inputs_digest bound by signature)`；
  - 一致但包未签名/签名无效：`INPUTS SELF-CHECK OK (inputs_digest matches manifest; NOT signed)`；
  - v3 缺 `inputs_digest`：`INPUTS FAIL`（新契约违约，失败关闭）；
  - v2 无 `inputs_digest`：`INPUTS DIGEST NOT CHECKED`（旧契约从未包含该字段，属版本缺失；不参与 `RESULT OK` 门禁，结果只能是 `RESULT PARTIAL`，exit 2）。
  这使单独跑 `wca-verify` 也能发现“整批换 `inputs/` 并同步改 `inputs/manifest.json`”，不再依赖 `replay` 才能发现。

## 4.1 跨版本可比性（0.4.9）

- 五联摘要（`conclusion_digest` / `evidence_digest` / `inputs_digest` / `input_fingerprint` /
  `artifacts_digest`）只在**同一 `rule_pack_version` 且同一 evidence schema** 下可比。
  跨版本或跨 schema 时，摘要不同不代表任一方被篡改。
- `anchor.json` 必须带 `comparability_scope`：`{"rule_pack_version": "...", "schema": "wca-evidence-package-v3"}`。
  旧锚点按版本命名（`anchor-<version>-<role>.json`），新版本不覆盖旧文件。
- 验算输出分三档：同版本同 schema 摘要不符 = `RESULT FAIL`（exit 1）；跨版本/跨 schema =
  `RESULT INCOMPARABLE`（exit 3）；缺字段/缺签名仍按原规则失败关闭（`FAIL`/`PARTIAL`）。
  **INCOMPARABLE 只用于“不可比”，不得吞掉任何真实的完整性失败。**
- `PRODUCER FAIL` 表示 wheel 与包版本不配对，随后签名检查早退为 `SIGNATURE NOT CHECKED`；
  它不是篡改结论，处理方式是换用对应版本 wheel 回放。
- 0.4.10 起，可比性判定只有一处实现（`evaluate_external_anchor`），`wca-verify` 与
  `wca replay` 的标签与退出码必须一致：
  - 锚点文件带 `anchor` 串却缺 `comparability_scope` → `INCOMPARABLE`（exit 3），不静默按可比处理；
  - `comparability_scope` 与 `anchor` 串互相矛盾 → `ANCHOR FAIL` 自相矛盾（exit 1），不是不可比；
  - 锚点文件里能从 `anchor` 串解出的冗余字段（`schema` / `rule_pack_version` /
    `input_fingerprint` / `conclusion_digest`）必须逐项一致，否则 `ANCHOR SELF-CONFLICT` 失败关闭。

## 5. 密钥管理

- `keygen --out var/keys/ed25519.key [--public-out var/keys/ed25519.pub] [--force]`
- 私钥文件：单行 Base64 seed；已存在且无 `--force` 时拒绝覆盖。
- Windows 用 `icacls /inheritance:r /grant:r <user>:F` 收紧 ACL，POSIX `chmod 0600`；公钥可公开。
- `key_id` 由公钥指纹算出；轮换时保留旧 `.pub`，旧包用旧公钥仍可验；`--public-key` 可重复传入新旧公钥。
- **轮换记录（0.4.4 → 0.4.5，实测）**：
  - 0.4.4 包用 `ed25519:ec2081…08d6`，0.4.5 包用 `ed25519:b07741b2…9555`。
  - 0.4.5 的私钥文件 `var/handoff-packages/keys/ed25519.key` 创建于 2026-11-04 09:29:15；0.4.4 对应的私钥在工作区已不存在。
  - 原因不是计划内轮换：`var/handoff_packages.py` 每次构建先删除 `var/handoff-packages`，再 `keygen` 生成新密钥；0.4.5 构建因此覆盖了 0.4.4 私钥。属构建脚本密钥生命周期缺陷，按安全事件记录在 `docs/安全与证据链现状.md`。
  - 处置：0.4.4 私钥作废且未备份；旧公钥仍保留在 `handoff/20261104-第六轮整改/trusted-public-key.pub`，**旧包仍可用 0.4.4 wheel + 该旧公钥验签**。
  - 0.4.5 及 0.4.6 复用 `ed25519:b07741b2…9555`，0.4.6 不产生新轮换。
  - **旧包不能直接用新版 wheel 验签**：旧包用 0.4.5 wheel 会先触发 `PRODUCER FAIL`，随后签名检查早退为 `SIGNATURE NOT CHECKED`；这不是“验签失败”，而是根本没走到验签。旧包验签必须配对应版本的旧 wheel。

- **发行物签名钥轮换记录（0.4.0 → 0.4.7，实测）**：
  - 0.4.0–0.4.5 的 `SHA256SUMS.sig` 使用 `ed25519:5e797e1842cf49c7043ba238f2a085b08c87d0a49663440f989cdc7df9ee5bb6`，
    私钥持久保存在 `var/release-keys/ed25519.key`，**不是每次构建重新生成**。
  - 0.4.6 发行物误用包签名钥 `ed25519:b07741b2e0bbcb9a3a37dd09a7348c717497145f7cbbdd580b18e7e80e7a9555`：
    构建命令把 `var/handoff-keys/ed25519.key` 传给了 `--signing-key`，而脚本当时不校验 `key_id`，
    发行物外部锚点因此被静默替换。已发布的 0.4.6 发行物不重签、不改写。
  - 生效版本：0.4.6 误用，0.4.7 恢复 `5e797e18…5bb6`。`scripts/build_release.py` 增加
    `EXPECTED_RELEASE_KEY_ID = "ed25519:5e797e18"` 守卫：`key_id` 不匹配时默认拒绝构建，
    只有显式 `--allow-key-rotation <理由>` 才放行；生成流程仍是“持久钥 + 受控轮换”，
    不存在“每版一个新钥”。
  - 旧钥处置：`b07741b2…9555` **不作废**，它仍是包签名钥，只是禁止再用于发行物；
    0.4.6 发行物配该公钥仍能自洽验签，但不能把 0.4.6 的 `key_id` 当作 0.4.7 的锚点。
  - 配对要求：`SHA256SUMS.sig` 必须与同目录 `RELEASE.json.release_signature.key_id` 一致；
    旧发行物（0.4.0–0.4.6）只能与各自版本的 `RELEASE.json`/`SHA256SUMS`/wheel 成套核验，
    逐文件 SHA-256 见交接目录 `release/旧发行物-SHA256清单.md`。
  - 结论：包钥轮换（0.4.5）与发行钥误用（0.4.6）都是流程缺陷，不是设计上的逐版轮换；
    0.4.7 起用脚本守卫固化，轮换必须留理由与记录。

## 6. 依赖

选 `PyNaCl==1.6.2`：只做 Ed25519，Windows 自带 libsodium 轮子，依赖面为 `cffi`/`pycparser`，比 `cryptography` 的编译/Rust 面更小。`uv add` 定向添加，不顺带升级其他包。包内附 `verify-requirements.txt`；独立验签需安装 `pynacl`。

## 7. 失败关闭与边界

- 签名存在但字段缺失、Base64/长度非法、`key_id` 不一致、签名不匹配、pin 不匹配：全部 FAIL。
- 签名覆盖 manifest 关键元数据、`manifest_checksum`（含 `artifact_sha256` / `artifacts_digest` / `verify_script_sha256` / `inputs_digest` / `evidence_digest` / `projection_fingerprint` / `conclusions_sha256`）与链头；新 v3 包还直接签 `artifacts_digest`、`verify_script_sha256` 与 `evidence_digest`。但**签名只证明“持有私钥者签过”**；签名者作恶或私钥失窃时，`evidence_digest` 必须靠包外 `--expect-evidence-digest`/单包 anchor 文件锚定，不能只看包内 manifest。改 `findings.csv` / `quality_issues.csv` / `input_files.csv` / `responsibility.json` / `not_covered.json` / `未覆盖清单.md` / `verify.py` 会被 `ARTIFACT FAIL` / `VERIFY SCRIPT FAIL` 发现；改 `findings.csv` 严重级别即使同步重算工件哈希，也会被 `FINDINGS DIGEST FAIL` 发现；改 evidence 定位元数据即使同步重算工件哈希，也会被 `EVIDENCE DIGEST FAIL` 发现。
- 签名覆盖 `inputs/` 下实际文件（含 `inputs/manifest.json`）：换 CSV、只改登记表、增删文件都会被 `INPUTS FAIL` 发现。
- `inputs_digest` 只证明“这些输入字节与签名一致”，**不证明**这些输入能复算出签名中的 `conclusion_digest`；结论是否正确仍必须 `replay` 实算三元组与 `projection_fingerprint`。
- `projection_fingerprint` 覆盖规则/引擎读取的字段；非投影字段被裁剪后，原始 `input_fingerprint` 会不同，这是预期，由投影指纹与结论摘要判定，不是包损坏。
- `replay` 将包内 `producer.version` / `commit` / `rule_pack_version` 与当前验算代码核对；不一致直接 `PRODUCER FAIL`（失败关闭），避免把跨版本复算显示成同版本可复算。`producer.python` 只记录、不参与失败判定（补丁版本差异不应让正确复算失败）。没有 `producer` 的修订前旧包仍可 replay，但输出明确提示“无法核对导出代码版本”；v3 验收应拒收或转入书面标注的跨版本例外流程。
- 发行物用 `scripts/build_release.py` 生成，`RELEASE.json.git_commit` 与 wheel 内 `BUILD_COMMIT`、包内 `producer.commit` 应逐一对应；验收方法见 `docs/交付与验收SOP.md` §5。
- 不解决“私钥持有人作恶”；不解决包外 pin 记录被同时改写；不替代 M-02 数据最小化。

## 8. 发行物自身签名（rehearsal 边界）

- `scripts/build_release.py --signing-key <私钥>` 在 `dist/wca-replay-<版本>/` 额外写：
  - `SHA256SUMS`：只覆盖**构建时的 5 个顶层文件**（wheel、`requirements.lock.txt`、
    `README-验收.md`、`RELEASE.json`、`VERIFY-SIGNATURE.txt`）；
    交付目录后续追加的 `old-wheels/`、`old-packages/`、旧发行物清单等**不在保护范围内**，
    以发行目录内 `SHA256SUMS-覆盖范围.md` 与实际行数为准；
  - `SHA256SUMS.sig`：对 `SHA256SUMS` 原始字节的 Ed25519 detached 签名（Base64）；
  - `VERIFY-SIGNATURE.txt`：key_id、公钥副本与可执行的 PyNaCl 验证片段；
  - `RELEASE.json.release_signature`：`file/algorithm/key_id/public_key_b64/signed_file/scope/note`。
- 验证顺序：先按 `SHA256SUMS` 逐文件核对，再用 `VERIFY-SIGNATURE.txt` 验 `SHA256SUMS.sig`；任一不一致拒收。
- **边界**：`SHA256SUMS.sig` 只签 `SHA256SUMS`，不覆盖 `.sig` 自身，也不构成可复现构建证明；替换 wheel 与 `SHA256SUMS` 后重签仍可能发生，必须靠独立渠道核验 key_id。发行 README 只写构建方法，**未验证可复现构建**。
- 发行签名与举证包签名是两套用途：前者保护“验算工具发行文件”，后者保护“单个证据包”。
- **硬规则：同一把私钥不得同时用于发行物签名与包签名。** 两者必须使用不同的密钥对，key_id 分别记录：发行钥为 `var/release-keys/ed25519.key`（key_id `ed25519:5e797e18…`），包钥为 `var/handoff-keys/ed25519.key`（key_id `ed25519:b07741b2…`）。
- **唯一例外（rehearsal）**：仅在非交付的离线演练环境，允许用同一把**测试钥**同时验证两条路径；此时必须在 `RELEASE.json` 与包 `manifest.json` 中显式写 `key_scope=rehearsal-shared`，并在包外审计记录中登记“例外范围、执行人、时间、未用于正式交付”。正式发行物与正式交付包不得复用同一把私钥，也不得在同一交付批次内混用。
