# 维护策略（建议稿，2026-11-03）

> 本文只给建议与依据，**不实际修改数据库参数**；默认写入仍 `single`、规则包仍 v5。
> 所有数字均为临时库/本机实测，生产执行前需结合实际磁盘、内存、备份窗口复核。

## 1. 结论先行

1. **重导不是免费的**：`punch` 每轮重导会 `DELETE` 旧行再插入新行，132,900 行一轮约产生 132,900 个 dead tuple；autovacuum 能回收，但**表文件不会缩回**。
2. **重复密集导入有额外写放大**：跨文件重复会把 132,900 条逐行 `QUAL-DUP` 先落库、再删除并汇总成 3,000 条 summary；`ingest_issue` 表会明显膨胀（实测 3,000 live 行对应约 92.7 MB 表）。
3. **临时空间随唯一键行数增长**：`punch_seen` 在 132,900 / 501,000 行时约 21.8 / 84.0 MB；`punch_seen_stage` 已用 `TRUNCATE` 清块，最大约 0.66 MB（不随文件增长）。
4. **参数调整建议按表设置**：`punch` 与 `ingest_issue` 单独降低 `autovacuum_vacuum_scale_factor`，不要全局激进调参；`VACUUM FULL` 只在维护窗口、有备份时使用。
5. **重导频率建议**：避免在同一维护窗口内反复全文件重导；大文件（≥50 万行）安排在低峰，导入后观察 dead tuple、表大小与 `temp_bytes`。

## 2. 实测依据

### 2.1 REV-31 连续 COPY 重导（132,900 行）

| 轮次 | 耗时（ms） | punch 行数 | raw_file | stage 残留 | 表 total 字节 | n_dead_tup | autovacuum_count |
|---|---:|---:|---:|---:|---:|---:|---:|
| 导入前（已 3 轮） | — | 132,900 | 4 | 0 | 100,122,624 | 0 | 1 |
| 第 4 轮 | 7,027.0 | 132,900 | 4 | 0 | 100,122,624 | 132,900 | 1 |
| 第 5 轮 | 7,041.5 | 132,900 | 4 | 0 | 100,876,288 | 265,800 | 1 |

- 第 4/5 轮单轮约 132,900 dead tuple；总表大小只增加约 0.75 MiB，但 dead tuple 持续累积，直到 autovacuum 再次触发。

- `ingest_issue` 3,000 live 行对应 92.7 MB，是跨文件重复写入/删除 summary 的直接后果；不是 dead tuple 残留（dead=0），而是**已分配但未返还的空页**。

### 2.3 `punch_seen` 临时空间实测

| 规模 | punch_seen 最大字节 | punch_seen 行数 | punch_seen_stage 最大字节 | stage 行数 | punch 表字节 | seen / punch |
|---|---:|---:|---:|---:|---:|---:|
| 132,900 | 21,782,528（20.8 MiB） | 132,900 | 663,552（0.63 MiB） | 5,000 | 40,738,816 | 53.5% |
| 501,000 | 84,041,728（80.1 MiB） | 501,000 | 663,552（0.63 MiB） | 5,000 | 146,096,128 | 57.5% |

- 口径：在每块 `TRUNCATE punch_seen_stage` 前用 `pg_total_relation_size(to_regclass(...))` 采样；`temp_bytes` 本次均为 0。
- `punch_seen` 随唯一键行数近似线性增长（132,900 → 501,000 约为 3.86×，行数 3.77×）；`punch_seen_stage` 只承载当前 5,000 行块，最大约 0.66 MB，TRUNCATE 后不随文件累积。
- `punch_seen` 在事务结束/临时表 DROP 后释放；但**单次导入期间**的 PG 临时空间约为 `punch` 表的 53–58%。

## 3. 建议的 autovacuum 参数（仅建议，未执行）

### 3.1 表级（优先于全局）

```sql
-- 建议值；未在本项目执行
ALTER TABLE punch SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 1000,
  autovacuum_vacuum_insert_scale_factor = 0.05,
  autovacuum_vacuum_insert_threshold = 1000
);

ALTER TABLE ingest_issue SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 500
);
```

依据：
- 132,900 行文件重导会一次性产生约 13 万 dead tuple；按默认 `scale_factor=0.2` 需要等表显著变化才触发，日级重导可能滞后。
- `punch` 与 `ingest_issue` 是重导/重复治理的主要膨胀源；表级参数只影响这两张表，风险可控。
- `ingest_issue` 的 churn（404,700 插入 / 401,700 删除）比 live 行数高两个数量级，阈值应更低。

### 3.2 全局（谨慎）

| 参数 | 建议 | 说明 |
|---|---|---|
| `autovacuum_naptime` | 30s（默认 60s） | 缩短巡检间隔，让表级阈值更快生效；会增加后台唤醒频率 |
| `autovacuum_max_workers` | 3（默认 3） | 不建议盲目提高；需结合 CPU/IO |
| `autovacuum_vacuum_cost_delay` | 2ms（默认 2ms） | 不建议全局设 0；可在维护窗口临时调整 |
| `autovacuum_work_mem` | 256–512 MB（按内存） | 只影响 autovacuum 单 worker 内存 |
| `maintenance_work_mem` | 512 MB–1 GB（按内存） | 只影响手工 `VACUUM`/`CREATE INDEX`，不自动执行 |
| `temp_buffers` | 保持默认或按会话设置 | `punch_seen` 84 MB@501k；提高 temp_buffers 只是延后磁盘临时文件，不等于解决临时空间 |

**不要**为提高导入速度而关闭 autovacuum；也不要把全局 `scale_factor` 一律降到 0.02。

## 4. 重导频率与操作建议

1. **正常重导**：每月一次全量、每周增量/修订文件；避免同一小时连续重导同一 `rel_path`。
2. **大文件（≥50 万行）**：安排在低峰；导入前确认临时表空间/磁盘余量（按 `punch_seen` 约 0.17 KB/行估算，501k 约 84 MB，1M 约 168 MB）。
3. **重复密集文件**：跨文件重复导入会先把逐行 QUAL-DUP 落库再汇总；如无业务必要，避免反复重导同一内容到不同 `rel_path`。
4. **维护窗口**：重导后至少等待一轮 autovacuum（30–60s 巡检）再评估表大小；不要导入后立即跑 `VACUUM FULL`。
5. **备份**：任何 `VACUUM FULL` / `REINDEX` 前先做备份；活动库操作按现有 `--allow-active` + 备份哈希 + 双确认流程，本文不建议直接执行。

## 5. 监控指标与告警阈值（建议）

| 指标 | 查询 | 建议关注 |
|---|---|---|
| dead tuple | `pg_stat_user_tables.n_dead_tup` | `punch` / `ingest_issue` dead > 20% live，或 > 100,000 |
| 表大小 | `pg_total_relation_size(relid)` | 超过同规模全新导入的 2×（如 punch 132k 基线约 40.7 MB） |
| 表增长 | `n_tup_ins` / `n_tup_del` | 单次导入 delete 接近 live 行数时，安排巡检 |
| autovacuum | `autovacuum_count` / `last_autovacuum` | 长时间未运行、或 dead 持续上升 |
| 临时空间 | `pg_stat_database.temp_bytes` | 单库累计持续增长；结合 `pg_ls_tmpdir()` 检查临时文件 |
| 临时表大小 | `pg_total_relation_size(to_regclass('punch_seen'))`（仅导入期间可见） | 501k 约 84 MB；> 200 MB 时评估分块或上限 |
| 进行中的 vacuum | `pg_stat_progress_vacuum` | 长事务、I/O 高时避免叠加 `VACUUM FULL` |

## 6. 何时需要人工 VACUUM

满足任一条件时，先在维护窗口执行 `VACUUM (ANALYZE) <表>`（在线、可并发读）：

1. `n_dead_tup` 连续两个巡检周期 > 20% live，且 autovacuum 未触发/被长事务阻塞；
2. `pg_total_relation_size` 超过同规模全新导入基线 2×，磁盘余量 < 20%；
3. `ingest_issue` 在重复密集导入后表大小显著高于 live 数据所需（实测 3,000 行约 92.7 MB）；
4. 索引膨胀明显（`pg_stat_user_indexes` / `pg_relation_size(indexrelid)`）。

`VACUUM FULL` 只在以下情况使用，且必须停机/维护窗口 + 备份：

- 磁盘空间已经紧张，普通 VACUUM 无法返还空间；
- 表长期高 churn 且业务可接受锁表；
- 执行前确认 `pg_stat_activity` 无长事务、无并发导入。
