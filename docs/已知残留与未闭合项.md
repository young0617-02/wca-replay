## 二、四项流程/法律未闭合

1. **信任根（Who signs the signer?）**
   评审方会追问：“我凭什么相信这把公钥就是你公司的？”
   我们能答：当前是**目录内 pin 公钥**，只能证明“包与这把钥匹配”；要防“公钥与包一起被替换”，
   需要评审方侧独立渠道（合同附件、官网指纹、企业 PKI）分发指纹——**本轮未闭合**。

2. **真实具名确认（Real named human confirmation）**
   评审方会追问：“`confirmed_by` 是谁？出了事谁负责？”
   我们能答：样例包里是**演示身份**，审计链能证明“某个身份确认过哪条结论”，
   但不能证明该身份对应真实自然人；要接评审方目录服务/实名认证与授权矩阵——**本轮未闭合**。

3. **法律文本充分性（Sufficiency of legal text）**
   评审方会追问：“规则条文引用是否完整、是否为最新有效版本？”
   我们能答：规则包只覆盖 PoC 范围内的条文与口径，**不构成法律意见**；
   要由评审方法务确认文本范围、版本与解释口径——**本轮未闭合**。

4. **数据合规（Data compliance）**
   评审方会追问：“样例里有没有个人信息？真实数据怎么脱敏、留存、删除？”
   我们能答：交付只用**合成数据**，不含真实个人信息；真实接入需要评审方完成个保法/数据出境/
   留存期限评估与数据处理协议——**本轮未闭合**。

## 三、使用边界

- 本目录验证的是：**确定性规则计算、证据包可复算、篡改可被发现、结论可回放**。
- 本目录**不验证**：企业真实制度是否合法、真实人事数据是否合规、生产环境的密钥与权限体系。
- 任何对外材料引用本目录结论时，必须同时保留这句话：
  **“PoC 验证工具 + 样例包，不构成合规结论，不可作生产就绪依据。”**

## 四、验收结论的边界

1. **护栏实现不随交付。** `scripts/check_handoff_refs.py` 与 `tests/test_doc_facts_guard.py`
   属仓库内工具，未随本目录交付；客户无法用本目录复核“护栏已修”这一声称。
   对外只能表述为“护栏存在、上一轮发现的漏洞已按实测修复”，**不得把该声称写入验收结论作为证据**。
   本目录可独立复核的是文档与实物的一致性：`交付清单.txt` 的逐文件哈希、锚点 `file`
   的可解析性、`SHA256SUMS` 与包签名的验算。

2. **JSON 自由文本不参与验算。** `wca-verify` 只核结构字段（版本、路径可解析性、摘要、签名、
   计数等），不核锚点 `note` 等自由文本。实测把 `note` 改成与实物不符的计数、并写入一个不存在的
   zip 路径，`wca-verify` 仍返回 `RESULT OK`。这是设计边界，不是缺陷；自由文本的准确性只能靠
   本目录内的文档扫描发现，而该扫描器同样不随交付（见上一条）。

3. **`final_conclusions` / `delivery_registered` 口径（0.4.18 已改，旧包仍按旧口径读）。**
   0.4.17 及更早实测：`APPROVED`、`REJECTED`、`NEEDS_MORE_DATA` 三种决定都会进入
   `conclusions_final.csv` 并计入 `counts.final_conclusions`；`signed: true` 只表示本 run 存在
   `evidence.sign` 交付登记，零确认时也可为 `true`。0.4.18 起：新增 `counts.approved_conclusions`
   与 `responsibility.approved_findings`（只统计 `decision=APPROVED`），`final_conclusions` 保留为
   “已人工处置合计”；`signed`/`signed_by` 改名为 `delivery_registered`/`delivery_registered_by`。
   旧包仍只有旧字段，`wca-verify` 与 `wca replay` 按“遇新读新、遇旧回落”双读，两字段并存且取值
   不一致判半迁移包并 FAIL。已交付的 0.4.17 包、签名与 `handoff/20261104-第十九轮整改/` 均未改。
   实测依据：`docs/具名确认-流程与角色定义.md` §11；口径：`docs/口径说明-已确认结论.md`；
   包外勘误：`包外勘误附件/`（0.4.17 包的两页勘误，随本目录交付）。

4. **金额表述边界（文档侧，已登记）。**
   包内 `README.txt` 第 3 行写“本包不含任何应付金额”，同一句在 `src/evidence.py:500` 的
   `PACKAGE_README` 与 `manifest.disclaimer` 里。2026-11-09 只读实测：包内 `findings`、
   `conclusions_final`、`responsibility` 对金额类词零命中，人工录入金额字段已在导出侧剔除
   （`src/evidence.py:656-666`），所以“不含应付金额”字面成立；但 `inputs/employee.csv` 的
   `normal_hourly_cents`（工资基数）12 人全部有值，原句容易被读成“包内没有任何工资数据”。
   当前**不影响验算与回放**（2026-11-09 干净 venv 单包实测：`engine-only` 的 `wca-verify` 与
   `wca replay` 均 `RESULT OK`、exit 0；8 包整体在冻结核对时为 16/16），也不需要重出包；
   只能用包外勘误解决，下一版本再改文案。
   勘误页：`docs/勘误-金额表述.md`；待办登记：`docs/下一版本候选清单.md` P0-03。

5. **包外勘误附件的位置与保护范围。** `包外勘误附件/` 的 4 个文件原样并入本目录（内容是
   0.4.17 包的两页勘误），**计入** `交付清单.txt` 的逐文件哈希；但它们位于 `release/` 之外，
   **不在** `release/SHA256SUMS` 与发行签名的保护范围。对 0.4.18 包本身不适用，仅作 0.4.17
