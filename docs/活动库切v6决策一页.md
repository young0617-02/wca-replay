> `reports/变异测试.md`。

## 一、切换收益

1. **审批证据模型升级**：v6 的 REG-01 从旧 `worktime_approval` 改读 P0 覆盖投影
   （批文 + 版本 + 范围 + 员工覆盖），有文号/版本/生效期/岗位/城市/附件 SHA-256/发布时间；
   旧表只有“一行一文号”的扁平记录，无法表达版本链与 org 范围。
2. **结论可追溯**：v6 新 finding 的 `rule_version` 标 v6，包三元组与 findings 版本一致；
   旧 finding 不改写（REV-20）。
3. **审计分段**：v6 首次 check 追加 `rule_pack.epoch.start`，v5 旧段保留、v5 旧包继续 legacy replay；
   v5 段封闭后不能再混写。
4. **迁移可对照**：`approval-migrate` 输出 v5/v6 REG-01 命中差异、丢弃/合并原因；
   备份副本演练已证明 `only_v5=0 / only_v6=0`，迁移没有放大审批覆盖。
5. **规模可控**：3,000 行审批实测输入 11,493,475 字节，落在 10.5–11.5 MiB 的 warning 档，
   距 12 MiB 硬上限余 1,089,437 字节；不需要分卷、不放大预算。

## 二、两种执行方式

| 方式 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A. 临时库迁移后四表回灌 | 临时库 apply → `pg_dump --data-only` 四表 → 活动库导入 | 工具不直接写活动库，权限最小 | 四表 ID/序列需保留或重映射；审计事件 `approval_doc.migrate` 不在活动库链里；导入必须单事务，失败整批回滚；拼接错误可能让 coverage 指向错版本 |
| B. 一次性 `allow-active`（**已实现，未执行**） | `approval-migrate --apply --allow-active` + 备份/SHA-256/双确认 + 实际 `current_database()` | 与临时库演练同一代码路径；ID 由活动库生成，无跨库重映射；审计事件直接进活动库链；单事务 | 唯一绕过临时库白名单的路径；任何 bug 直接写活动库，只能靠备份回滚；必须严格维护窗口和双人复核 |

**决策建议**：采用 **B**。理由：避免四表 ID/审计链跨库拼接；代码路径与已演练的副本一致；
但 B 的放行条件必须全部满足（备份存在+SHA-256、`--confirm-active wca_worktime`、
`--confirm-apply wca_worktime`、实际 `current_database()` 命中、单事务、审计事件）。
A 保留为对照，不推荐默认执行。

## 三、维护窗口与双人复核

- **窗口**：停止写入/导入；Web/API 只读或停机；确认无并发 check/export/publish。
  建议预留 **60–120 分钟**（活动库当前 12 人规模；若真实台账接近 3,000 行，
  参考副本演练 check 约 0.7 s、3,000 行演练 check 44 s / export 9 s / replay 39 s，按实际规模调整）。
- **双人复核**：
  - 执行人：按清单执行备份、恢复副本、迁移、check/export/replay/verify；
  - 复核人：核对备份 SHA-256、实际库名、四表计数、员工集合、三元组、审计头哈希与回滚命令；
  - 批准人：确认变更单与回滚窗口，未批准不得执行。
- **前置**：`python -m src.cli verify` 通过；记录当前 run 三元组、`audit_event` 最大 seq/头哈希、
  旧台账行数/文号/员工集合、四表计数。

## 四、验收判据

| 判据 | 要求 |
|---|---|
| 备份 | dump 存在、非空、SHA-256 与记录一致；已恢复到临时恢复库并核对计数 |
| 实际库名 | 迁移/切换命令连接后读到的 `current_database()` = `wca_worktime`，不是配置自述 |
| 迁移 | 批文/版本/范围/覆盖计数与 dry-run 计划一致；丢弃/合并原因逐条可解释；`only_v5` **必须为 0** |
| REG-01 | v6 命中集合与临时库预测一致；`only_v6` 逐人解释；v5 旧台账行数不变 |
| 结论版本 | 新 v6 finding `rule_version` 全 v6；旧 run 的 finding 原值不改 |
| 审计 | `verify` 通过；v5 旧段/ v6 新段不断链；`EPOCH OK`；`audit_genesis` 不变 |
| 举证包 | v6 包 `approval_source=v6-coverage`、`approval_rows` 与覆盖一致；`verify.py` 三 OK；replay 条数/三元组一致 |
| 旧表 | `worktime_approval` 行数不变；v6 告警仍可见，不静默 |

**副本演练已实测**：`wca_drill_restore_v6_20261103` 上 v5/v6 REG-01 均 4、only 0；
v6 check 115 条、8 输入 301,910 字节、包 53,738 字节、replay 115/115、verify 三 OK。

## 五、回滚步骤（失败即退回 v5）

1. **停止**所有写入/导入，保留现场日志；不继续重跑。
2. 确认备份可读：`pg_restore --list <pre-v6 dump>`。
3. **先在临时回滚库演练**：恢复备份到 `wca_rollback_drill_<stamp>`，
   用独立 identity 运行 `verify`，核对 run 三元组、audit 头哈希、旧台账行数、四表计数。
4. 演练通过后，才对活动库执行全库恢复（`pg_restore --clean --if-exists`，双人复核）。
5. 恢复后设置 `WCA_RULE_PACK=v5`，运行 `verify` 与一次 v5 check；四表计数/旧台账/审计头哈希
   必须与切换前快照一致。
6. 记录回滚时间、备份 SHA-256、恢复库结果与最终 `verify` 输出。

**关键原则**：v6 写入纪元后 v5 段已封闭，不能只改 `WCA_RULE_PACK` 回 v5 继续跑；
必须恢复切换前的全库备份或受控快照。

## 六、失败回退条件（任一命中即停）

- `only_v5` 非空（v6 比 v5 更宽松，覆盖被放大）；
- 迁移后四表计数/员工集合与 dry-run 不一致，或丢弃/合并原因无法解释；
- replay 三元组或结论条数不一致，且无法用包内输入解释；
- `verify` 断链、`EPOCH OK` 失败、审计头哈希与快照不一致；
- 备份缺失、为空、SHA-256 不符，或恢复库演练失败；
- 发现并发写入/审批发布未停止。

## 七、不切会怎样

- 活动库继续 v5：REG-01 仍读旧 `worktime_approval`，P0 覆盖投影/版本链/org 范围不参与判据；
- 旧台账若继续增长，仍会出现“多员工同文号、版本不可表达、范围只到岗位字符串”等限制；
- `approval_doc`/版本/覆盖四表保持空置，v6 包格式、覆盖指纹、迁移对照能力无法在活动库使用；
- 不会立即破坏现有判据：活动库仍显式钉 v5，既有 run/包/审计链可继续用；代码默认 v6
  只影响未显式指定规则包的新库/新 run；
- 代价是技术债与后续迁移成本随时间增加；若业务已需要版本链/范围/覆盖证明，建议在窗口内切换；
  若暂时没有这类需求，可保持 v5，但应把本决策页与回滚方案保留为待执行状态。
