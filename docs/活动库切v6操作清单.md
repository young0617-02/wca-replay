## 3. 活动库四表回灌（受控，双人复核）

> 当前 CLI 不会在活动库执行 `approval-migrate`。如果产品决定采用“临时库迁移后回灌”的方式，
> 在维护窗口内用 `pg_dump` 只导出四张 P0 表（`--data-only --table=...`）再导入活动库；
> 不要手工改旧表，不要删除旧 `worktime_approval`。若产品决定给工具加一次性 `--allow-active`
> 开关，必须单独评审、单独测试，本文不假设该开关存在。

步骤：

1. 在临时库确认四表计数与 dry-run 计划一致：批文数、版本数、范围数、覆盖数；
2. `pg_dump` 只导出四表数据（`approval_doc`、`approval_doc_version`、`approval_doc_scope`、`employee_approval_coverage`），记录文件 SHA-256；
3. 活动库先 `pg_restore --list` 核对目标表；
4. 导入后在活动库只读核对计数、员工集合、附件哈希数量；
5. 旧 `worktime_approval` 保持原样；不执行任何 `DELETE/UPDATE`。

### 3.1 两种迁移执行方式的差异与风险

| 方式 | 做法 | 优点 | 风险 / 必须处理 |
|---|---|---|---|
| A. 临时库迁移后四表回灌 | 临时库 `approval-migrate --apply` → `pg_dump --data-only` 四表 → 活动库导入 | 工具永远不写活动库；可先在临时库完整演练 | 四表 ID 需保留/重映射：`approval_doc.doc_id`、`approval_doc_version.version_id`、`approval_doc_scope.scope_id`、`employee_approval_coverage.coverage_id` 及序列必须对齐；否则覆盖指向错版本。审计事件 `approval_doc.migrate` 只在临时库链里，活动库链不会自动出现，需单独说明/补记，不能假装已在链上；导入必须在单事务中完成，失败要整批回滚 |
| B. 一次性 `allow-active` 开关（**已实现，未执行**） | `approval-migrate --apply --allow-active --backup-path <dump> --backup-sha256 <sha> --confirm-active wca_worktime --confirm-apply wca_worktime ...` | 与临时库演练走同一套代码路径；ID 由活动库生成，无跨库重映射；审计事件直接进活动库现有链；迁移写入在单事务内 | 工具从“拒绝活动库”变为“可在活动库写”，风险最高；必须同时满足：备份存在+SHA-256、确认串、实际 `current_database()`、单事务、审计事件；任一失败 rc=2 不写库。仍需维护窗口、双人复核、备份校验与回滚演练 |

**方案 B 已按用户决定实现（REV-26），但未在活动库执行。** 放行条件不是配置自述，而是连接后的
`current_database()`；`--allow-active` 只能与 `--apply` 同用，活动库 dry-run 仍禁止。
A（临时库迁移后四表回灌）未实现；其 ID/序列与审计链拼接风险仍存在。
B 的优点是避免跨库 ID/审计拼接；风险是唯一绕过临时库白名单的路径，必须严格按维护窗口执行。
备份副本演练已通过：`wca_drill_restore_v6_20261103`，v5/v6 REG-01 均 4、only_v5/only_v6 均 0，
v6 check 115 条、export 8 输入 / 301,910 字节、包 53,738 字节、replay 115/115、verify 三 OK。
