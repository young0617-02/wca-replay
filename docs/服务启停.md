# 服务启停 · 一键开关的行为边界与恢复建议

> 2026-10-09 ｜ 对应代码 `src/service_manager.py`（状态机）+ `src/service_cli.py`（共同内核）
> + 两个入口：`python -m src.cli start|stop|status` 与 `python tools/start_services.py` / `tools/stop_services.py`
> **两个入口走的是同一个内核**，行为必须一致；不一致就是缺陷（本轮查出并修掉一条，见第六节）。

## 一、它是什么 / 不是什么

是：**本机单用户的进程管家**。按 `config/services.json` 的清单把服务拉起来、探活、优雅停掉、
把端口与资源账本核对干净，并把每次操作写进 `var/logs/tool-*.log`。

不是：

| 别指望它 | 原因 |
|---|---|
| systemd / Supervisor 的替代品 | 不做崩溃自动重启、不做开机自启、不做进程树看护；关掉终端进程还在（要停就 `stop`） |
| 外部依赖的启动器 | `managed: false` 的服务（如 ollama）**只探测、不启不停**；缺了会报 `missing-dependency` 并给处置建议，不会去猜一个没配好的模型地址 |
| 公网部署工具 | 配置里只绑 `127.0.0.1`；没有 TLS、没有并发多实例编排，也不打算做 |
| 端口冲突仲裁者 | 端口被**别人的**进程占用时报 `port-occupied` 并给出 pid 核查命令，**绝不替你杀不认识的 pid** |

## 二、`config/services.json` 字段含义

顶层：`schema` / `note` / `defaults` / `services[]`。`defaults` 里的值会被每个服务继承，服务内同名字段覆盖它。

| 字段 | 含义 | 取值与后果 |
|---|---|---|
| `name` | 服务名 | `--only` 用它筛；也是 `var/run/<name>.json`、`var/logs/<name>.log` 的文件名 |
| `managed` | 本工具是否负责启停 | `true`＝负责；`false`＝只探测（外部依赖） |
| `start_order` / `stop_order` | 启动升序、停止降序 | 数值小者先起；停止时反过来，避免依赖被先抽走 |
| `host` / `port` | 监听地址与探测端口 | 端口通不通是**唯一就绪判据**（`probe: "port"`），本工具不看 HTTP 健康检查 |
| `probe` | 探活方式 | 目前只有 `port`；`port` 之外未实现，写别的会被当作端口探测 |
| `kind` / `module` / `argv` | 被管理服务的启动方式 | `python-module` 时用 `argv`，其中 `<python>` 会被替换成**当前解释器**（所以必须用 `.venv` 的 python 起，否则服务也跑在错误环境里） |
| `cwd` | 子进程工作目录 | 默认 `.`（项目根）；`rel_path` 类路径推导依赖它 |
| `env` | 注入子进程的环境变量 | 例：`{"WCA_SERVICE": "api"}`；**不放密钥**，密钥只在 `.env`，由被启动的代码自己读 |
| `required_when` | 该外部依赖何时算"必须有" | `{"env": "WCA_LLM_PROVIDER", "equals": "ollama"}`：只有 `.env` 真是这个 provider 才要求在线，否则 precheck 报 `not-required` 并跳过 |
| `ready_timeout_s` | 启动后等待端口就绪的上限 | 默认 30 s；超时报 `failed` 并把日志路径给你 |
| `grace_period_s` | 优雅停止等待上限 | 默认 12 s；先写 `<name>.stop` 停止请求（**主通道，与信号无关**），超时才强杀 |
| `notes` | 给人看的说明 | 工具不解析它，改了不影响行为 |

日志与状态落盘位置来自 `defaults`：`log_dir`（`var/logs`）、`run_dir`（`var/run`）。这两处都在 `.gitignore` 里，不入库。

## 三、参数矩阵（两个入口都成立）

| 命令 | 认的参数 | 说明 |
|---|---|---|
| `cli start` / `tools/start_services.py` | `--config` `--env` `--only` `--no-restart` `--timeout` `--json` `--verbose` | 默认**在跑就先停后起**；`--no-restart` 改为拒绝动手（退出码 1，附处置建议） |
| `cli stop` / `tools/stop_services.py` | `--config` `--env` `--only` `--grace` `--force` `--no-checkpoint` `--json` `--verbose` | 默认优雅停 + 停完做 WAL 落盘检查；`--force` 跳过宽限直接强杀 |
| `cli status` / `tools/stop_services.py --status` | `--config` `--env` `--only` `--json` | **纯只读**，不停任何东西、不写状态文件；`--only` 真过滤（写了不存在的服务名 → 退出码 2 并打印原因），`--json` 输出 `{"as_of","services","filter","judged","all_ok"}`，其中 **`all_ok` 只统计 `required` 为真的服务**——按配置不需要的外部依赖（如 provider≠ollama 时的 ollama）不把整体判成不健康 |
| 三个子命令共有 | `--env` | 指定 `.env` 路径，影响 `required_when` 的判断。**注意**：`--env` 挂在 CLI 根解析器上，桥接时显式传给内核 |

退出码：`0` 全部干净 / `1` 有服务没干净或动作被拒 / `2` 配置错误（清单读不出、`--only` 里没有这个服务名）。

## 四、状态判读（`status` 的六种结论）

| 显示 | 内部 origin | 你该做什么 |
|---|---|---|
| `运行中（本工具启动）` | `ours` | 正常 |
| `端口被外部进程占用` | `foreign` | 先看 pid：`tasklist /FI "PID eq <pid>"`，确认是谁再说，别盲杀 |
| `状态残留（进程已不在）` | `stale` | `var/run/*.json` 是陈年的（崩溃或机器重启后）；下一次 `start` 会覆盖它 |
| `外部依赖在线` | `ready` | 正常（不由本工具管） |
| `外部依赖不在线` | `absent` | 若 `required_when` 命中，启动会被拦下并给建议；否则忽略 |
| `未运行` | `none` | 需要就 `start` |

## 五、实测行为（2026-10-09 09:20–09:21，本机 loopback，`.venv` 解释器）

| 动作 | 结果 | 取样 |
|---|---|---|
| `cli start`（首次） | rc=0，总 2265 ms；api 就绪 **1539 ms** | 账本 `open_sockets=0 sqlite_handles=0 state_files=['api.json']` |
| 起后真打 HTTP | `GET /login` 200、`/` `/qa` `/review` 未登录 **401** | 服务端日志确认加载 `rule_pack=rp-2026.10.gd-pilot-standard.v4` |
| `cli start`（已在跑） | rc=0，**先优雅停 862 ms 再起**，总 3051 ms | precheck 显示 `running` |
| `cli start --no-restart` | rc=1，pid **未变**，打印处置建议 | 语义＝"不重启就别动它"，不是失败 |
| `cli stop` | rc=0，优雅 **764 ms**；`wal_checkpoint busy=0 log=0` | 停完端口探测连不上、`var/run` 清空 |
| `tools/start_services.py` + `tools/stop_services.py --force` | rc=0，起 1450 ms / 强杀 784 ms | 与 cli 桥接行为一致 |

## 六、本轮查出的三个不一致（都已修，留此备查）

1. **本文曾经不存在**：`config/services.json` 与 README 都写着"字段含义见 `docs/服务启停.md`"，而文件没有——
   悬空链接就是交付完整性缺陷，不是排版问题。
2. **`status` 吃参数不办事**：`--json` 输出的还是人读表格、`--only` 根本不裁剪。
   根因是 `status_text()` 接收了参数却没读它。这一类**静态对账抓不到**——参数在上游 `_service_argv`
   确实被"读过"，只是下游把它丢了；只有实跑能发现。现在 `--only` 会过滤（写了不存在的服务名直接退出码 2），
   `--json` 输出 `{"as_of","services","filter","all_ok"}`。
3. **`--no-restart` 的提示自相矛盾**：precheck 无条件写「已在运行，将先停后起」，紧接着又拒绝重启。
   现在按 `restart_if_running` 分支措辞。

## 七、明确没做 / 未验证

1. 两个终端**同时** `start` 的竞态（没测；WAL + `busy_timeout=5000` 不等于并发编排）。
2. 非 Windows 平台行为（信号通道按 Windows 实现与测试）。
3. 进程崩溃后的自动拉起、健康检查重启、日志轮转。
4. 公网暴露下的加固（TLS、限流、CSRF 之外的浏览器侧策略）——本项目不打算做，服务只绑 127.0.0.1。
5. **`WCA_LLM_PROVIDER` 决定要不要出网**：本机 `.env` 现在是 `openai`，也就是说服务一起来、
   有人往 `/qa` 提问就会**真的调用云 API 并产生账单**。离线演示请先把它改成 `stub`。
   本轮我起了服务做开关验证，但**没有发出任何一个问答请求**（服务端日志里 0 条问答记录）。
