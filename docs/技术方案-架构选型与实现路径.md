## 2. 技术路线对比与选型结论

| 路线 | 代表形态 | 能不能满足需求 §1.4 的 G3（错承诺 0 / 越权 0） | 能不能满足 G5（无凭证复跑） | 单人 19.5 人日可行性 | 结论 |
|---|---|---|---|---|---|
| A. 通用 RAG 问答 | 文档切块 + 向量召回 + LLM 生成 | ✗ 数值与金额由模型口述，无法机械证明"不承诺" | △ 模型不可用即整链失效 | 高 | **否**：项目命题（可举证判断链）落空 |
| B. 自主 Agent（多轮工具 loop） | LLM 自行决定调用序列与终止 | ✗ 循环引入不确定性，评测归因被污染 | ✗ | 低（调试成本不可控） | **否**：需求 §6.2 已排除"看起来更真实"的做法 |
| C. 规则引擎 + LLM 只做解释（Workflow） | 确定性判据 → 受限函数调用 → 检索增强 → 出口白名单守卫 | ✓ 白名单 + 只解释不给数，两条红线可测 | ✓ 离线 stub 跑同一条链 | 中 | **选定**：与基线一致，也是需求 §1.2 的原始定位 |
| D. 传统考勤 SaaS 模块 | 无 AI，纯规则 + 报表 | ✓ 但无问答链 | ✓ | 中 | **否**：作品集落点（AI 应用开发）不成立 |

**选型结论**：走 **C**。本方案的全部技术选择都服务于一个约束——**两条红线（错承诺 0、越权 0）必须是可机械断言的，而不是靠提示词自觉**。

## 3. 分层选型

### 3.1 TECH-01 模型后端：闭源 API / 开源本地 / 混合

| 候选 | 优 | 劣 | 判定 |
|---|---|---|---|
| 闭源云 API（OpenAI 兼容协议） | 无显存门槛；中文叙述质量好；单价可按 token 核算 | 数据出域；账单成真；无凭证时链路不可用 | **采用**（需求决定 3） |
| 本地开源模型（Ollama 等） | 零现金、零出域 | 基线已有 `HttpProvider(ollama)` 通道但本机显存与模型分发不在 19.5 人日内；评审者复现门槛反而更高 | **保留通道、不作默认**，不投入新工作量 |
| 混合（云叙述 + 本地兜底） | 可用性最好 | 两套权重/两套行为 → 评测归因分裂；**且已决定覆盖广州、深圳、佛山三市**，条文按地域分档属数据分档，不该再叠加按地域分模型 | **不采用为"双模型混合"**，但采用**"双轨 provider"**（见下） |

**结论（TECH-01）**：**双轨 provider，一轨云 API、一轨离线 stub**。
- `WCA_LLM_PROVIDER=stub`（默认）→ `pytest -m "not llm"`、评测集打分、界面冒烟全部离线可跑（NFR-19 / G5）；
- `WCA_LLM_PROVIDER=cloud` → 演示档与"真模型重测"档，走 `src/llm.py:308` 已有分支；
- 两轨**共用同一套出口守卫**（`src/guard.py` 数字白名单 + 重大事项拒诺），因此"换真模型"不改变红线机制，只改变指标数值——这正是评测集要重跑的理由（GAP-10）。

云 API 接入前必须实测确认的三件事（不写进结论，写进 `docs/口径声明.md`）：① 实际单价与账单口径；② 结构化输出（意图 JSON）在 temperature=0 下的稳定性；③ 端到端 P95 是否落在需求 NFR-06 的 4 s 设计值内。**当前全部为 `[未测]`。**

待填：`【填：模型名】`、`【填：base_url】`、`【填：月度现金上限】`、`【填：实际账单】`（集中写进 `.env` 的 TODO 段，不散落）。

### 3.2 TECH-02 架构：Prompt / RAG / Function Calling / Agent / Workflow

| 机制 | 本项目的用法 | 不用在哪 |
|---|---|---|
| Prompt | 两段固定模板：意图分类（`src/llm.py:263`）、事实叙述（`src/llm.py:283`，强制"只用给定数字"） | 不做自由对话、不做多轮上下文累积 |
| RAG | **带 ACL 谓词下推的检索**（`src/retrieve.py`，SQL WHERE/JOIN 层过滤），命中条目作为出处随答案返回 | 不做"先召回再让模型过滤"（NFR-01 红线，变异测试 M5 专门盯这条） |
| Function Calling | **受限**：LLM 只产出 `{intent, period, want_amount}`，工具集合固定为「本人聚合 + findings 明细」两个确定性入口（`src/agent.py:260-306`） | 不让模型决定调用序列，不给它算钱权力 |
| Agent | 单次编排：plan → retrieve → tool → compose → guard → persist | 不做自主 loop / 不自愈重规划 |
| Workflow | 校验侧是纯确定性批处理（gen → ingest → check → report → export），CLI 与界面共用同一条链（避免双实现，需求 §7.3-5） | 不做通用工作流引擎 |

**结论（TECH-02）**：**Workflow 主干 + 受限 Function Calling + ACL 下推 RAG + 出口白名单守卫**。界面（P6）挂在同一条 Workflow 上，不新开第二条实现路径。

### 3.3 TECH-03 数据层：向量库 / 数据库 / 缓存 / 日志

| 子层 | 现状 `[实测]` | 结论 | 理由与代价 |
|---|---|---|---|
| 数据库 | SQLite 单文件 `var/worktime.sqlite3`，23 张表，判定链禁浮点（`tests/test_acceptance.py:150` 扫 schema） | **沿用 SQLite**，新增 `app_user` / `app_session` 两张表 | 需求 NFR-07 要"无容器、评审者一次跑通"；引入 PG 会直接破坏 G5 |
| 向量库 | `WCA_EMBEDDING_BACKEND=bm25`，代码里 vector 不可用时如实降级并标 `degraded_from`；语料仅 34 条静态 + 每员工 2 条动态 | **本期不引入向量库**（不新增 sqlite-vec/FAISS 依赖） | 34 条语料上 BM25 的检索段 5.3 ms `[V1.1 时点实测]`；引入向量库要额外维护 embedding 模型分发，与"无凭证可跑"冲突。**触发引入的条件**：语料 >500 条，或 Hit@5 实测 <【填：可接受的 Hit@5 阈值】，两者任一成立才立项 |
| 缓存 | 无 | **不引入** | 整轮校验稳态 199.8 ms `[V1.1 时点实测]`，瓶颈不在 I/O；加缓存反而让"同输入同结论"的可复现性变复杂 |
| 日志/留痕 | `audit_event`（hash 链 append-only）+ `question_log` + `span`（分段计时）+ `var/logs/` 进程日志 | **沿用，并把三类新增事件纳入审计链**：登录/登出、复核结论登记、举证包签发 | 需求 US-RV-04 / US-UI-02 要"责任落到人"，日志里没有登录主体就无法归责 |
| 数据出域边界 | **违规**：`src/kb/loader.py:122-130` 把员工化名与薪酬基数写进可召回条目正文，`src/llm.py:284` 把全部 facts 原样送云端 → 姓名 + 金额基数会出域 | **必须改**（GAP-07） | 见 §5 |
