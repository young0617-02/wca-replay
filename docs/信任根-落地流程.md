# 信任根落地流程（PoC 阶段）

> 目的：把「公钥怎么到接收方手里、私钥怎么保管、旧钥怎么退役、`key_id` 怎么由独立渠道核验」写成可直接照做的流程。
> 边界：本文只写流程与记录要求，**不修改代码、规则包、`handoff/` 下任何文件与已交付的包**；不构成合规结论，也不声称信任根已闭合。
> 标注约定：**【事实】** 有文档或实物依据；**【实测】** 本次在本机/本目录实际执行得到；**【建议】** 本文判断；**【未知，需确认】** 现有材料没有、不得补全。
> 依据：`reports/四项未闭合事项-决策方案.md` §1、`docs/签名方案.md`、`docs/交付与验收SOP.md`、`docs/安全与证据链现状.md` §3、`handoff/20261104-第十九轮整改/KEY-NOTE.txt`、同目录 `README-验收.md` 与 `release/` 实物。

【实测】2026-11-09 用 PowerShell 对两个 `.pub` 做 Base64 解码后 SHA-256，得到 `ed25519:b07741b2…9555` 与 `ed25519:5e797e18…5bb6`，与上表逐字一致；`key_id` 算法为 `ed25519:` + 公钥字节 SHA-256 十六进制（`docs/签名方案.md` §2）。

### 1.2 硬规则与当前版本事实

- 【事实】**同一把私钥不得同时用于发行物签名与包签名**；两者必须不同 `key_id`。唯一例外仅限非交付的离线演练，且须在 `RELEASE.json` 与包 `manifest.json` 显式写 `key_scope=rehearsal-shared`（`docs/签名方案.md` §8）。
- 【事实】0.4.17 的包签名钥为 `b07741b2…9555`，发行钥为 `5e797e18…5bb6`（`README-验收.md` 生成区与 §八）。
- 【事实】0.4.17 发行物：commit `d4e5366b97637b2b4683339ce3ad5404469d8659`，构建时间 `2026-11-05T21:34:19+08:00`，`release/SHA256SUMS` 实有 **5 行**（`release/RELEASE.json`、`release/SHA256SUMS`）。
- 【事实】`SHA256SUMS.sig` 只签 `SHA256SUMS` 原始字节，不覆盖 `.sig` 自身；`old-wheels/`、`old-packages/` 与签发后追加文件不在保护范围（`release/VERIFY-SIGNATURE.txt`、`README-验收.md` §六）。
- 【事实】工具输出中的 `pinned` 统一为中性表述 `pinned (key matches supplied pin; independent key_id verification not done)`，即**只表示包与供给副本匹配，不表示来源身份已核验**（`docs/签名方案.md` §4、`docs/交付与验收SOP.md` §2）。

### 2.2 应该做到什么（【建议】，PoC 阶段最小可执行）

1. **存放位置**
   - 两把私钥**分开存放**：不同目录、不同介质；包钥与发行钥不得放在同一可移动介质或同一共享盘。
   - 私钥只放在受控机器本地目录或加密离线介质；不得进入仓库、邮件、聊天工具、交付目录、云笔记或任何同步盘。
   - 交付包、公钥、锚点记录可随交付；私钥、原始数据库、内部路径不交付（`docs/交付与验收SOP.md` §1）。
2. **权限控制**
   - Windows：对**每个私钥文件与所在目录**执行 `icacls /inheritance:r /grant:r <user>:F`（`docs/签名方案.md` §5 的既定做法）。8 个私钥文件与 7 个存放私钥的父目录已于 2026-11-09 全部收紧并复查，均只剩指定用户（目录用 `(OI)(CI)F` 保证新建文件继承同一权限，见附录 D.1、D.7）。
   - POSIX：`chmod 0600`，目录 `0700`。
   - 权限变更须留记录（执行人、时间、前后 ACL 摘要）。
3. **备份与恢复**
   - 至少 **2 份离线备份**，分地点存放，介质加密；备份内容与私钥文件逐字节一致，登记备份文件的 SHA-256（具体介质、地点、口令分持、恢复与演练频率见附录 D.9；**当前仅完成方案设计，未实际制作介质**）。
   - 备份介质不得与在用私钥同处一柜；备份清单只写「介质编号 + 存放地点 + SHA-256 + 登记人 + 日期」，不写私钥内容。
   - **恢复演练**：每 6 个月至少一次（周期为【建议】，实际周期【未知，需确认】）；演练只验证「能从备份恢复出与在用公钥 `key_id` 一致的私钥」，不签正式交付物。
   - 恢复步骤（流程）：取备份 → 复制回受控目录 → 重新收紧 ACL → 由 seed 推出公钥并核对 `key_id`（用 PyNaCl 本地计算，**不新增 CLI 参数**）→ 登记恢复事件与演练结论。
4. **谁能取用**
   - 每把钥指定**主保管人 1 名、备保管人 1 名**，名单与授权范围成文；具体人员 **【未知，需确认】**。
   - 取用必须有书面/工单申请，写明用途（签哪个包/哪个发行物）、预计产出、使用时段；非密钥持有人不得代为取用。
5. **双人控制怎么落（PoC 可行版）**
   - **物理双人**：私钥介质置于双锁容器，主、备保管人各持一把钥匙；开封须两人同时在场。
   - **使用留痕**：每次签名由执行人填写《密钥使用登记》，独立复核人核对「`key_id`、产物 SHA-256、包/发行物版本、时间」后签字。
   - **构建复核**：发行物构建完成后，由非执行人核对 `release/RELEASE.json.release_signature.key_id` 是否等于 `5e797e18…5bb6`，包签名 `key_id` 是否等于 `b07741b2…9555`，不一致即停发。
   - 更彻底的 HSM/KMS + quorum 属生产化选项，PoC 不强制；见第 6 节表。
6. **泄露与误用应急预案**
   - **判定**：私钥文件出现在非受控位置、介质丢失、他人取得、`key_id` 与预期不符、签名产物 `key_id` 异常，任一即视为疑似泄露/误用。
   - **立即动作**：停止用该钥签任何新包/新发行物；保全现场（不要删除文件、记录 ACL/时间/终端）；通知主备保管人与交付负责人。
   - **换钥**：按第 5 节生成新钥；旧钥标记「停用」但**不删除旧公钥**，旧包仍用旧公钥 + 旧 wheel 回放。
   - **对外**：在交付记录与接收方渠道中发布「旧 `key_id` 停用声明」，写明原因、生效版本、旧钥处置、旧包验签指引；不得只口头通知。
   - **事后**：写事故记录（时间线、根因、影响包清单、处置、复核人），并复查构建脚本参数与 `key_id` 守卫是否生效。
   - 现有两次事件已有记录（`docs/安全与证据链现状.md` 文末），但**尚无「泄露演练」与「停用声明模板」的成文记录**。

## 3. 公钥交付与接收方侧独立核验：分步流程

> 前提：接收方已取得 ①发行目录（wheel + `requirements.lock.txt` + `SHA256SUMS` + `SHA256SUMS.sig` + `VERIFY-SIGNATURE.txt` + `RELEASE.json`）；②待验包 zip；③单包锚点 `anchor-0.4.17-<role>.json`；④公钥副本 `trusted-public-key.pub`。这些均可在 `handoff/20261104-第十九轮整改/` 内找到（包在 `package/`）。
> 公钥副本**必须来自包外**，且其 `key_id` 须先从独立渠道核对（第 4 节），再进入本节。

### 第 1 步：核对发行物文件哈希

```powershell
# 在 release/ 目录内执行（UTF-8 读取，避免中文文件名乱码）
Get-Content SHA256SUMS -Encoding UTF8 | ForEach-Object {
  $hash, $name = $_ -split '\s+', 2
  $actual = (Get-FileHash $name -Algorithm SHA256).Hash.ToLower()
  if ($actual -ne $hash) { throw "SHA256 不匹配：$name" }
  "OK $name"
}
```

期望：5 行 `OK <文件名>`，对应 `README-验收.md`、`RELEASE.json`、`VERIFY-SIGNATURE.txt`、`requirements.lock.txt`、`worktime_compliance_agent-0.4.17-py3-none-any.whl`。任一不符即**拒收，不要继续安装**（`release/README-验收.md` §1）。

### 第 2 步：验 `SHA256SUMS.sig` 并核对发行钥 `key_id`

按 `release/VERIFY-SIGNATURE.txt` 内的 PyNaCl 片段执行（该文件给出 `key_id`、`public_key_b64` 与可直接运行的代码）。期望输出：

```text
SHA256SUMS SIGNATURE OK
```

同时核对 `release/RELEASE.json.release_signature.key_id` 是否为：

```text
ed25519:5e797e1842cf49c7043ba238f2a085b08c87d0a49663440f989cdc7df9ee5bb6
```

并自行从 `release-public-key.pub` 反算公钥指纹（应得到同一 `key_id`）：

```powershell
$b64 = (Get-Content release-public-key.pub -Raw).Trim()
$bytes = [Convert]::FromBase64String($b64)
$sha = [System.Security.Cryptography.SHA256]::Create()
$hex = [BitConverter]::ToString($sha.ComputeHash($bytes)).Replace('-','').ToLower()
"ed25519:$hex"
```

期望：`ed25519:5e797e1842cf…5bb6`。

### 第 3 步：从公钥副本反算包签名钥 `key_id`

```powershell
$b64 = (Get-Content trusted-public-key.pub -Raw).Trim()
$bytes = [Convert]::FromBase64String($b64)
$sha = [System.Security.Cryptography.SHA256]::Create()
$hex = [BitConverter]::ToString($sha.ComputeHash($bytes)).Replace('-','').ToLower()
"ed25519:$hex"
```

期望：`ed25519:b07741b2e0bb…9555`。
该值与第 4 节两条独立渠道记录的 `key_id` 逐字一致后，才可认为「公钥副本与记录匹配」。

### 第 4 步：建干净环境（不复用项目 `.venv`）

```powershell
py -3.12 -m venv .venv-clean
.venv-clean\Scripts\python -m pip install --require-hashes -r release\requirements.lock.txt
.venv-clean\Scripts\python -m pip install --no-deps release\worktime_compliance_agent-0.4.17-py3-none-any.whl
```

`--require-hashes` 失败即依赖与锁定清单不一致，不要绕过（`docs/交付与验收SOP.md` §5.2）。

### 第 5 步：字节层核验（推荐一次给全锚点）

```powershell
.venv-clean\Scripts\wca-verify.exe package\engine-only.zip `
  --anchor-file anchor-0.4.17-engine-only.json `
  --public-key trusted-public-key.pub
```

`--anchor-file` 可一次提供 `anchor`/`package_sha256`/`artifacts_digest`/`evidence_digest`（`release/README-验收.md` §3）。

等价的分项参数写法（参数名均出自 `docs/交付与验收SOP.md` §2 与 `docs/签名方案.md` §4）：

```powershell
.venv-clean\Scripts\wca-verify.exe package\engine-only.zip `
  --public-key trusted-public-key.pub `
  --expect-anchor "3,rp-2026.11.gd-pilot-standard.v5,8b3b54a09aa8ede51697b899ddf2d2e738262d6a612b9bee4e34037a6aa8456e,5dc46558152089f1c0be7522c7b1c175b387309d1c316eb8445dd81ada1d5b7d" `
  --expect-package-sha256 9b105901533ee8bca1cfa779948b5fc8f03187dfd65ad91c1d23453d5be94d84 `
  --expect-artifacts-digest 906728867e39c2526de4c62c184cd94b3b06d20c78866050cc457e222d5a94c2 `
  --expect-evidence-digest ed3b3f1b3c1961a22683979750bc12e44a048c9926617ef1a645fdfaa9cddfeb
```

上述四段锚点、包 SHA、`artifacts_digest`、`evidence_digest` 均取自实物 `anchor-0.4.17-engine-only.json`；换其他角色包时替换为对应 `anchor-0.4.17-<role>.json` 的值。

期望关键行（顺序以 `handoff/20261104-第十九轮整改/reports/round19-techcheck.txt` 的原始输出为准）：

```text
MANIFEST CHECKSUM OK
ARTIFACTS OK
VERIFY SCRIPT OK
FINDINGS DIGEST OK (9 fields; source_* not covered by digest)
EVIDENCE DIGEST OK
COUNTS 发现（未签认）… / 已确认结论 …
CHAIN OK
INPUTS COMPLETENESS OK
INPUTS DIGEST OK
SIGNATURE OK / pinned (key matches supplied pin; independent key_id verification not done)
ANCHOR CHECK OK
RESULT OK
```

`RESULT OK` 须同时满足五项门禁：签名 `pinned` + 外部锚点 + 外部 `package_sha256` + 外部 `artifacts_digest` + 外部 `evidence_digest`；缺一为 `RESULT PARTIAL`（exit 2），错值为 `RESULT FAIL`（exit 1）。

### 第 6 步：字段层回放

```powershell
.venv-clean\Scripts\wca.exe replay package\engine-only.zip `
  --anchor-file anchor-0.4.17-engine-only.json `
  --public-key trusted-public-key.pub
```

期望：`工件逐文件：OK`、`发现摘要：一致`、`EVIDENCE DIGEST OK`、三元组逐项 `=`、`发现（未签认）`条数一致、`RESULT OK`，exit 0（`release/README-验收.md` §4）。

### 第 7 步：留痕

接收方侧保存：两条渠道的 `key_id` 记录、`wca-verify` 与 `wca replay` 的**完整原始输出与退出码**、包 SHA-256、`artifacts_digest`、`evidence_digest`、四/五段锚点、验收时间、验收人。只保存结论、不留原始输出，事后无法复核。

### 退出码怎么读

| 退出码 | 标签 | 含义 | 处置 |
| --- | --- | --- | --- |
| 0 | `RESULT OK` | 内容检查 + 签名 pin + 四项外部项全通过 | 当通过（仍不等于来源可信） |
| 1 | `RESULT FAIL` | 有证据的不一致/篡改；schema v3 缺 `inputs_digest` | 当失败，阻断 |
| 2 | `RESULT PARTIAL` | 缺外部项、未 pin，或无签名 v2 包 | 不得当通过 |
| 3 | `RESULT INCOMPARABLE` | 跨 `rule_pack_version` / 跨 evidence schema | 既不当通过，也不当篡改 |

【事实】依据 `handoff/20261104-第十九轮整改/README-验收.md` §三。

## 4. 独立渠道核验 `key_id` 的具体做法

### 4.1 「独立」的判定标准

满足以下至少三条，且**至少一条不由被核验方单方控制**，才算有意义的独立渠道：

1. 不同系统（合同系统 / 工单系统 / 官网 / 纸质纸条）；
2. 不同经手人（交付方密钥保管人之外的第二人）；
3. 不同介质（纸质、系统记录、当面口述+手写）；
4. 不同时间（交付前预登记，而不是交付后补发）。

同一封邮件里的公钥与 `key_id`、同一个人转发两次，**不算两条渠道**。

### 4.2 可用渠道与验证方法

| 渠道 | 记录内容 | 验证方法（接收方侧） | 独立性 | 本周能否落地 |
| --- | --- | --- | --- | --- |
| A 合同/采购订单附件 | 两个 `key_id`、两把公钥 Base64 全文、生效版本、日期 | 从**接收方自己的合同系统**导出附件，抄录 `key_id`；与本机 `.pub` 反算值逐字比对 | 由接收方留存，交付方不能单方改 | 需接收方采购配合；内部可先做模板 |
| B 接收方 IT 工单/变更单 | 两个 `key_id`、公钥 SHA-256、用途 | 从工单系统复制 `key_id`，与 `.pub` 反算值比对；核对工单创建时间早于首次交付 | 与邮件、合同系统不同源 | 需接收方工单系统；内部可用内部工单演练 |
| C 当面互换纸条/视频会议 | 双方各自**手写** `key_id` 并签名/拍照，各持一份 | 会后各自照片中的 64 位十六进制与 `.pub` 反算值逐字比对（建议每 16 位分组抄写，避免 0/O、1/l 混淆） | 不经邮件与文件系统，第三方无法同时替换 | **可以**，无需外部系统 |
| D 官网/企业公示页 HTTPS | 两个 `key_id` 与公钥全文 | 接收方自行浏览器访问、抄录、比对；核对域名与 HTTPS 证书 | 需域名控制权，属交付方一侧，但接收方可独立访问 | **否**：当前是否存在公示页 **【未知，需确认】** |
| E 第三方 CA / 时间戳 / 公证 | 证书或时间戳凭证 | 由第三方验证并出具凭证 | 最强，独立于双方 | **否**：需外部方与预算 |

### 4.3 本周不需要外部方的具体动作（对应决策方案的「本周第一步」）

1. 内部建立一页《密钥登记与交付记录模板》（见附录 A），登记两把 `key_id`、公钥、用途、保管人、备份位置、轮换/吊销责任人。
2. 做一次**内部模拟接收方侧核验演练**：由**非密钥持有人**执行：
   - 从两个内部渠道（交付记录表 + 内部工单/邮件）各取一份 `key_id`；
   - 用第 3 步命令独立从 `trusted-public-key.pub` 反算 `key_id`；
   - 用第 5、6 步命令跑 `wca-verify` 与 `wca replay`；
   - 留存原始输出与退出码，填《交付记录》。
3. 结论只写「内部双渠道核对一致」，**不得写成「接收方已确认来源」**；接收方侧确认必须等接收方实际执行并回签。

## 5. 轮换与旧钥退役

### 5.1 触发条件【建议】

1. 私钥泄露、疑似泄露、介质丢失或被非授权人接触；
2. 主/备保管人变更、离职或权限被收回；
3. 构建参数误用、签名产物 `key_id` 与预期不符（0.4.6 类型事件）；
4. 计划周期到期（周期 **【未知，需确认】**；建议按年或按接收方合同要求）；
5. 加密库/算法/依赖发生重大变更；
6. 接收方或监管明确要求换钥。

### 5.2 轮换步骤【建议；其中工具能力均为事实】

1. **记录触发**：填写轮换事件表（附录 A.3），写明原因、涉及钥、拟生效版本。
2. **生成新钥**：`keygen --out <新路径> --public-out <新公钥路径>`；**不覆盖旧钥**（已存在且无 `--force` 时工具拒绝覆盖）。
3. **更新守卫**：发行钥轮换须改 `scripts/build_release.py` 的 `EXPECTED_RELEASE_KEY_ID` 并以 `--allow-key-rotation <理由>` 显式放行；不得直接改值不留记录。
4. **新旧并存**：保留旧 `.pub`；`--public-key` 可**重复传入**新旧公钥，验签时新旧都能匹配。新包只用新钥，旧包继续用旧钥。
5. **交付登记**：交付记录同时写「本次包 `key_id`」与「历史包 `key_id` 清单」；接收方侧应同时 pin 新旧公钥。
6. **并存期长度**：**【未知，需确认】**；建议至少覆盖所有在用旧包的生命周期或合同期。
7. **通知**：通过第 4 节的两条以上渠道发布新 `key_id`，并说明旧钥停用时间。

### 5.3 旧包回放约束【事实】

- 旧包**必须配同版本 wheel**；用新 wheel 验旧包会先 `PRODUCER FAIL`，随后签名检查早退为 `SIGNATURE NOT CHECKED`——**这不是篡改，也不是验签失败**（`KEY-NOTE.txt` 第四节、`docs/签名方案.md` §5）。
- 旧 wheel / 旧包 / 旧锁的实际位置：`release/old-wheels/` 13 个 wheel、`release/old-packages/` 48 个包；0.4.10/0.4.11 的依赖锁只在 `release/old-packages/`，0.4.13–0.4.16 的锁在 `release/old-wheels/`（`KEY-NOTE.txt` 第四节、`README-验收.md` §九）。
- 0.4.4–0.4.8 旧 wheel 不做 `comparability_scope` 判定，其 `RESULT OK` 仅表示旧口径通过，不表示可比性已核验（`KEY-NOTE.txt`）。
- 旧钥退役后，旧包仍可用旧公钥验，但交付记录必须标注「该包由已停用钥签发」。

### 5.4 旧钥退役步骤【建议】

1. 旧公钥**不删除、不覆盖**，移入 `retired/` 或按版本命名保存；登记 `retired_at`、停用原因、最后使用版本。
2. 发布《停用声明》：旧 `key_id`、新 `key_id`、生效时间、旧包验签指引（用哪个 wheel/哪个公钥）。
3. **禁止**重签旧包、改写旧审计链、重置 genesis 或批量改写历史 finding；旧包与旧锚点按原样保留。
4. 旧锚点按版本命名保存，不互相覆盖（`docs/签名方案.md` §4.1）。

### 5.5 历史锚点怎么标【事实 + 建议】

- 命名：`anchor-<version>-<role>.json`；文件名版本、内容版本、目标包 `producer.version` 必须三方一致（0.4.17 的锚点即按此生成）。
- 每个单包锚点写 `comparability_scope`（`rule_pack_version` + `schema`）；跨版本/跨 schema 摘要差异只报 `INCOMPARABLE`（exit 3），不得当篡改。
- `file` 字段要么是可解析相对路径，要么显式标注「仅记录、不可解析」（0.4.12 的锚点即属后者，因包未随本目录交付）。
- 历史锚点不得当作新包锚点使用；新版本另存新文件，不覆盖旧文件。

## 6. 这一步做完，「pinned」能提升到什么程度

| 层级 | 本周动作完成后 | 仍缺什么 / 需要谁 |
| --- | --- | --- |
| `pinned`（与供给副本匹配） | 可达到并**可被接收方独立复核**：接收方用自己算出的 `.pub` 指纹 + 两条渠道的 `key_id` 记录比对一致后，工具输出 `SIGNATURE OK / pinned` | 工具仍写 `independent key_id verification not done`（工具无法知道你做过人工核对）；这句话不会因本流程改变，也不应改 |
| 「公钥副本与记录匹配」的人证 | 可从「交付方自述」提升为「接收方侧有两条独立记录 + 自算指纹 + 原始输出留痕」 | 至少一条渠道须由接收方/第三方留存；仅交付方两处记录仍属同一控制方 |
| 来源可信（公钥属于某个具名主体） | **不能**仅靠本流程达成 | 需外部方配合：合同签署主体核验、企业 PKI/CA、官网域名+HTTPS 公示、公证或第三方时间戳 |
| 防「公钥 + 包外锚点同时被替换」 | 风险下降（两条渠道提高替换成本） | 彻底解决需接收方或第三方独立保存锚点与公钥；交付方单方动作无法消除 |
| 私钥治理（双人、备份、权限、泄露预案） | 私钥文件与 7 个父目录 ACL 已于 2026-11-09 收紧；构建工作副本已只读标记；离线备份方案已设计（D.9）但**未落地**；双人保管、使用登记、停用声明模板仍待实施 | HSM/KMS、quorum、集中审计、不可否认时间戳需采购/外部服务 |
| 旧包可持续回放 | 已具备条件（旧 wheel/旧包/旧锁齐全，按版本配对） | 接收方侧需按 `OLD-WHEELS.md` 自行建对应版本环境 |
| 第三方不可否认（时间戳） | **未达成** | 需第三方 TSA 或公证，属外部方 |

一句话：本周动作能把「pinned = 与交付方给的副本匹配」提升为「**接收方侧已用两条独立渠道核对过该副本的 key_id，并留有原始验算输出**」；但**不能**把 `pinned` 变成「来源可信」，后者必须由外部方参与。

### D.10 冻结交付物收尾核对（219 文件 / 0 差异）

本次对 `var/` 的改动只涉及 ACL、只读属性与一份说明文件，未改 `handoff/` 下任何文件。复核方法：读取 `handoff/20261104-第十九轮整改/交付清单.txt` 中每行 `bytes=… sha256=…`，逐文件重算比对，并检查有无未登记文件。

```powershell
$root = 'handoff\20261104-第十九轮整改'
$rootFull = (Resolve-Path $root).Path
$list = Get-Content "$root\交付清单.txt" -Encoding UTF8
$entries = @()
foreach ($line in $list) {
  if ($line -match '^\s{2}(.+?)\s{2}bytes=(\d+)\s{2}sha256=([0-9a-f]{64})$') {
    $entries += [pscustomobject]@{
      Name = $matches[1].Trim(); Bytes = [int64]$matches[2]; Hash = $matches[3]
    }
  }
}
$bad = @()
foreach ($e in $entries) {
  $p = Join-Path $rootFull ($e.Name.Replace('/', '\'))
  if (-not (Test-Path -LiteralPath $p)) { $bad += "MISSING $($e.Name)"; continue }
  $h = (Get-FileHash -LiteralPath $p -Algorithm SHA256).Hash.ToLower()
  if ($h -ne $e.Hash) { $bad += "HASH $($e.Name)" }
  if ((Get-Item -LiteralPath $p).Length -ne $e.Bytes) { $bad += "SIZE $($e.Name)" }
}
$actual = Get-ChildItem -LiteralPath $rootFull -Recurse -File |
  ForEach-Object { $_.FullName.Substring($rootFull.Length + 1).Replace('\', '/') }
"listed_entries=$($entries.Count)"
"bad=$($bad.Count)"
"actual_files=$($actual.Count)"
"extras=$(@($actual | Where-Object { $_ -ne '交付清单.txt' -and $_ -notin @($entries.Name) }).Count)"
```

实际输出：

```text
listed_entries=218
bad=0
actual_files=219
extras=0
```

解释：`交付清单.txt` 按约定不登记自身，故登记条目为 218；加上清单自身共 **219 个文件**。`bad=0` 表示 218 个登记文件的字节数与 SHA-256 全部一致，`extras=0` 表示没有未登记文件。**219 文件 0 差异**，密钥治理未波及已冻结交付物。
