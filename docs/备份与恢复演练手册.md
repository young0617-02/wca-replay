# 备份与恢复演练手册（PostgreSQL 18）

> 目的：回答两个验收问题——“我的审计日志被改过吗”“数据库坏了怎么恢复”。
> 本手册给出可执行命令与恢复后**必须**核对的项；实测记录只写实际跑过的结果，
> 没跑过的（当前 PG 环境）明确标为待办，不用 SQLite 结果冒充 PostgreSQL 结论。

## 1. 适用范围与前置

| 项 | 要求 |
|---|---|
| 数据库 | PostgreSQL 18，活动库 `wca_worktime`；连接串只在本地 `.env`/进程环境 |
| 工具 | `pg_dump`、`pg_restore`、`psql`、`createdb`（Docker 内或本机安装均可） |
| 代码 | 仓库根目录执行；Python 3.12 + `uv` |
| 命名 | **一项目一库**；恢复库名重名时自动换名（例如追加 `_2`、时间戳），**不得覆盖活动库** |
| 窗口 | 恢复演练只在新库进行；对活动库做恢复必须走维护窗口与变更审批 |

先在仓库根目录确认目标：

```powershell
uv run python -m src.cli db-target --show
```

输出里的库名必须是你要操作的那一个；`--show` 只读，不改 identity。

## 2. 备份（活动库 → 文件）

```powershell
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
New-Item -ItemType Directory -Force var/backup | Out-Null
$url = $env:WCA_DATABASE_URL          # 例：postgresql://root:<口令>@127.0.0.1:5927/wca_worktime
pg_dump "$url" -Fc -f "var/backup/wca_worktime-$stamp.dump"
pg_restore --list "var/backup/wca_worktime-$stamp.dump" > "var/backup/wca_worktime-$stamp.list"
Get-FileHash "var/backup/wca_worktime-$stamp.dump" -Algorithm SHA256
```

Linux/macOS 等价命令：

```bash
pg_dump "$WCA_DATABASE_URL" -Fc -f "var/backup/wca_worktime-$stamp.dump"
pg_restore --list "var/backup/wca_worktime-$stamp.dump" > "var/backup/wca_worktime-$stamp.list"
sha256sum "var/backup/wca_worktime-$stamp.dump"
```

**备份时同时记录**（写进变更单/值班记录，后面恢复要对照）：

```powershell
uv run python -m src.cli audit-scan --json > "var/backup/wca_worktime-$stamp.audit.json"
```

记下 `head_seq`、`head_hash`、`total_rows` 三项。它们就是恢复后的外部锚点。

## 3. 恢复到新库（不动活动库）

```powershell
$restoreDb = "wca_restore_$stamp"      # 重名时改成 wca_restore_${stamp}_2
psql "$env:WCA_DATABASE_URL" -c "CREATE DATABASE \"$restoreDb\""
$restoreUrl = $env:WCA_DATABASE_URL -replace '/[^/]+$', "/$restoreDb"
pg_restore --dbname "$restoreUrl" "var/backup/wca_worktime-$stamp.dump"
```

若 `CREATE DATABASE` 报“已存在”，**不要删原库**，换名重建：

```powershell
$restoreDb = "wca_restore_${stamp}_2"
psql "$env:WCA_DATABASE_URL" -c "CREATE DATABASE \"$restoreDb\""
```

恢复后先接入恢复库（不改活动库的 identity 文件）：

```powershell
$env:WCA_DATABASE_URL = $restoreUrl
$env:WCA_DB_IDENTITY_PATH = "var/restore-drill/db_target_$stamp.json"
uv run python -m src.cli db-target --show
```

> 只改当前进程的环境变量；不要改写仓库 `.env`。演练结束关闭该终端即可。

## 4. 恢复后必须做的校验（按顺序）

| # | 校验项 | 命令/判定 | 不通过意味着 |
|---|---|---|---|
| 1 | 恢复库身份 | `wca db-target --show` 显示的是恢复库 | 接错库，后续数字全部作废 |
| 2 | 关键表行数与备份前一致 | 对照备份前记录：`run`、`finding`、`audit_event`、`evidence_package`、`employee`、`punch`、`approval_doc*` | 备份不完整或恢复中断 |
| 3 | 审计链全量自检（只读） | `wca audit-scan --expect-head <备份前 head_hash> --expect-max-seq <备份前 head_seq>` → exit 0、`结论：完整` | 链被改写/截断，或恢复不完整 |
| 4 | 链头与备份前一致 | `head_seq`、`head_hash` 与第 2 节记录逐字相同 | 尾部事件丢失或恢复到了错误时点 |
| 5 | 规则包纪元一致 | `rule_pack_epoch` 行数与 `segment_start_seq`/`prev_head_hash` 与备份前记录一致 | 纪元表未恢复或被改写 |
| 6 | 抽一个 run 重导出 | `wca export --run <run_id>`，三元组与备份前记录一致 | 输入或结论数据缺失/被改 |
| 7 | 用包回放对照 | `wca replay <新导出的包.zip>` → `RESULT OK` 或说明缺哪项外部锚点 | 引擎/规则包与包不一致，或输入被改 |
| 8 | 已交付包签名/锚点 | 对涉及交付的包跑 `wca-verify --public-key ... --expect-anchor ...` | 包字节或签名链有问题（与恢复无关，但必须一起核） |

第 3 步是本轮新增的只读命令，**只执行 SELECT，不写库**。示例输出：

```text
审计链自检（只读，不写库）：postgres:127.0.0.1:5927/wca_worktime
  段 legacy（legacy，已封闭）：seq 1–19，19 条，OK
  段 epoch-...-v5-19（...v5，已封闭）：seq 20–1180，1161 条，OK
  段 epoch-...-v6-1181（...v6，开放）：seq 1182–1300，119 条，OK
合计 1300 条；链头 seq=1300 hash=...
结论：完整
```

若断链，输出会直接给出“从第几条起不对”：

```text
结论：从 seq=57 起不对（共 2 处问题）
  · [seq_gap] 段 ... seq 57：seq 跳号：期望 57，实际 58
  · [prev_hash_break] 段 ... seq 58：prev_hash 与前一条 entry_hash 不衔接
```

`audit-scan` 与 `verify` 的分工：

| 能力 | `wca verify`（既有） | `wca audit-scan`（本轮新增） |
|---|---|---|
| prev_hash 断裂（中间删除/改写） | 是 | 是 |
| entry_hash 内容重算 | 是 | 是 |
| 只验当前配置的段 | 是（legacy + 当前规则包段） | 否，**扫描全部纪元段** |
| seq 跳号/缺号 | 否 | 是 |
| 重复 seq | 否（主键阻止，未报告） | 是（显式查询并报告） |
| 已封闭段链头截断 | 否 | 是（用 `rule_pack_epoch` 锚点） |
| 开放段尾部截断 | 否 | 需 `--expect-head`/`--expect-max-seq` |
| 写库 | 否 | 否 |

## 5. 失败时怎么回滚

**原则：恢复失败只影响恢复库，活动库一字节不动。**

1. 记录失败点：`audit-scan --json` 输出、`pg_restore` 退出码与 stderr、行数对照表。
2. 关闭恢复库连接，删除恢复库（确认库名不是 `wca_worktime`）：

   ```powershell
   psql "$env:WCA_DATABASE_URL" -c "DROP DATABASE IF EXISTS \"$restoreDb\""
   ```

3. 保留 dump 文件与 `.list`、SHA-256、备份前 `audit-scan --json`，不要覆盖。
4. 换一份备份重试；连续两次失败则停止演练，按值班流程升级。
5. **只有在恢复库完整通过第 4 节全部校验后**，才允许在维护窗口对活动库执行恢复；
   活动库恢复前必须再做一次全库备份，并用 `pg_restore --clean --if-exists` 明确写出目标库。
6. 如果活动库已经恢复但校验失败：立即停止写入，用恢复前的全库备份回退；不要“修补”审计链。

### 6.2 SQLite：仅流程演示（**不证明 PostgreSQL 恢复行为**）

为了验证“备份→恢复新库→链自检→同 run 回放对照”这条流程本身，用临时 SQLite 库
（`var/restore-drill-20261112/`）跑了一遍。数据与命令见同目录 `drill_sqlite.py`、
`drill-result.json`。

| 指标 | 实测值 |
|---|---|
| 备份方式 | SQLite `Connection.backup` 到新文件（对应 PG 的 `pg_dump -Fc`） |
| 恢复库大小 | 2,760,704 字节 |
| 备份耗时 | 45.2 ms |
| 行数（源 → 恢复） | `run` 1→1、`finding` 115→115、`audit_event` 11→11、`evidence_package` 1→1、`employee` 12→12、`punch` 3896→3896 |
| 链头（源 = 恢复） | `seq=11`，`4b515ddbff177b8b47f36ab778d21ae5f0201beee96a28acd3797be886014646` |
| 恢复库链自检 | `ok=true`，0 处问题（用源库链头作外部锚点） |
| 同 run 导出耗时 | 源 410.2 ms；恢复库 458.9 ms |
| 三元组 | 源与恢复库逐项相同（`conclusion_digest=a4e31ef3…`、`input_fingerprint=3680c4d5…`、v6） |
| 包回放 | `replay_ok=true`，2242.9 ms；`RESULT PARTIAL` 仅因未提供外部公钥/锚点/包 SHA-256 等包外记录 |

**这些数字只能说明流程可执行，不能说明 `pg_dump`/`pg_restore` 在同版本 PG 上的耗时、
锁行为或大对象/序列恢复是否正确。**
