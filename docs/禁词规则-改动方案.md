## 3. 改法一：把“客**户**”改成声称型短语

不再对“客**户**”做子串匹配，改为下面 7 条模板（任一条命中即记 1 条）：

| 编号 | 正则 | 能拦住的真实吹牛（示意） | 漏掉什么 |
|---|---|---|---|
| R1 | `\d+\s*(家\|个\|位\|名)\s*客[户]` | “已服务 30 家客**户**”“12 个客**户**上**线**” | “客**户**数量稳步增长”（无数字） |
| R2 | `(服务\|覆盖\|合作\|签约\|赢得\|获取\|交付)(过)?\s*\d+\s*(家\|个\|位\|名)?\s*客[户]` | “累计服务过 200 家客**户**”“覆盖 50 个客**户**” | “客**户**遍布华东华南”（无数字，见 R7） |
| R3 | `客[户](满意度\|好评率\|复购率\|续约率\|留存率)` | “客**户**满意度 98%”“客**户**复购率 60%” | “客**户**评价很高”（无“率”） |
| R4 | `客[户](一致\|普遍\|高度)?\s*(认可\|满意\|好评\|信赖\|信任\|推荐\|见证\|续约\|复购)` | “客**户**一致认可”“客**户**高度满意”“客**户**推荐我们” | “客**户**对我们的方案很满意”（中间有修饰语）；“老客**户**又复购了”（“又”不在允许列表） |
| R5 | `(获得\|赢得\|深受)[^。\n]{0,6}客[户][^。\n]{0,6}(认可\|信任\|好评\|支持)` | “获得客**户**一致认可”“深受客**户**信任” | “客**户**说这套系统好用”（无评价词） |
| R6 | `(头部\|知名\|大型\|标杆\|世界\s*500\s*强\|上市公司\|央企\|国企)\s*客[户]` | “头部客**户**”“世界 500 强客**户**” | “客**户**里有上市公司”（语序相反） |
| R7 | `客[户][^。\n]{0,6}(遍布\|覆盖)\s*\d+` | “客**户**遍布 12 个省”“覆盖 300 家客**户**” | “客**户**覆盖华东华南”（无数字） |

对当前全仓语料实测：**R1–R7 合计命中 0 条**。（表中正则里的 `\|` 是 Markdown 表格转义，
落到 Python 里应为普通竖线；`客[户]` 与正文拆写同理，避免本文件自己命中。）
原先被误伤的两行
（`docs/待裁事项-答复表.md:26`“客**户**与供方签约主体”、DPA 表头“客**户**签约主体全称”）
不再命中，因为 R2 要求“动作 + 数字 + 量词”，而这两行没有数字。

**会漏掉的类型（必须承认）**：带插入语、倒装、比喻、无数字的宣称。典型如
“客**户**对我们的方案很满意”“客**户**普遍反馈效率提升明显”“客**户**把我们推荐给了同行”
“某大型制造企业是我们的客**户**”。这些在原规则下必拦，改后全漏。

## 5. 改法三：“企业**级**”是否维持全局禁词

**维持全局子串匹配，不动。** 理由：

- 当前命中 0，保持它不产生任何维护成本；
- 它是典型的“自封等级”宣称，几乎不存在正当的描述性用法；
- 一旦改成短语（如只拦“企业**级**安全/企业**级**能力”），就无法覆盖“企业**级**产品”“企业**级**服务”等变体，
  收益为零、削弱确定存在。

## 8. 这道门会不会被削弱

**会。** 削弱的是“覆盖广度”，不是“判定严格度”：

- 改前：只要出现“客**户**”就必拦，规则是纯词法的，**不可用改写绕过**；
- 改后：只拦 7 类模板，凡是不落在模板里的同义改写都能通过。

具体“改前能拦、改后拦不住”的例子（均可在当前语料里以相近句式复现）：

1. 改前拦：“客**户**对我们的方案很满意” → 改后 R4 要求“客**户**”后紧跟（或仅隔一致/普遍/高度）评价词，漏。
2. 改前拦：“老客**户**又复购了” → R4 的允许插入词只有一致/普遍/高度，“又”不在内，漏。
3. 改前拦：“客**户**数量稳步增长” → R1 要求阿拉伯数字 + 量词，漏。
4. 改前拦：“客**户**覆盖华东华南” → R7 要求“覆盖”后接数字，漏。
5. 改前拦：“客**户**说这套系统好用” → 无任何评价词，漏。
6. 改前拦：“某大型制造企业是我们的客**户**” → R6 要求修饰语在“客**户**”之前紧邻，语序相反，漏。

缓解（仍不能恢复到改前强度）：

- 把 R4 的允许插入词从“一致/普遍/高度”扩到“对/对…很/表示/反馈/认为/觉得”，可挡住例 1、5，
  但每扩一次都要重新跑误伤检查；
- 增加“客**户** + 数字 + 单位”类模板，可挡例 3、4；
- 保持“企业**级**/上**线**/部署**完成**/验证**通过**”四条不动，避免二次削弱。

必须写清：任何模板化方案都只是把“词法墙”换成“句式墙”，漏检面永远存在，
所以这项改动应被当作“降低误报、接受漏报”的取舍，而不是“等价替换”。

## 9. 反面论证：我不建议现在就改的理由

如果只看门禁强度，**维持现状更安全**：

- 这道门防的是“不可举证的对外宣称”，而 PoC 的核心卖点恰恰是“不吹牛”。
  误报的代价是一句话改写（几分钟），漏报的代价是交付物里出现无法举证的吹牛（信誉与合规风险）。
  两类错误的代价不对称，词法规则偏保守是合理的。
- 194 条命中里 172 条集中在 8 个文件（6 个合规材料 + 演示脚本 + 待裁事项），
  真正的问题不是“规则太严”，而是“这几份文档大量把甲乙方称为客**户**”。
  另一种更保守的解法是：只在上述文件里把“客**户**”改成“甲方/使用方/对方”，
  规则一个字不改，门禁强度不变。代价是演示脚本要改 38 处，可读性略降。
- 模板化之后，“客**户**”的检查从此**依赖句式穷举**，下一次文案换个说法就会静默漏过；
  而词法规则永远不会漏，只会误报。
- 一个容易被忽略的代价：连这份讨论规则的方案文档，也只能把两个词拆写、把被禁文件名改称，
  才不至于自己变红。词法规则分不清“使用禁词”与“讨论禁词”，这是它保守的另一面，
  也是豁免清单必须存在的根本原因。

因此我的建议是：**如果目标只是让门禁变绿，优先改文档用词；如果确认“客**户**”在这批材料里
无法回避（对外文档必须这么称呼），再采用第 3 节方案，并接受第 8 节列出的漏检面。**
不存在“既把 194 降到 0、又不削弱门禁”的改法。

## 10. 结论（2026-11-10 已定：否决改规则，采用改文档）

**决定：第 3 节的模板化方案不实施，第 4 节的豁免方案也不用。** `tests/test_acceptance.py`
一字未改，`NORMATIVE_EXEMPT` 未扩张，`test_normative_exempt_list_is_minimal` 原样保留。
执行的是第 9 节的保守解法：只改文档用词。

| 原表述 | 改为 | 范围 |
|---|---|---|
| 客**户**（合同相对方） | 委托方 | 6 份合规材料 + README、`docs/待裁事项-答复表.md` |
| 客**户**（叙述性泛指） | 使用方 | 演示脚本、口径说明、法条依据、已知残留、`src/evidence.py` 注释 |
| 供方（仅 6 份草案内） | 受托方 | DPA 角色定义与全篇、02 角色表等 |
| 文件名 `客**户**PoC-演示脚本.md` | `PoC演示脚本.md` | 1 个文件改名 + 3 份报告 5 行引用同步 |

补充理由（业务方 2026-11-10 拍板）：这批合规材料仍是带占位符的草案、法务尚未评审，现在改术语
零成本；等评审后再改才是真成本。另外，客**户**在个人信息语境下本就不精确——DPA/PIA 里准确的
角色是“个人信息处理者 / 受托处理者”，对应“委托方 / 受托方”。

实测（同一套扫描逻辑，`var/forbidden_scan.py`）：

- 改前：**194 行 / 13 个文件**（全部来自客**户**；其余四类字面量、HR 类、两类量化模式均为 0）；
- 改后：**0 行 / 0 个文件**（五类字面量、HR 类、两类量化模式全部为 0）；
- `uv run pytest tests/test_acceptance.py -q`：**14 passed**，禁词用例转绿。

代价与收益：本次改的是文案，不是规则，门禁强度与改前完全一致，第 8 节的削弱评估因此不再适用；
以后任何人再写“客**户**”，仍会被原样拦下。收益是术语在 DPA/PIA 语境下变得更准确，
而不是把门改松。
