## 1. 一句话结论

当前能证明“包内自洽，且同一批输入在同版本代码下可复算出同一三元组”；把**四元组**（`schema_version` + 三元组）、包 SHA-256 与 `artifacts_digest` 另存在包外时，还能发现整包被替换、工件被改或“伪装成 v1”的降级。0.3.0 起**信任依据是发行 wheel 的 `wca-verify`**：它自己重算 manifest checksum、审计链、输入摘要、工件逐文件哈希、`findings.csv` 反算 `conclusion_digest` 与签名，**不执行**包内 `verify.py`。配置 Ed25519 私钥后导出 v3 签名包；签名载荷包含 `inputs_digest`、`artifacts_digest` 与 `verify_script_sha256`。复核方用**包外固定公钥**（`--public-key`）验签时，只能证明“包与供给公钥匹配”；**不等于公钥属于某个已核验主体**。来源身份必须由双方通过独立渠道核验 `key_id` 并在交付记录中声明，不属于软件验收能力。签名仍不证明结论正确（仍需 `wca replay`），也不能防私钥持有人作恶。

- **能防**：单条审计事件被改（链重算）、输入文件被替换（v3 `inputs_digest`）、整批换 `inputs/` 并同步改 `inputs/manifest.json`（v3 `INPUTS FAIL`）、改 findings/quality/input_files/responsibility/not_covered/未覆盖清单/verify.py（工件哈希或脚本哈希）、同步重算工件哈希并重签但改 findings 语义（`FINDINGS DIGEST FAIL`）、在包根或 `inputs/` 加未声明文件（`EXTRA FILE FAIL`）、manifest 字段被改而未同步校验和、manifest 任一字段被改后重算 checksum（签名覆盖）、包内 schema/三元组与包外锚点不一致（需显式传锚点）、换签名者（需外部 pin）。
- **不能防**：能取得签名私钥者签任意包；包外 pin 公钥/锚点/包 SHA 被同时替换；不传 `--expect-anchor` 时 `wca-verify`/`wca replay` 只输出 `RESULT PARTIAL`（exit 2），不能当完整验收；`inputs_digest`/工件哈希不证明输入能复算出签名中的结论摘要（仍需 `wca replay`）；未配置私钥时导出仍是 v2 无签名包；包内 `verify.py` 只是便利脚本，不是信任依据。

1. **H-01 残余边界（Ed25519 已落地）**

   交付事件登记入口现为 `record_delivery_event()` / `--record-delivery-as`；旧别名 `sign_package()` / `--sign-as` 保留。它只向审计链追加 `evidence.sign` 事件，**不是密码学签名**，不要和 v3 `manifest.signature` 混为一谈。

   **已证明**：配置私钥后导出的 v3 包，manifest 关键字段（schema/三元组/`inputs_digest`/`manifest_checksum`，含 `conclusions_sha256`）与重算链头由私钥签过；改 manifest 任一字段并重算 checksum、换 `inputs/` 文件并同步改 `inputs/manifest.json`、只改登记表、增删输入文件、改结论 CSV、v3 缺签名/缺输入摘要都会 FAIL；用包外固定公钥 pin 时可识别换签名者。

3. **旧 schema 兼容面：v1 允许缺校验和**  
   `verify.py` 与 `replay` 对 `wca-evidence-package-v1` 缺 `manifest_checksum` 只打印 `MANIFEST CHECKSUM MISSING` 并继续；把 v2 包改成 v1 并删校验和，manifest 完整性检查即被跳过。当前已实现 `--expect-anchor` / `WCA_EXPECT_ANCHOR` 四元组：若包外记录 `schema_version=2`，伪装 v1 会被 `ANCHOR FAIL` 拦下；**但不传四元组时仍走旧包兼容路径**。

4. **`raw_file.row_count` 语义**  
   CSV 通道 `import_csv_file` 登记的是 `len(header)`（表头列数），程序化 `import_rows` 登记的是 `len(seq)`（行数）；该值进入 `input_fingerprint` 的 `rows` 字段，且 `input_files.csv` 的 `row_count` 会误导读者。同一批数据换通道导入可能得到不同指纹。  
   **闭合需要**：统一成数据行数并接受指纹断代（升版本、重跑全套证据）；或拆成 `header_columns` / `row_count` 两个字段并改文档/测试。该取舍已记在 `docs/待确认清单.md` 第 R-8 项，需先裁定。

5. **目录包资源上限已补，但外部解压仍不受控**

   **剩余风险**：外部解压器/用户手工解压可先耗尽磁盘；目录包根目录本身若是指向别处的链接，调用方需自行确认来源；不可信包默认只接受 zip 的交付规则仍未强制。

## 4. 举证包可信度分层（由低到高）

| 层级 | 形态 | 攻击者要骗过需做到什么 | 靠什么发现 | 现状 |
|---|---|---|---|---|
| 1 | 无校验和旧包（schema v1） | 改写 manifest/链/输入并重算链；不需要密钥 | 包外四元组或独立重放；无锚点时 `RESULT OK` 也可能出现 | 仅作 legacy 兼容 |
| 2 | 有自校验和（schema v2 `manifest_checksum`） | 改字段后重算 `manifest_checksum`、链和输入哈希 | 包外四元组；否则只能发现“忘记重算校验和”的低级错误 | 当前默认 |
| 3 | 自校验和 + 包外四元组 | 同时篡改包与包外记录，或让接收方使用错误锚点 | `--expect-anchor` 含 `schema_version`，不符即 `ANCHOR FAIL`；可拦“伪装 v1” | 已支持，但非强制 |
| 4 | Ed25519 签名包（schema v3） | 取得签名私钥，或替换包外 pin 公钥 | 验签失败、`key_id`/公钥指纹不符、`inputs_digest` 不符；未 pin 时仅证明包内自洽 | **已实现**；由 `--signing-key` / `WCA_SIGNING_KEY_*` 启用 |

> 层级 3 保护 schema 版本与三元组；manifest 的 counts、scope、inputs 元数据仍可能被改。层级 4 把“包与某把公钥匹配”变成密码学可验证：**必须用包外固定公钥 pin**，包内自带公钥只能证明“包内自洽”；公钥是否属于某个已核验主体，仍要独立渠道核验 key_id。

## 5. 交付验收清单

| 命令 | 证明什么 | 单独跑的盲区 |
|---|---|---|
| `wca-verify`（发行 wheel） | manifest 自校验和、工件逐文件哈希/`artifacts_digest`/包内 `verify.py` 哈希、findings 反算 `conclusion_digest`、审计链、输入逐文件哈希、`inputs_digest`、签名（`pinned`/`package self-check`）、包内 schema/三元组与包外锚点/包 SHA/工件摘要一致 | 不重跑引擎，不能证明“这些结论是这批输入算出来的”；`inputs_digest` 只证明输入字节与签名一致 |
| `wca replay` | 重导输入、重跑引擎，得到实算三元组与**发现（未签认）**条数，并与包内三元组比对；同样校验工件绑定、`ARTIFACT` 与签名 | 不覆盖包外锚点与包体完整性；不重建人工确认 |
| 包内 `verify.py` | 便利脚本：manifest 自校验和、链、输入摘要、结论集哈希、签名 | **不是信任依据**；不校验工件绑定/findings 反算摘要；不能替代上两条 |

```powershell
# 1) 用发行 wheel 的 wca-verify（不执行包内代码）
wca-verify <包>.zip --public-key <包外固定公钥> --expect-anchor "<四/五段>" `
  --expect-package-sha256 <包SHA256> --expect-artifacts-digest <artifacts_digest> `
  --expect-evidence-digest <evidence_digest> --require-signature
# 期望：MANIFEST CHECKSUM OK / ARTIFACTS OK / VERIFY SCRIPT OK / FINDINGS DIGEST OK /
#       COUNTS 发现（未签认）... / 已确认结论 ... / CHAIN OK / INPUTS COMPLETENESS OK /
#       INPUTS DIGEST OK / SIGNATURE OK / pinned / ANCHOR CHECK OK / EVIDENCE DIGEST OK /
#       RESULT OK，rc=0

# 2) 用同一包外锚点重放（会创建临时库，不写活动库）
wca replay <包>.zip --public-key <包外固定公钥> --expect-anchor "<四/五段>" `
  --expect-package-sha256 <包SHA256> --expect-artifacts-digest <artifacts_digest> `
  --expect-evidence-digest <evidence_digest> --require-signature
# 期望：工件逐文件 OK、发现摘要一致、三元组逐项一致、发现（未签认）条数一致、
#       EVIDENCE DIGEST OK、RESULT OK，rc=0
```

- **不传 `--expect-anchor`**：`wca-verify`/`wca replay` 输出 `ANCHOR NOT CHECKED` + `RESULT PARTIAL`（exit 2），不是完整验收；`--expect-triple` 只是 legacy 比对，不给 `RESULT OK`。
- **签名包必须带 `--public-key`**：包内公钥只能打印 `SIGNATURE OK (package self-check; NOT source trust)`；只有包外固定公钥 pin 才打印 `SIGNATURE OK / pinned`。交付验收建议同时加 `--require-signature`，强制旧 v1/v2 无签名包失败。
- **`wca-verify` 覆盖输入摘要与工件**：`INPUTS DIGEST OK` / `INPUTS SIGNED OK` 表示输入摘要与签名一致；`INPUTS FAIL` 表示换 CSV、改 `inputs/manifest.json` 或增删输入文件；`ARTIFACT FAIL`/`VERIFY SCRIPT FAIL`/`EXTRA FILE FAIL` 表示工件被改、包内脚本被换或夹带文件。但结论是否正确仍必须 `wca replay`。
- **裁剪包必须记五段锚点**：`schema_version,rule_pack_version,input_fingerprint,conclusion_digest,projection_fingerprint`；四段旧调用不变，五段不匹配会 `ANCHOR FAIL`；包内无投影字段却传五段会失败关闭。交接步骤见 `docs/交付与验收SOP.md`。
- **包外锚点记录位置**：随交付邮件正文/附件清单记录，并写入工单或变更单的固定字段；至少两处不同系统，最好由接收方或第三方保存。普通包记四元组；裁剪包记五段（末尾 `projection_fingerprint`）。建议一起记录 `run_id`、包文件 SHA-256、`artifacts_digest`、交付时间、验收人、签名 `key_id`。
- **不要**写进包内 README/manifest 或文件名；**不要**用 `manifest_checksum` / `manifest_sha256` 代替包外锚点。`python -m src.cli verify` 是库内审计链自检，不等价于 `wca-verify` 或包内 `verify.py`。
- `manifest_checksum` 与 `manifest_sha256` 不是同一个值：前者是 manifest 内自校验和（文件内，v3 被签名覆盖），后者是 manifest 文件字节哈希（返回值/数据库列），两者都不是签名本身。

## 7. 已决策与待决策项

**签名算法：已选 Ed25519（2026-11-03，见 `docs/签名方案.md`）**

选 `pynacl==1.6.2`：复核方只拿公钥验签，私钥留在导出方/受限目录；比 HMAC 少一个“复核方持私钥也能伪造”的结构性问题。代价是包内 `verify.py` 验签需要 PyNaCl（`verify-requirements.txt` 固定版本，缺失时失败关闭），且私钥生命周期/备份/轮换/吊销仍需运维落地。当前取舍：配置私钥才导出 v3，未配置保持 v2；旧包不强制签名，交付验收用 `--require-signature` + 包外 pin 收紧。

**数据最小化取舍**  
按 run 裁剪输入、字段白名单、金额单独受限、问答按 run 脱敏，能降低隐私/商业保密暴露和包体积；代价是 `input_fingerprint` 与包内哈希会变、旧包不可直接比较，且 `QUAL-02` 这类依赖全库 `ingest_issue` 的结论可能需要保留全局文件，否则 replay 可能对不上。保留全量输入则举证最完整、重放最省事，但外部接收方会看到与本次结论无关的员工、工资基数和跨 run 问答元数据。需要先定“默认发 scoped 还是 full”，再决定是否升 schema 与重跑证据。

## 签名密钥丢失事件（0.4.4 → 0.4.5）

- **性质**：不是计划内轮换，是构建脚本密钥生命周期缺陷导致的私钥丢失与重新生成。
- **证据**：
  - 0.4.4 包 `key_id=ed25519:ec2081…08d6`，公钥随 `handoff/20261104-第六轮整改/trusted-public-key.pub` 保留；
  - 工作区内已找不到与 `ec2081…08d6` 匹配的私钥；
  - 0.4.5 私钥 `var/handoff-packages/keys/ed25519.key` 创建时间 2026-11-04 09:29:15，
    对应 `key_id=ed25519:b07741b2…9555`；
  - `var/handoff_packages.py` 每次构建先整体删除 `var/handoff-packages`，再调用
    `signing.generate_keypair()`，不做旧 key 备份或复用。
- **影响**：
  - 0.4.4 私钥不可恢复，无法再为 0.4.4 格式的新包签名；
  - 旧包签名本身仍有效：用 0.4.4 wheel + 第六轮交接包里的旧公钥仍可验；
  - 用 0.4.5+ wheel 验 0.4.4 包会先 `PRODUCER FAIL`，随后签名检查早退为
    `SIGNATURE NOT CHECKED`，不是验签失败；
  - 不影响 `conclusion_digest`/`inputs_digest` 等数据摘要，只影响“谁签的”信任链。
- **处置**：
  - 0.4.6 复用 `b07741b2…9555`，不再生成新 key；
  - 后续构建改为从固定路径加载私钥，禁止删除或覆盖；
  - 交接包保留旧公钥与旧 wheel 位置说明，旧包验签必须配对应版本 wheel。

## 发行物签名钥误用事件（0.4.6 → 0.4.7）

- **性质**：发行物层 `SHA256SUMS.sig` 的 `key_id` 从 `ed25519:5e797e18…5bb6`
  静默变为 `ed25519:b07741b2…9555`，无任何记录；不是计划内轮换。
- **根因**：0.4.6 构建命令把包签名私钥 `var/handoff-keys/ed25519.key` 传给
  `scripts/build_release.py --signing-key`；当时脚本不校验 key_id，故未报错。
  两把私钥都是持久文件，问题在**构建参数与用途混用**，不是“每版 keygen”。
- **影响**：0.4.6 发行物与 0.4.5 及更早发行物不再共享同一个来源锚点；外部核验方若
  缓存了 0.4.1–0.4.5 的 `key_id`，会判定 0.4.6 发行物来源不明。轮换本身未泄露私钥，
  0.4.6 发行物仍可用 `b07741b2…9555` 自洽验签。
- **处置**：
  - 0.4.6 发行物不重签、不改写，按历史原样保留；
  - 0.4.7 恢复 `5e797e18…5bb6`，`build_release.py` 固定期望 key_id，非预期钥
    默认拒绝构建，只有显式 `--allow-key-rotation <理由>` 才放行；
  - 交接目录附旧发行物逐文件 SHA-256 清单，旧发行物仍可独立核验；
  - 两把钥继续分别用于“发行物”与“举证包”，不得混用；详见 `docs/签名方案.md` §5。
