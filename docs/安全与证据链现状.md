## 1. 一句话结论

当前能证明“包内自洽，且同一批输入在同版本代码下可复算出同一三元组”；把**四元组**（`schema_version` + 三元组）另存在包外时，还能发现整包被替换或“伪装成 v1”的降级。配置 Ed25519 私钥后导出 v3 签名包；签名载荷新增 `inputs_digest`，把 `inputs/` 全部文件（含 `inputs/manifest.json`）纳入签名。复核方用**包外固定公钥**（`--public-key`）验签时，才能把“来源可信”从包外记录提升为密码学验证。签名仍不证明结论正确（仍需 `replay`），也不能防私钥持有人作恶。

- **能防**：单条审计事件被改、输入文件被替换（v3 `inputs_digest`）、整批换 `inputs/` 并同步改 `inputs/manifest.json`（v3 `INPUTS FAIL`）、manifest 字段被改而未同步校验和、改 `conclusions_final.csv`（v3 `ARTIFACT`）、manifest 任一字段被改后重算 checksum（签名覆盖）、包内 schema/三元组与包外四元组不一致（需显式传锚点）、换签名者（需外部 pin）。
- **不能防**：能取得签名私钥者签任意包；包外 pin 公钥被同时替换；没有包外四元组/固定公钥时 `verify.py` 仍可能输出 `RESULT OK`（此时只是包内自洽）；`inputs_digest` 不证明输入能复算出签名中的结论摘要（仍需 `replay`）；未配置私钥时导出仍是 v2 无签名包。

## 3. 仍未闭合 / 仅部分闭合

1. **H-01 残余边界（Ed25519 已落地）**

   交付事件登记入口现为 `record_delivery_event()` / `--record-delivery-as`；旧别名 `sign_package()` / `--sign-as` 保留。它只向审计链追加 `evidence.sign` 事件，**不是密码学签名**，不要和 v3 `manifest.signature` 混为一谈。

   **已证明**：配置私钥后导出的 v3 包，manifest 关键字段（schema/三元组/`inputs_digest`/`manifest_checksum`，含 `conclusions_sha256`）与重算链头由私钥签过；改 manifest 任一字段并重算 checksum、换 `inputs/` 文件并同步改 `inputs/manifest.json`、只改登记表、增删输入文件、改结论 CSV、v3 缺签名/缺输入摘要都会 FAIL；用包外固定公钥 pin 时可识别换签名者。

   **仍不能证明/防**：私钥持有人可签任意包；pin 公钥若与包外记录一起被换，信任根仍失守；`inputs_digest` 只证明输入字节与签名一致，不证明这些输入能复算出签名中的结论摘要；结论正确性仍需 `replay`。**运维剩余**：交付验收应统一要求 `--require-signature` + 外部 pin；私钥托管、备份、轮换与吊销流程需另行落地（`keygen` 已支持轮换期多公钥并存）。

2. **M-02 数据最小化（部分闭合）**

   **已做（零风险部分）**：`question_log` 增加 `run_id`，问答落库时关联最近一次校验 run；导出只收本 run 记录，历史 NULL 行与其他 run 记录不进入包。导出 `responsibility.json` 与 `conclusions_final.csv` 去掉 `amount_cents_input`、`amount_entered_by`；数据库与复核台仍保留金额和录入人，包内不再出现。两项都不改变 `input_fingerprint`、`conclusion_digest` 或既有包 replay；签名包的 `inputs_digest` 也不变。

   **仍会看到**：`inputs/employee.csv` 整文件含 `normal_hourly_cents`、`pseudonym` 等；`employee/punch/schedule/leave` 等原始行仍按 run 范围整文件打包；`responsibility.json` 仍含 `confirmed_by`、`note`；审批文号/附件哈希仍可见。**未做**：输入 CSV 字段裁剪、`emp_id`/`pseudonym`/`confirmed_by` 假名化、包内字段级加密。原因是输入副本一改，`input_fingerprint` 与包内指纹就会变，当前 replay 仍要求指纹等于 run 时的原始输入；需要先设计“包内输入指纹重算”或重新跑 check。详见 `docs/数据最小化方案.md`。

3. **旧 schema 兼容面：v1 允许缺校验和**  
   `verify.py` 与 `replay` 对 `wca-evidence-package-v1` 缺 `manifest_checksum` 只打印 `MANIFEST CHECKSUM MISSING` 并继续；把 v2 包改成 v1 并删校验和，manifest 完整性检查即被跳过。当前已实现 `--expect-anchor` / `WCA_EXPECT_ANCHOR` 四元组：若包外记录 `schema_version=2`，伪装 v1 会被 `ANCHOR FAIL` 拦下；**但不传四元组时仍走旧包兼容路径**。  
   **闭合需要**：交付验收只接受 v2+；v1 仅作历史回放并要求显式 legacy 开关 + 包外四元组；旧包只登记、不重写历史。

4. **`raw_file.row_count` 语义**  
   CSV 通道 `import_csv_file` 登记的是 `len(header)`（表头列数），程序化 `import_rows` 登记的是 `len(seq)`（行数）；该值进入 `input_fingerprint` 的 `rows` 字段，且 `input_files.csv` 的 `row_count` 会误导读者。同一批数据换通道导入可能得到不同指纹。  
   **闭合需要**：统一成数据行数并接受指纹断代（升版本、重跑全套证据）；或拆成 `header_columns` / `row_count` 两个字段并改文档/测试。该取舍已记在 `docs/待确认清单.md` 第 R-8 项，需先裁定。

5. **目录包资源上限已补，但外部解压仍不受控**  
   `replay.unpacked` 现对目录包执行 `_check_dir_limits`：条目 256、单文件 32 MiB、总量 64 MiB、深度 8；遍历时逐块读实际内容，拒绝符号链接/Windows 重解析点/硬链接/设备或非普通文件。`verify.py` 运行在已解压目录上，无法限制外部解压工具先写出巨型文件；`inputs/manifest.json` 作为普通文件受单文件/总量限额约束，但没有单独更小的上限。  
   **剩余风险**：外部解压器/用户手工解压可先耗尽磁盘；目录包根目录本身若是指向别处的链接，调用方需自行确认来源；不可信包默认只接受 zip 的交付规则仍未强制。

6. **同机回环可绕过演示口令闸门**  
   `assert_demo_credentials_safe` 对回环直接返回；请求中间件对 `scope["server"]` 的回环地址直接放行；`README.md` 与 `docs/演示脚本-30分钟.md` 仍公开 `wca-demo-*` 口令。  
   **影响**：同机进程、多人共用主机、或从本机回环连入的反向代理，仍可用公开口令登录 AD/OP/RV/EM/AU；非回环闸门对这条路径无效。**闭合需要**：移除/轮换文档口令，改成一次性生成或显式 `WCA_ALLOW_DEMO_ACCOUNTS`；或把本机回环明确列为信任边界并配 OS 级访问控制。

## 4. 举证包可信度分层（由低到高）

| 层级 | 形态 | 攻击者要骗过需做到什么 | 靠什么发现 | 现状 |
|---|---|---|---|---|
| 1 | 无校验和旧包（schema v1） | 改写 manifest/链/输入并重算链；不需要密钥 | 包外四元组或独立重放；无锚点时 `RESULT OK` 也可能出现 | 仅作 legacy 兼容 |
| 2 | 有自校验和（schema v2 `manifest_checksum`） | 改字段后重算 `manifest_checksum`、链和输入哈希 | 包外四元组；否则只能发现“忘记重算校验和”的低级错误 | 当前默认 |
| 3 | 自校验和 + 包外四元组 | 同时篡改包与包外记录，或让接收方使用错误锚点 | `--expect-anchor` 含 `schema_version`，不符即 `ANCHOR FAIL`；可拦“伪装 v1” | 已支持，但非强制 |
| 4 | Ed25519 签名包（schema v3） | 取得签名私钥，或替换包外 pin 公钥 | 验签失败、`key_id`/公钥指纹不符、`inputs_digest` 不符；未 pin 时仅证明包内自洽 | **已实现**；由 `--signing-key` / `WCA_SIGNING_KEY_*` 启用 |

> 层级 3 保护 schema 版本与三元组；manifest 的 counts、scope、inputs 元数据仍可能被改。层级 4 才把“来源可信”从包外记录移到密码学验证：**必须用包外固定公钥 pin**，包内自带公钥只能证明“包内自洽”。

## 5. 交付验收清单

| 命令 | 证明什么 | 单独跑的盲区 |
|---|---|---|
| 包内 `verify.py` | manifest 自校验和、审计链、输入逐文件哈希、`inputs_digest`、结论集哈希（`ARTIFACT`）、签名（`pinned`/`package self-check`）、包内 schema/三元组与包外四元组一致 | 不重跑引擎，不能证明“这些结论是这批输入算出来的”；`inputs_digest` 只证明输入字节与签名一致 |
| `src.cli replay` | 重导输入、重跑引擎，得到实算三元组与结论条数，并与包内三元组比对；同样校验 `ARTIFACT` 与签名 | 不覆盖 manifest 自校验和、包外四元组与包体完整性 |

```powershell
# 1) 解包后用系统 Python 跑包内 verify.py（旧 v1/v2 无签名时只依赖标准库）
Expand-Archive var/packages/<run_id>.zip -DestinationPath var/verify-<run_id>
Set-Location var/verify-<run_id>
pip install -r verify-requirements.txt   # 仅 v3 验签需要：pynacl==1.6.2
python verify.py --expect-anchor 2,<rule_pack_version>,<input_fingerprint>,<conclusion_digest> `
                 --public-key <包外固定公钥> --require-signature
# 期望：MANIFEST SCHEMA v3 OK / MANIFEST CHECKSUM OK / CHAIN OK / INPUTS OK /
#       INPUTS DIGEST OK / INPUTS SIGNED OK / ARTIFACT OK /
#       SIGNATURE OK (pinned key_id=...) / ANCHOR CHECK OK / RESULT OK，rc=0

# 2) 用同一包外四元组重放（会创建临时库，不写活动库）
Set-Location <项目根目录>
uv run python -m src.cli replay var/packages/<run_id>.zip --expect-anchor 2,<rule_pack_version>,<input_fingerprint>,<conclusion_digest> --public-key <包外固定公钥> --require-signature
# 期望：三元组逐项一致、结论条数一致，rc=0
```

- **`verify.py` 必须带 `--expect-anchor`**：不传时只做包内自洽校验，`RESULT OK` 不能当成来源可信；`--expect-triple` 仍可用但不约束 schema。
- **签名包必须带 `--public-key`**：包内公钥只能打印 `SIGNATURE OK (package self-check; NOT source trust)`；只有包外固定公钥 pin 才打印 `SIGNATURE OK (pinned ...)`。交付验收建议同时加 `--require-signature`，强制旧 v1/v2 无签名包失败。
- **`verify.py` 现在覆盖输入摘要**：`INPUTS DIGEST OK` / `INPUTS SIGNED OK` 表示输入摘要与签名一致；`INPUTS FAIL` 表示换 CSV、改 `inputs/manifest.json` 或增删输入文件。但结论是否正确仍必须 `replay`。
- **包外四元组记录位置**：随交付邮件正文/附件清单记录，并写入工单或变更单的固定字段；至少两处不同系统，最好由接收方或第三方保存。建议一起记录 `run_id`、四元组、包文件 SHA-256、交付时间、验收人、签名 `key_id`。
- **不要**写进包内 README/manifest 或文件名；**不要**用 `manifest_checksum` / `manifest_sha256` 代替包外锚点。`python -m src.cli verify` 是库内审计链自检，不等价于包内 `verify.py`。
- `manifest_checksum` 与 `manifest_sha256` 不是同一个值：前者是 manifest 内自校验和（文件内，v3 被签名覆盖），后者是 manifest 文件字节哈希（返回值/数据库列），两者都不是签名本身。

## 7. 已决策与待决策项

**签名算法：已选 Ed25519（2026-11-03，见 `docs/签名方案.md`）**

选 `pynacl==1.6.2`：复核方只拿公钥验签，私钥留在导出方/受限目录；比 HMAC 少一个“复核方持私钥也能伪造”的结构性问题。代价是包内 `verify.py` 验签需要 PyNaCl（`verify-requirements.txt` 固定版本，缺失时失败关闭），且私钥生命周期/备份/轮换/吊销仍需运维落地。当前取舍：配置私钥才导出 v3，未配置保持 v2；旧包不强制签名，交付验收用 `--require-signature` + 包外 pin 收紧。

**数据最小化取舍**  
按 run 裁剪输入、字段白名单、金额单独受限、问答按 run 脱敏，能降低隐私/商业保密暴露和包体积；代价是 `input_fingerprint` 与包内哈希会变、旧包不可直接比较，且 `QUAL-02` 这类依赖全库 `ingest_issue` 的结论可能需要保留全局文件，否则 replay 可能对不上。保留全量输入则举证最完整、重放最省事，但外部接收方会看到与本次结论无关的员工、工资基数和跨 run 问答元数据。需要先定“默认发 scoped 还是 full”，再决定是否升 schema 与重跑证据。
