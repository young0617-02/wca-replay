# 具名确认：流程与角色定义

> 适用软件版本：0.4.17（已冻结）
> 文档性质：企业落地流程草案。标【待确认】的条目必须由业务方书面裁定后才生效。
> 本文只定义流程与角色，不改代码、不改规则包、不改 `handoff/` 下任何文件、不改已交付包。
> 读者对象：企业 HR、法务、合规、IT 管理员、内部审计。

## 0. 标注约定与一句话结论

| 标记 | 含义 |
|---|---|
| 【事实】 | 可从当前代码、schema、导出产物或仓库文档直接核对 |
| 【建议】 | 本文给出的流程设计，企业可按自身制度裁剪 |
| 【待确认】 | 必须由业务方书面决定，本文不替企业拍板 |

**一句话结论**：系统已能登记“谁在什么时候对哪条结论做了什么决定”，并把该记录导出到举证包；但系统里**没有真实姓名、职务、工号、工单号、附件字段**，确认人也只是登录账号名。因此真实具名确认必须采用**系统内登记 + 包外凭证归档**双轨，单靠系统字段不足以证明“某位真实自然人签认”。

## 1. 当前系统能做什么、不能做什么

### 1.1 已具备（【事实】）

| 能力 | 实际落点 |
|---|---|
| 每条需人工处置的结论自动开复核单 | 校验时对 `REVIEW`、`VIOLATION` 级 finding 写入 `review_item`，初始 `OPEN` |
| 人工给出三种决定 | `APPROVED` / `REJECTED` / `NEEDS_MORE_DATA` |
| 记录确认人与时间 | `review_item.reviewer`、`review_item.decided_at` |
| 记录确认说明 | `review_item.note` |
| 追加审计事件 | `audit_event`，动作 `review.decision`，操作者 `human:<账号名>` |
| 进入举证包 | `conclusions_final.csv`、`responsibility.json`、`manifest.counts.final_conclusions` |
| 包级防篡改 | 两个文件受 `artifact_sha256`、`artifacts_digest` 与包签名保护 |

### 1.2 尚不具备（【事实】）

| 缺口 | 后果 |
|---|---|
| 无真实姓名字段 | `reviewer` 只是登录用户名；`employee.pseudonym` 是合成化名，系统按设计不存真实姓名 |
| 无职务、无 HR 工号字段 | 无法在包内直接证明“此人是 HR 负责人/法务” |
| 无工单号、无附件字段 | 凭证必须落在包外 |
| 不按结论等级做授权 | 只要拥有 `RV` 或 `AD` 角色，就能对本 run 任意一条复核单提交任意决定 |
| 不支持双签 | 一张复核单只有一个 `reviewer` 和一个 `decided_at`，第二签无处落 |
| 不支持撤回 | 已决复核单不可覆盖；无撤回接口 |
| 无演练/真实标记 | 系统没有专门字段区分演练数据与真实签署 |
| 复核台不按组织隔离 | `RV/AD` 可看到本 run 全部员工的复核单 |

> 这些缺口决定了本文的写法：**能在系统里做的，写进系统；系统做不到的，用包外凭证与授权书补足，并明确标注“系统未强制”。**

## 2. 谁能确认

### 2.1 系统内实际存在的角色（【事实】）

系统角色码来自 `src/auth.py` 的 `ROLES`，服务端权限来自 `src/web/routes.py`。

| 角色码 | 系统定位 | 与“确认”直接相关的能力 | 不能做什么 |
|---|---|---|---|
| `OP` | 运营 | 导入、发起校验、导出 | 不能进复核台、不能提交复核结论 |
| `RV` | 复核 | 复核台 `/review`、提交复核结论、导出、登记交付事件 | 不能导入/发起校验、不能写审批台账 |
| `AD` | 管理员 | 复核、导出、导入/校验、审批台账读写 | 技术上什么都能做，因此**不适合兼任业务确认人** |
| `AU` | 审计 | 审批台账只读；可登录与问答 | 不能复核、不能导出、不能写审批台账；问答会写观测留痕 |
| `EM` | 员工 | 仅本人问答 | 不参与确认流程 |

- 【事实】提交复核结论的接口是 `POST /api/review/{review_id}/decision`，服务端要求 `RV` 或 `AD` 角色，并强制 CSRF；角色不足返回 403。
- 【事实】`decide_review()` 函数本身**不校验角色、不校验结论等级**；角色限制只在 Web 入口。直接调用服务层或直接改库可以绕开角色限制，因此必须靠账号治理与操作审计补足。
- 【事实】系统没有 CLI 复核命令；正常确认入口只有复核台/该 HTTP 接口。

### 2.2 企业岗位到系统角色的映射（【建议】）

| 企业岗位 | 建议授予的系统角色 | 建议职责 | 备注 |
|---|---|---|---|
| HR 专员 | `RV` | 核对 `REVIEW` 级结论的事实与行级来源，提交“通过/存疑”建议 | 不建议单独确认 `VIOLATION` |
| HR 负责人 | `RV` | 确认 `VIOLATION` 第一签；录入人工金额（如需） | 金额不是引擎输出 |
| 法务 | `RV`，可加 `AU` | 对 `VIOLATION` 会签；审阅定性风险 | `AU` 只读，便于查审批台账 |
| 合规官 | `RV`，可加 `AU` | 对高风险结论会签；维护授权矩阵 | 与法务职责边界由企业划定 |
| IT 管理员 | `AD` | 账号、密钥、导出、备份 | 建议**不担任**业务确认人，避免既当运动员又当裁判 |
| 内部审计 | `AU` | 只读抽查 | 不能确认、不能导出 |

- 【建议】同一人不要同时持有 `AD` 与业务确认职责；若因人数少必须兼任，应在授权书中写明兼任理由与补偿控制（如双人复核、月度抽查）。
- 【事实】创建账号前，该 `emp_id` 必须已存在于 `employee` 主数据；否则 `users` 命令直接拒绝，或同步时被跳过。
- 【事实】账号口令只以 scrypt 哈希写入 `config/users.json`，不存明文。

### 2.3 按结论等级的确认权限矩阵（【建议】，系统未强制）

| 结论等级 | HR 专员 | HR 负责人 | 法务 | 合规官 | 系统当前是否强制 | 说明 |
|---|---|---|---|---|---|---|
| `REVIEW` | 可确认 | 可确认 | 可复核 | 可复核 | 否 | 建议至少一人确认；高风险主题可升级会签 |
| `VIOLATION` | 不可单独确认，只能提交建议 | 可确认（第一签） | 必须会签（第二签） | 可确认/会签 | 否 | 系统一张复核单只能记一个确认人，第二签需包外凭证补足（见 §8.4） |
| `DEFENSIBLE` | 不建议确认 | 不建议确认 | 不建议确认 | 不建议确认 | 系统不自动开单 | 保留机器判定，不作为“违规/合规”结论使用 |
| `REJECT`（导入质量） | 可处置 | 可处置 | 不涉及 | 不涉及 | 走导入质量清单 | **不是合规结论**，不计入确认范围 |
| 人工金额 | 不可录入 | 可录入 | 不可录入 | 不可录入 | 否（`RV` 均可录） | 金额只作复核参考，导出时被剔除 |
| 计量值/倍数/条文/分级 | 不可修改 | 不可修改 | 不可修改 | 不可修改 | 是（无字段可改） | 机器判定必须保留 |

> 【事实】上表的“系统是否强制”一列为“否”的项，当前代码都不会拦；它们只能靠授权书、账号分离、复核台操作规范和包外凭证执行。
> 【待确认】企业需决定：`VIOLATION` 是否强制双签、哪类主题升级到合规官、金额是否必须录入。

### 2.4 不允许人工确认、必须保留机器判定的对象（【事实】+【建议】）

| 对象 | 系统行为（【事实】） | 流程要求（【建议】） |
|---|---|---|
| 工时分钟数、加班倍数档位 | 由确定性引擎计算，复核接口无字段可改 | 不得以“确认”名义改写数值 |
| `rule_id`、`rule_version`、条文引用、来源行号 | 由引擎与规则包产出，复核接口无字段可改 | 不得手工替换条文或行号 |
| `severity` | `decide_review()` 只更新 `status/reviewer/decided_at/note/amount_*`，**不改 severity** | 人工确认不能让 `VIOLATION` 变成 `REVIEW`，也不能反向升级 |
| 应付金额、赔偿数额、违法定性 | `responsibility.json` 的 `never_output` 明确列为不输出 | 这些不是“可确认结论”，不得借确认流程产出 |
| 无证据定位的结论 | 仍会进入 `findings.csv` 等待处置 | 不得用“已确认”把无证据结论包装成有证据 |
| 缺失输入导致无法判断的事项 | 进入未覆盖清单/质量问题 | 只能补数据后重跑，不能靠确认绕过 |

- 【建议】确认只回答“这条机器结论是否成立、证据是否可接受”，不回答“法律责任是什么、该赔多少钱”。
- 【事实】`DEFENSIBLE` 级结论不会自动生成复核单，因此复核台无法“确认”它；它保持机器判定。

## 3. 确认的对象与边界

### 3.1 三种决定的实际语义（【事实】）

| 决定值 | 复核台文案 | 实际含义 | 是否算“确认结论成立” | 导出后出现在哪里 |
|---|---|---|---|---|
| `APPROVED` | 通过 | 认可该结论及其证据 | **是** | `responsibility.json` 的 `human_confirmations`；`conclusions_final.csv` 的 `decision=APPROVED` |
| `REJECTED` | 更正 | 不认可该结论 | **否**，属于处置意见 | 同样两个文件，`decision=REJECTED` |
| `NEEDS_MORE_DATA` | 存疑 | 证据不足，要求补证/继续核查 | **否**，事项未闭环 | 同样两个文件，`decision=NEEDS_MORE_DATA` |
| `OPEN` | — | 尚未处置 | 否 | 不进入结论集，计入 `unsigned_pending` |

> 【实测·风险】已在独立临时 SQLite 库实测（`APPROVED` / `REJECTED` / `NEEDS_MORE_DATA` 各一例）：三种决定都会写入 `conclusions_final.csv`，且 `manifest.counts.final_conclusions` 都从 0 变为 1；完整原始输出见 §11。
> 这与 `docs/操作手册.md` §5.1（修正前）的表述不一致；该句已按 §11.5 路径 A 改写。
> 【建议】对外引用计数时，必须同时看 `decision` 列，不能只看行数；对外口径的选择见 §9 Q3。

### 3.2 确认的粒度（【事实】）

- 一条 finding 对应一张复核单；一次决定只覆盖该 finding。
- 没有批量确认接口；不能一次确认“某规则下所有员工”。
- 周期聚合/批次 finding（例如 `QUAL-01` 的批次结论）在 CSV 里是一行，但代表多条问题；**一次确认覆盖整批**，不能只确认批内某一条来源。
- 确认是**按 run** 的：新一次校验会生成新的 `review_item`，上一次 run 的确认不会自动带到新 run。

### 3.3 哪些动作算确认、哪些不算

| 动作 | 算不算 | 依据 |
|---|---|---|
| 对具体 `review_id` 提交 `APPROVED` | **算** | 写 `review_item` 状态并追加 `review.decision` 审计 |
| 提交 `REJECTED` 或 `NEEDS_MORE_DATA` | **不算** | 是处置意见，不是“结论成立” |
| 只填写 `note`、不选决定 | **不算** | 接口要求 `decision` 为三个合法值之一，否则 400 |
| 在复核台查看、筛选、导出报表 | **不算** | 无状态写入 |
| 登记交付事件 `evidence.sign` | **不算** | 只记录“谁登记了这次交付”，不改任何结论状态 |
| 给举证包做 Ed25519 签名 | **不算** | 证明包字节与私钥匹配，不证明某自然人确认了结论 |
| 邮件回复“同意”、口头同意、会议纪要 | **不算**（除非另行归档为凭证并回填工单） | 系统无记录 |
| 在审批台账发布批文 | **不算** | 审批台账是特殊工时批文，不是 finding 确认 |

### 3.4 能改什么、不能改什么（【事实】）

| 可写 | 不可写 |
|---|---|
| `review_item.status`（三选一，仅未决单） | `finding.severity` |
| `review_item.reviewer`（由入口写入账号名） | `finding.rule_id` / `rule_version` |
| `review_item.decided_at`（系统时间） | `finding.metric_json` |
| `review_item.note`（自由文本） | `finding.emp_id` / `work_date` / `period_key` |
| `review_item.amount_cents_input` 及录入人/时间（人工金额） | `finding.citation_ids` / `source_refs` / `evidence_json` |
| — | 新增/删除 finding |

- 【事实】人工金额只留在库与复核台，导出包会剔除 `amount_cents_input`、`amount_entered_by`（`_minimized_responsibility`）。
- 【建议】`note` 只写结论说明与凭证编号，不写真实姓名、身份证号、联系方式等个人信息；`note` 会进审计链并导出到包内。

## 4. 系统内的实际落点

### 4.1 承载表：`review_item`（【事实】）

| 字段 | 类型/取值 | 含义 | 来源 |
|---|---|---|---|
| `review_id` | 自增主键 | 复核单号 | `src/schema.sql` |
| `run_id` | 文本，可空 | 归属校验 run | 同上 |
| `source_type` | `finding` / `answer` / `ingest_issue` | 复核对象类型 | 同上 |
| `source_id` | 文本 | finding 的键：`rule_id:emp_id:(work_date 或 period_key)` | 同上；由 `src/engine.py` 开单时拼装 |
| `status` | `OPEN` / `APPROVED` / `REJECTED` / `NEEDS_MORE_DATA` | 复核状态 | 同上 |
| `reviewer` | 文本，可空 | 确认人，写入的是**登录账号名**，不是姓名 | 同上 |
| `decided_at` | ISO-8601 文本，可空 | 决定时间，系统本地时间（+08:00） | 同上 |
| `note` | 文本，可空 | 复核说明 | 同上 |
| `amount_cents_input` | 整数（分），可空 | 人工录入金额，非引擎输出 | `src/db.py` 的 `_migrate_review_amount` 补列 |
| `amount_entered_by` | 文本，可空 | 金额录入人（`human:<账号名>`） | 同上 |
| `amount_entered_at` | ISO-8601 文本，可空 | 金额录入时间 | 同上 |

- 【事实】`review_item` **没有开单时间字段**；开单时间只能从 `run.finished_at` 或 `audit_event` 的 `check.run` 事件推断。
- 【事实】`review_item` **没有姓名、职务、工号、工单号、附件、双签、演练标记字段**。
- 【事实】复核单由引擎在 `check` 时自动创建，仅针对 `REVIEW` 与 `VIOLATION`；`DEFENSIBLE` 不开单。
- 【事实】`answer` 与 `ingest_issue` 也可能有复核单，但它们不是工时结论确认，流程上不得混用。

### 4.2 状态流转（【事实】）

```text
check 运行
  └─ 对每条 REVIEW / VIOLATION finding：INSERT review_item(status=OPEN, note='校验引擎自动开单，待人工复核')
       │
       ├─ 复核台提交 APPROVED          → status=APPROVED
       ├─ 复核台提交 REJECTED          → status=REJECTED
       └─ 复核台提交 NEEDS_MORE_DATA   → status=NEEDS_MORE_DATA
                    │
                    └─ 终态：不可再次覆盖；无撤回/重置接口

新一次 check 运行
  └─ 生成新的 review_item（新 run_id、新 review_id）；旧 run 的复核单保持原样
```

- 【事实】`decide_review()` 发现 `decided_at` 已非空即拒绝，报“已有复核结论，不得覆盖（只允许追加新单）”。
- 【事实】复核台只在 `status=OPEN` 时显示决定表单；已决行只读展示。
- 【事实】审计链只追加，不删改；`review.decision` 事件即使用户后来反悔也不会消失。

### 4.3 审计事件（【事实】）

| 项 | 实际值 |
|---|---|
| 动作 | `review.decision` |
| 操作者 | `human:<reviewer>`，其中 `<reviewer>` 为登录账号名 |
| 时间 | 与 `decided_at` 同一时间 |
| 载荷 | `review_id`、`source_type`、`source_id`、`decision`、`note`、`amount_cents_input` |
| 链 | 进入 `audit_event` hash 链；包内 `audit_chain.jsonl` 与 `manifest.chain_verification` 覆盖 |

### 4.4 包内承载（【事实】）

| 包内文件 | 承载内容 | 受什么保护 |
|---|---|---|
| `conclusions_final.csv` | 每行：`rule_id, emp_id, work_date, period_key, severity, decision, confirmed_by, confirmed_at, note` | `artifact_sha256`、`artifacts_digest`、包签名 |
| `responsibility.json` | `human_confirmations`（含 `decision/confirmed_by/confirmed_at/note`）、`human_confirmed_findings`、`unsigned_findings_excluded_from_conclusions`、`signed`、`signed_by` | 同上 |
| `manifest.json` | `counts.final_conclusions`、`counts.unsigned_pending`、`responsibility` 摘要块 | `manifest_checksum` 与签名 |

- 【事实】`responsibility.json` 的 `signed` / `signed_by` 来自 `evidence.sign` **交付登记事件**，不是“确认人已签字”。有交付登记也可能零确认（§11 实测：零确认时 `signed=true`）；有确认也可能没有交付登记。
- 【事实】`signed` 不随 `APPROVED`/`REJECTED`/`NEEDS_MORE_DATA` 变化，也不代表有人做过决定；它只是“本 run 有交付登记”。
- 【事实】`conclusion_digest` 只覆盖 finding 的九个规范字段，**不覆盖人工确认**；改 `conclusions_final.csv` 不会报 `FINDINGS DIGEST FAIL`，而会报 `ARTIFACT FAIL`。验收时必须同时看 `ARTIFACTS OK`。
- 【事实】`wca replay` 不重建人工确认；只核对 `conclusions_final.csv` 行数、`manifest.counts.final_conclusions` 与该文件的 `conclusions_sha256`。

### 4.5 入口、权限与实名缺口（【事实】）

| 项 | 实际值 |
|---|---|
| 唯一正常入口 | `POST /api/review/{review_id}/decision`（复核台调用） |
| 角色 | `RV` 或 `AD` |
| CSRF | 必须，缺失/错误 403 |
| 确认人来源 | 会话中的 `user.username`；不接受调用方自报姓名 |
| CLI | 无复核命令 |
| 组织范围 | 复核台不按组织过滤，`RV/AD` 可见本 run 全部复核单（`employee.acl_scope` 存在，但复核队列查询未使用） |
| 真实姓名 | 系统内不存在；`employee.pseudonym` 是合成化名 |
| 工号 | 只有 `app_user.emp_id`，指向合成化名员工，不保证等于企业 HR 工号 |

> 结论：**系统能证明“某个账号在某个时间对某条结论做了某个决定”，不能单独证明“某个真实自然人签了字”。** 后者必须由 §5 的包外凭证补足。

## 5. 签署凭证怎么留

### 5.1 凭证要素与落点（【事实】+【建议】）

| 凭证要素 | 系统内是否已有 | 实际字段/位置 | 包内是否可见 | 【建议】归档位置 |
|---|---|---|---|---|
| 姓名 | 否 | 无；`employee.pseudonym` 是化名 | 否 | 人员授权书、签字页/电子签文件 |
| 职务/岗位 | 否 | 无职务字段；`employee.job_code` 是决定特殊工时适用性的岗位编码，不是确认人职务 | 否 | 人员授权书 |
| HR 工号 | 否（`app_user.emp_id` 不是 HR 工号） | 仅账号绑定 `emp_id` | 仅 `confirmed_by` 账号名 | 人员授权书、凭证页 |
| 确认时间 | 是 | `review_item.decided_at` → `confirmed_at` | 是 | 包内 + 外部凭证时间 |
| 工单号 | 否 | 无专用字段；只能写进 `note` | 是（若写入 note） | 工单系统 + 外部台账 |
| 附件 | 否 | 无（`approval_doc.attachment_sha256` 属审批台账，不是确认附件） | 否 | 凭证归档目录/电子签平台 |
| 结论标识 | 是 | `source_id`、`rule_id`、`emp_id`、`work_date/period_key` | 是 | 包内 + 外部台账 |
| 包标识 | 是 | `manifest.run_id`、包文件名、`package_sha256`、四/五段锚点 | 是 | 交付记录/外部台账 |

- 【建议】姓名、职务、工号、签字原件只放包外；包内保持化名与账号名，避免把真实身份重新引入已做数据最小化的举证包。
- 【建议】`note` 采用可读前缀，例如 `[CONFIRM] ticket=HR-2026-00123 cred=ARCH-2026-001`；这只是流程约定，系统不做格式校验，也不阻止他人写别的内容。
- 【事实】`note` 会进 `audit_event` 并写入 `conclusions_final.csv` / `responsibility.json`，因此不要把敏感个人信息写进 `note`。

### 5.2 凭证与举证包的绑定关系（【建议】）

```text
系统内                               包内                                  包外
────────────────────────────────────────────────────────────────────────────────
review_item(decision=APPROVED)  →  conclusions_final.csv          →  交付记录：包 SHA-256
reviewer / decided_at / note    →  responsibility.json            →  四/五段锚点
review.decision 审计事件        →  artifact_sha256（逐文件）       →  artifacts_digest
                                →  artifacts_digest（整组）         →  key_id / 签名时间
                                →  Ed25519 签名（v3 包）            →  工单号 + 凭证归档编号
                                                                   →  授权书 + 签字原件
```

绑定操作顺序（【建议】）：

1. 在复核台完成决定，确认 `review_item` 已有 `reviewer`、`decided_at`、`decision`。
2. 导出举证包；从 `manifest.json` 取 `run_id`、`counts.final_conclusions`、`artifact_sha256["conclusions_final.csv"]`、`artifacts_digest`。
3. 计算包文件 SHA-256；按 `docs/交付与验收SOP.md` §1 记录四段或五段锚点、`key_id`、交付时间、验收人。
4. 在包外凭证台账登记：包 SHA-256、锚点、`artifacts_digest`、`run_id`、结论标识、`confirmed_by` 账号名、工单号、凭证归档编号。
5. 接收方用 `wca-verify` + `wca replay` 验包；**验包工具不会校验包外凭证**，凭证真实性由人工按工单号调阅归档件核对。

### 5.3 包外归档清单（【建议】）

| 归档物 | 内容 | 保存责任 |
|---|---|---|
| 人员授权书 | 姓名、岗位、系统角色、可确认等级、金额权限、生效期、主/备份确认人、本人签字 | HR / 合规 |
| 单次确认凭证 | 结论标识、决定、理由、签字页或电子签 PDF、签署时间、工单号 | 确认人所属部门 |
| 工单记录 | 工单号、发起/关闭时间、附件索引 | 工单系统管理员 |
| 交付记录 | 包 SHA-256、四/五段锚点、`artifacts_digest`、`key_id`、交付时间、验收人 | 交付方 |
| 密钥登记 | 公钥、`key_id`、保管人、轮换记录 | 交付方（模板见 `docs/信任根-落地流程.md` 附录 A） |
| 旧包与旧锚点 | 每次交付的包与锚点，按版本/时间归档，不删除 | 交付方 + 接收方各存一份 |
| 演练记录 | 演练账号、演练库、演练包、演练结论 | 内部审计，单独存放 |

### 5.4 禁止事项（【事实】+【建议】）

- 【建议】不得把私钥、原始数据库、明文口令、真实身份信息放进举证包或 `note`。
- 【建议】不得用 `note`、邮件或会议纪要代替正式凭证；它们只能作为辅助材料。
- 【建议】不得把“包签名成功”当成“确认人已签字”；两者是不同主体、不同动作。
- 【建议】不得把真实姓名写进 `note` 来“补字段”；这会破坏包的数据最小化设计，正确做法是包外归档并用凭证编号关联。

## 6. 拒绝、撤回与更正

### 6.1 三种处置的系统呈现（【事实】）

| 处置 | `review_item.status` | `responsibility.json` | `conclusions_final.csv` | `manifest.counts` |
|---|---|---|---|---|
| 通过 | `APPROVED` | 进入 `human_confirmations`，`decision=APPROVED` | 有一行，`decision=APPROVED` | 计入 `final_conclusions` |
| 拒绝 | `REJECTED` | 进入 `human_confirmations`，`decision=REJECTED` | 有一行，`decision=REJECTED` | **当前也计入 `final_conclusions`** |
| 存疑 | `NEEDS_MORE_DATA` | 进入 `human_confirmations`，`decision=NEEDS_MORE_DATA` | 有一行，`decision=NEEDS_MORE_DATA` | **当前也计入 `final_conclusions`** |
| 未处置 | `OPEN` | 不进入 `human_confirmations` | 不进入 | 计入 `unsigned_pending` |

> 【实测·风险】“拒绝/存疑也计入已确认结论”是当前代码行为（§11 实测），不是本文建议。对外汇报时必须按 `decision` 列拆分统计；口径调整列入 §9 Q3。

### 6.2 撤回：系统不支持（【事实】）

- 已决复核单的 `decided_at` 非空后，`decide_review()` 一律拒绝覆盖；复核台也不再显示决定表单。
- 系统没有“撤回”“作废”“重置”接口。
- 审计链只追加，`review.decision` 事件不能删除。
- 【建议】流程上把“撤回”定义为**新增一次更正流程**，而不是修改旧记录。

### 6.3 更正路径（【建议】，配合系统事实）

| 场景 | 系统行为（【事实】） | 建议处置 |
|---|---|---|
| 确认后发现结论有误 | 旧 `review_item` 不可改 | 修正输入数据或规则适用问题后**重新跑 check**，生成新 run、新复核单、新包 |
| 确认人想反悔 | 旧决定仍在审计链与旧包中 | 走新的更正 run；在包外台账把旧包标注为“已被新包替代”，不得删除旧包 |
| 接收方已收到旧包 | 旧包不可变 | 出具书面“撤回/更正说明”，写旧包 SHA-256、锚点、替代包 SHA-256 与锚点；新旧包并存归档 |
| 只是说明写错 | `note` 已写入审计链，不能改 | 新 run 重新确认并在新 note 中说明；或包外补充说明，注明对应旧审计事件 |
| 发现确认人越权 | 旧记录仍有效 | 立即停用账号、复核其全部确认、按授权书追责；对受影响结论重跑并重新确认 |

- 【建议】旧包处理三原则：**不删除、不改写、不重签**；只新增替代包与书面说明。
- 【建议】对外只声称“当前有效包”为最新一版；旧包作为历史证据保留，并明确标注替代关系。
- 【事实】包内摘要与签名保证旧包字节未被改动；任何“修补旧包”的做法都会被 `ARTIFACT FAIL` / 验签发现。

## 7. 演练数据与真实数据的区分标记

### 7.1 当前事实：系统没有专用标记

- 【事实】`review_item` 没有“数据来源/演练标记”字段。
- 【事实】`reviewer` 是自由文本；当前 2 条演练确认来自测试夹具 `tests/test_public_materials.py`，确认人固定写为 `auditor`，说明为“测试：临时确认”。
- 【事实】这 2 条是测试产物，**不能视为真实业务签认**，也不能视为已覆盖 7 条 `VIOLATION` 级结论。
- 【事实】`run.notes` 是自由文本，且**不会导出到 `manifest.json`**；因此只写 `run.notes` 无法让包接收方一眼识别。
- 【事实】包内能看到的相关字段只有：`conclusions_final.csv` 的 `confirmed_by` / `note`、`responsibility.json` 的 `confirmed_by` / `note`、`manifest.run_id`、`producer`。它们都没有“演练/真实”语义。

### 7.2 建议的区分方法（【建议】，系统未强制）

| 层次 | 做法 | 包内可见性 | 强度 |
|---|---|---|---|
| 账号命名 | 演练账号统一 `drill-<角色>`；真实账号按 HR/法务名册编号 | `confirmed_by` 可见 | 中 |
| 说明前缀 | 演练确认的 `note` 以 `[DRILL]` 开头 | `conclusions_final.csv` 与 `responsibility.json` 可见 | 中 |
| 数据库隔离 | 演练只用一次性临时库（名称含 `drill`），不连活动库 | 包外 | 强 |
| 目录隔离 | 演练包放独立目录，不进入交付目录 | 包外 | 强 |
| 台账标记 | 交付记录/凭证台账标注 `DRILL` 或 `PRODUCTION` | 包外 | 强 |
| 交付前检查 | 断言 `confirmed_by` 不在授权名册内即拒收；出现 `auditor` / `drill-` 即拒收 | 包外 | 强 |

### 7.3 交付前“一眼识别”检查清单（【建议】）

1. 打开 `conclusions_final.csv`，逐行看 `confirmed_by`：是否全部为授权名册中的真实账号。
2. 看 `note`：是否出现 `[DRILL]`、`测试`、`临时确认` 等字样。
3. 看 `manifest.run_id` 与包路径：是否来自演练库/演练目录。
4. 对照包外台账：该包是否登记为 `PRODUCTION`，是否有对应工单与凭证。
5. 任一项不符，**不得对外交付**。

### 7.4 局限（必须如实告知业务方）

- 以上全部是**约定**，不是系统强制；内部人员仍可把账号命名为 `auditor` 或在真实包中写 `[DRILL]`。
- 真正可靠的区分需要：账号治理 + 权限最小化 + 包外凭证 + 交付前双人检查 + 审计抽查。
- 若企业要求“机器可校验的演练标记”，需新增字段（如 `review_item.data_origin` 或 manifest 顶层标记），属于代码/schema 变更，列入 §9，不在本文范围。

### 11.3 与 `docs/操作手册.md` §5.1 逐字对照

修正前原文（`docs/操作手册.md` §5.1 第 4 条；已于 2026-11-09 按本节路径 A 改写）：

> 提交后写 `review.decision` 审计事件；`APPROVED` 的 finding 才进入对外结论集，未确认项保持 `unsigned_pending`。

#### 11.3.1 判定一：文档写错（主判定）

- 【事实】修正前原文断言“`APPROVED` 的 finding 才进入对外结论集”。
- 【实测】`REJECTED` 与 `NEEDS_MORE_DATA` 同样进入 `conclusions_final.csv`，同样把 `final_conclusions` 从 0 变成 1。
- 【判定】**这一句是文档写错**：它把“只有 `APPROVED` 才进入”写成事实，但当前代码不是这样。该句已按 §11.5 路径 A 改写。

#### 11.3.2 判定二：不是代码计算错误（与判定一分开）

- 【事实】`_write_conclusions_csv()` 的注释写明“只收**已登记人工结论**的条目”，并在实现中选取 `status != OPEN` 的全部记录。
- 【事实】`responsibility_block()` 同样把 `status != OPEN` 的记录写入 `human_confirmations`。
- 【判定】代码在其自身定义下是**内部一致**的：它计算的是“已登记人工处置”的条数，不是“确认成立”的条数。没有发现算术错误、字段错配或漏写；因此**不属于代码计算错误**。
- 【边界】如果业务方要求“结论集只收 `APPROVED`”，那是**业务语义变更**，不是修 bug；需按 §11.5 路径 B 进入下一版本。

#### 11.3.3 判定三：命名与对外表述含糊（独立问题）

- 【事实】字段名 `final_conclusions`、CLI 文案“已确认结论 N 条”、包内 `CONFIDENCE.md` 的“已确认结论：N 条”，都容易被读成“确认成立的条数”。
- 【事实】实际语义是“已登记人工处置的条数”，包含 `REJECTED` 与 `NEEDS_MORE_DATA`。
- 【判定】这是**命名/文案层面的口径含糊**，不是计算错误，也不是单纯的文档错字；它会让读者把“处置过”误读为“确认成立”。应通过下一版本的字段与文案拆分解决，或在冻结期内用外部口径说明补足。

#### 11.3.4 补充核实：`signed` 字段名是否误导（独立问题）

- 【代码依据】`responsibility_block()` 中先取 `SELECT seq, actor, ts ... FROM audit_event WHERE action = 'evidence.sign' AND run_id = ?`，再写 `"signed": bool(signs)`。
- 【代码依据】`record_delivery_event()` 的注释明确写：“这不是密码学签名，也不提供签名信任根；`evidence.sign` 只表示‘谁登记了这次交付’。”
- 【实测】§11.2.1 阶段 1：只登记交付、没有任何决定，`human_confirmations=0`，`signed=true`。
- 【判定】`signed` 的真实含义是“本 run 存在至少一条交付登记事件”，**既不代表结论被认可，也不代表有人做过决定**；它也不是包的密码学签名（后者是 `manifest.signature`）。字段名 `signed` 会被读成“已签署/已确认”，属于误导性命名。
- 【建议】下一版本改名或拆分：`delivery_registered`（交付登记）与 `conclusions_approved`（确认成立数）；0.4.17 冻结期内不改代码，只在包外口径说明中解释。

### 11.4 影响面与接收方高估风险

| 受影响输出 | 实际行为（【事实】） | 对接收方的影响 |
|---|---|---|
| `conclusions_final.csv` 行数 | 三种决定都写一行 | 接收方若按行数统计，会把“否定/存疑”算成“已确认” |
| `manifest.counts.final_conclusions` | 三种决定都加 1 | 对外汇报的“已确认结论 N 条”会高估确认成立数 |
| `manifest.counts.unsigned_pending` | 任一决定都减 1 | “未确认”数量下降，但不代表结论被认可 |
| `responsibility.human_confirmations` | 三种决定都进入 | 责任区块看起来像“三条都被确认”，实际含否定/存疑 |
| `responsibility.human_confirmed_findings` | 三种决定都加 1 | 与上同 |
| `responsibility.signed` | 只随 `evidence.sign` 交付登记变化，与决定类型无关；可零确认时为 `true` | 接收方可能误读为“已签署/已确认”，实际只是交付登记 |
| CLI 输出 | `src/cli.py` 第 237、253、450 行按 `final_conclusions` 打印“已确认结论” | 运维与接收方直接读到高估数字 |
| 包内 `CONFIDENCE.md` | 导出时写入“已确认结论：N 条”（`src/evidence.py` 第 747 行） | 包内文档自带高估口径 |
| `verify` / `replay` 的 COUNTS 行 | 只核对行数与计数，不区分决定类型 | 校验会“通过”，但语义仍是“人工处置数” |

对外引用该数字的主要文档（【事实】）：

- `README.md`：第 167、169、266、343、344 行。
- `docs/操作手册.md`：第 348、466、467 行。
- `docs/交付与验收SOP.md`：第 226、368、382、516、533 行。
- `docs/口径声明.md`：第 75 行。
- `policies/口径声明-对外版.md`：第 8 行。
- `policies/CONFIDENCE.md`：第 13、25 行。

当前交付包是否已经高估（【事实】）：

- 现有交付包的 2 条确认均为 `APPROVED`（见 `docs/整改回应表.md` 第 56 行与相关实测记录），因此**当前 8 个交付包的“2 条已确认结论”没有实际高估**。

- 该风险不改变包字节、不影响验签与回放；它改变的是“数字的业务含义”。
