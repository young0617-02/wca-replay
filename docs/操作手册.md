## 1. 系统边界一页

### 1.1 做什么

- **工时合规裁决**：按员工主数据、排班、打卡、请假、出差、补卡等 CSV，运行确定性规则引擎，输出 `VIOLATION / REVIEW / DEFENSIBLE` 分级结论、条文依据与行级来源。
- **质量门禁**：导入阶段检查缺失列、空值、时间格式/时区、重复打卡、未来时间、员工/组织不存在等；拒绝行进入 `ingest_issue`，可反查原始文件与行号。
- **审批台账**：登记特殊工时批文、版本、范围与员工覆盖投影；发布后供 `REG-01` 读取，不改变员工申报工时制。
- **举证包**：导出结论明细、审计链快照、责任区块、未覆盖清单与自含输入；发行 wheel 的 `wca-verify`
  独立校验链、输入哈希、工件哈希、findings 反算摘要与签名（**不执行包内 `verify.py`**），`wca replay`
  可重导输入复算三元组。包内 `verify.py` 只是便利脚本，不是信任依据。
- **问答**：制度问答走检索 + 确定性事实；LLM 只做意图归类与叙述，不参与算术；默认 `stub` 离线。

### 1.2 不做什么

- **不产出应付金额**：引擎只输出小时数、倍数档位与分级；金额只能由 HR 负责人在复核台**具名人工录入**，且不是引擎输出。
- **不做违法定性**：只输出合规分级、条文依据、证据与未覆盖项，不判定“违法/不违法”。
- **不是全栈考勤系统**：没有排班/请假/出差审批流、没有考勤机/门禁/移动端接入；输入只来自 CSV。
- **不做外部审批工作流**：审批台账只有本项目内的草稿/发布/覆盖投影，无外部审批 HTTP API、消息通知或附件原件管理。

### 1.3 已知限制清单（L1–L18，共 18 条）

1. **L1 不产出金额**：不做工资/加班费应付计算；复核人手工录入的金额字段属于人工结论。
2. **L2 不做违法定性**：不输出违法认定或法律责任结论。
3. **L3 不是全栈考勤**：无排班/请假/出差审批流、无硬件终端接入，只处理 CSV。
4. **L4 规则包不自动切换**：默认 v5；v4 可回放，v6 为代码内可选路径；不自动选包或自动升级。
5. **L5 无 `auto` 写入方式**：当前只支持 `single` / `executemany` / `copy`，默认 `single`；`auto` 尚未实现，配置为 `auto` 会报“未知导入写入方式”。SQLite 上 `executemany/copy` 自动降级为 `single`。
6. **L6 规模无 SLA**：3,000 员工月是本机实测，不是性能承诺；百万行未测。
7. **L7 输入自含包 12 MiB 硬上限**：10.5 MiB 为 warning、11.5 MiB 为 critical（仍导出、需人工确认）；>12 MiB 拒绝，不分卷、不截断。
8. **L8 `--no-inputs` 包不能离线重放**：不含原始输入 CSV，接收方无法自行 `replay`。
9. **L9 `raw_file.row_count` 语义问题**：CSV 导入登记的是表头列数（如 `employee.csv` 为 8），不是数据行数；`input_fingerprint` 里的 `rows` 不能当数据行数使用。
10. **L10 QUAL-DUP 汇总形态**：同一员工同一文件重复超过阈值时存一条 summary；`quality_issues.csv` 不是逐行明细；混有其他质量问题的员工不汇总。
11. **L11 同 run 导出不等待**：并发第二个直接 409（“该 run 正在导出”）；SQLite 锁文件在进程崩溃后可能残留，需要人工清理。
12. **L12 只绑本机**：Web 只监听 `127.0.0.1:9763`，无 HTTPS/反向代理/多租户/SSO/API token；不要暴露到局域网或公网。
13. **L13 审批附件只登记哈希**：不保存原件；无外部审批 API/工作流/通知；网页 CSV 上限 1 MiB / 2,000 行。
14. **L14 云端 LLM 未验证**：默认 `stub`；云/Ollama 需要本地凭证，未做云轨验收；向量检索默认 BM25 降级。
15. **L15 合成/演示定位**：无生产运行记录、无真实个人信息；不能作为真实用工个案的法律意见。
16. **L16 临时空间无硬上限**：`punch_seen` 随唯一键行数线性增长（501,000 行实测约 80 MiB），无自动上限；需要监控。
17. **L17 导入期间不要改源文件**：哈希和解析是同一句柄的两遍读取；原地改写可能导致指纹与解析内容不一致。
18. **L18 同名文件换内容不自动清理旧事实**：幂等键是 `(rel_path, sha256)`；同 `rel_path` 但内容变化按新文件登记，旧 sha 的事实不会自动删除，需要新 `rel_path` 或单独清理流程（当前无自动替换命令）。

## 2. 首次部署

### 2.1 前置条件

| 项 | 要求 |
|---|---|
| Python | 3.12 |
| 依赖通道 | `uv`（`uv sync`，不使用 pip；`.venv` 里没有 pip） |
| 数据库 | PostgreSQL 18（试点推荐）；也可用 SQLite 离线 |
| PG 连接 | 本机 `127.0.0.1:5927`，用户 `root`，口令只放本地 `.env`；库名用**新库**，例如 `wca_pilot_20261103` |
| Web | `127.0.0.1:9763`，只绑本机 |
| 数据 | 合成演示或试点提供的 CSV；不要放真实个人数据到公开仓库 |

> 不要指向活动库 `wca_worktime`。同一项目要新建库；若名字已存在，换后缀（如 `wca_pilot_20261103_2`），不要覆盖原库。

### 2.2 安装与配置

```powershell
# 项目根目录
uv sync

# 复制配置模板（PowerShell）
Copy-Item .env.example .env
```

编辑 `.env`（示例，不要把真实口令写进 Git）：

```dotenv
WCA_DB_BACKEND=postgres
WCA_DATABASE_URL=postgresql://root:<本地口令>@127.0.0.1:5927/wca_pilot_20261103
WCA_DB_IDENTITY_PATH=var/db_target_pilot_20261103.json
WCA_RULE_PACK=rp-2026.11.gd-pilot-standard.v5
WCA_IMPORT_WRITE_MODE=single
WCA_IMPORT_BATCH_SIZE=5000
WCA_QUAL_DUP_AGGREGATE_THRESHOLD=20
WCA_REGION_CODE=440300
WCA_LLM_PROVIDER=stub
WCA_EMBEDDING_BACKEND=bm25
# Web 本机监听；TLS 相关开关默认关闭
WCA_HOST=127.0.0.1
WCA_HTTPS_MODE=false
WCA_HSTS=false
```

说明：
- `WCA_DATABASE_URL` 必须指向**新库**；`init` 会在库不存在时创建，已存在时复用。
- 口令只在本机 `.env`；`config/services.json`、日志与错误信息只显示脱敏目标。
- `WCA_REGION_CODE` 必须使用 `config/region_profile.json` 里已有的城市档；未建档城市会出 `SCOPE-04`，不要猜市名。
- 默认规则包 v5；改规则包要走版本/审计流程，本手册不建议直接改。
- `WCA_IMPORT_WRITE_MODE` 默认 `single`；**不要写 `auto`**（当前不支持）。
- `WCA_LLM_PROVIDER=stub` 可离线；云/Ollama 是可选轨道，需另行提供凭证。

### 2.3 初始化、导入与建库

```powershell
uv run python -m src.cli init
uv run python -m src.cli ingest --dir data/raw
uv run python -m src.cli kb
```

- `init`：建表/迁移、检查审计纪元。规则包版本来自 `.env` 的 `WCA_RULE_PACK`；**全新库的审计 genesis 在首次审计写入（首次导入或 check）时建立**；从旧 v4 链切到 v5 时，`init` 会按现有逻辑建立 epoch 并保留旧链。
- `ingest`：按固定文件名识别类型并导入；详见第 3 节。
- `kb`：构建制度知识库与检索索引；规则引用的条文 id 缺失时会返回非 0 并提示。
- 合成演示可先执行：
  ```powershell
  uv run python -m src.cli gen --seed 20260106
  ```
  该命令写 `data/raw`；试点请替换为试点 CSV。

### 2.4 建界面账号

账号必须绑定已导入的员工 `emp_id`：

```powershell
uv run python -m src.cli users --username ad1 --emp T-STD --roles AD --password "<口令>"
uv run python -m src.cli users --username au1 --emp T-CMP --roles AU --password "<口令>"
uv run python -m src.cli users --username op1 --emp T-STD --roles OP --password "<口令>"
uv run python -m src.cli users --username rv1 --emp T-STD --roles RV --password "<口令>"
```

- 口令在本机换成 scrypt 哈希写 `config/users.json`，再同步到库；仓库不存明文。
- 员工不存在时命令会拒绝并提示先导入 employee.csv。
- 角色可组合（如 `AD,RV`）；服务端按角色集合判定。

### 2.5 启动 Web（端口 9763）

```powershell
uv run python -m src.cli start --config config/services.json --only api
uv run python -m src.cli status --config config/services.json --json
```

浏览器打开：

```text
http://127.0.0.1:9763/login
```

停止：

```powershell
uv run python -m src.cli stop --config config/services.json
```

- 默认服务清单 `config/services.json` 的 `api` 端口是 **9763**，只绑 `127.0.0.1`。
- 服务启动前会预检 `fastapi`/`uvicorn`；缺失时先 `uv sync`。
- 不提供公网/局域网部署、HTTPS、反向代理或多租户配置。

Web 监听与传输相关配置（默认值见 `.env.example`）：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `WCA_HOST` | `127.0.0.1` | `src.api_server` 读取的进程环境变量；服务管理器的实际绑定以 `config/services.json` 的 `host` 为准（启动时注入同名变量），直接 `uvicorn` CLI 以 `--host` 为准。改成 `0.0.0.0`/局域网地址时，启动期会检查 `config/users.json` 与数据库 `app_user`；只要仍有账号能用 `wca-demo-*` 演示口令，就拒绝启动。回环地址保留演示流程。 |
| `WCA_HTTPS_MODE` | `false` | **反向代理终止 TLS 时必须显式设为 `true`**。设为 `true` 后，即使应用收到的请求 scheme 是 `http`，会话 Cookie 也会带 `Secure`；它不会改变 `scope["server"]` 的绑定判定，也不是“已启用 HTTPS”的证明。 |
| `WCA_HSTS` | `false` | 只有真实 HTTPS（`scheme=https`）且显式 `true` 才下发 `Strict-Transport-Security`；HTTP 部署保持 `false`，默认不加 `includeSubDomains`。 |

请求层演示口令闸门：

- 直接 `uvicorn src.api:app --host 0.0.0.0` 启动时，`create_app` 拿不到真实绑定地址；请求层以 **ASGI `scope["server"]`（服务端本地 socket 地址）**判定，非回环/通配绑定的每个请求都会复检配置与数据库 `app_user`。
- 命中演示口令 → **503** 且不提供服务；`scope["server"]` 缺失/非法、配置不可读、数据库不可读也按 503 失败关闭。
- **`Host` / `X-Forwarded-Host` 只写日志，不参与放行判断**；请求方伪造 `Host: 127.0.0.1` 不能绕过。`WCA_HTTPS_MODE` 也不会改变绑定判定。
- 反向代理无法通过请求头改变 `scope["server"]`，但如果代理从本机回环连入，`scope["server"]` 可能显示回环地址；公网/共享主机场景仍应先改掉演示口令，不能只依赖这道闸。
- 以后若要引入“可信代理”模式，必须先定义代理来源白名单并同步补测试，不能直接信任请求方可伪造的头。

### 2.6 SQLite 与 PostgreSQL 双后端

| 后端 | 配置 | 用途 / 限制 |
|---|---|---|
| SQLite | `WCA_DB_BACKEND=sqlite`，`WCA_DB_PATH=var/pilot_<stamp>.sqlite3` | 离线/单机演示；不需要 PG；批量写入请求会自动降级 `single` |
| PostgreSQL | `WCA_DB_BACKEND=postgres` + `WCA_DATABASE_URL` | 试点推荐；支持 `executemany/copy`，并发/审计/临时表链路按 PG 验证 |

- SQLite 下 `executemany/copy` 会输出一条 WARNING 并降级 `single`，不报错；结果与 `single` 一致。
- 不要用活动 SQLite 路径 `var/worktime.sqlite3` 做试点；用新文件名。

## 3. 数据导入规范

### 3.1 文件名与顺序

CLI `ingest` 只识别以下文件名（放在 `--dir` 目录）：

| 文件名 | kind |
|---|---|
| `org.csv` | org |
| `employee.csv` | employee |
| `schedule.csv` | schedule |
| `punch.csv` | punch |
| `leave.csv` | leave |
| `trip.csv` | trip |
| `correction.csv` | correction |

- 未识别文件名会被跳过并在 stderr 提示；不会自动猜类型。
- 导入顺序固定：`org → employee → schedule → punch → leave → trip → correction`；员工/组织未就绪时，相关行会按 `QUAL-EMP/QUAL-ORG` 处理。
- Web 导入在 `/` 页面上传，单文件上限 **4 MiB**（`MAX_UPLOAD_BYTES`）；CLI 本机导入没有这个 4 MiB 限制，但仍建议按试点规模分批。

### 3.2 CSV 字段

`*` 为必需列；其余为可选列（大小写按表头原样使用）。

| 文件 | 必需 / 可选字段 |
|---|---|
| `org.csv` | `org_id*`, `org_name*`, `parent_id` |
| `employee.csv` | `emp_id*`, `pseudonym*`, `job_code*`, `org_id*`, `region_code*`, `worktime_regime*`, `normal_hourly_cents*`, `contract_approved_flex` |
| `schedule.csv` | `emp_id*`, `work_date*`, `planned_start*`, `planned_end*`, `rest_minutes` |
| `punch.csv` | `emp_id*`, `event_ts*`, `punch_type*`, `device_id` |
| `leave.csv` | `emp_id*`, `leave_kind*`, `start_ts*`, `end_ts*`, `approved`, `paid` |
| `trip.csv` | `emp_id*`, `destination*`, `start_ts*`, `end_ts*` |
| `correction.csv` | `emp_id*`, `claimed_ts*`, `claimed_type*`, `reason*`, `approved` |

字段要点：
- 时间建议写成带时区的 ISO-8601，例如 `2025-09-02T09:00:00+08:00`；无时区标记会按北京时间补齐并留 `QUAL-TZ`（可申辩）。
- `punch_type` 支持 `in/out` 及常见中文写法（`上班/下班` 等）；无法识别时按 `unknown` 入库并要求复核。
- `worktime_regime` 只允许 `standard / comprehensive_monthly / comprehensive_quarterly / comprehensive_yearly / flexible`。
- `normal_hourly_cents` 必须是正整数（分）；这是导入/主数据字段，**不是引擎应付金额输出**。
- `employee` 的 `job_code` 会用于审批覆盖展开；`job_codes` 为空数组时展开 0 人。

### 3.3 编码与换行

- 编码：UTF-8，可带 BOM；读取时按 `utf-8-sig` 处理。
- 换行：LF / CRLF 均可；解析按 `\n` 分行（裸 `\r` 保留在字段内，行为与旧实现一致）。
- 非法 UTF-8 字节会被替换为 `U+FFFD` 并可能产生质量问题；不要用 GBK/Excel 私有编码保存后直接导入。
- 导入期间不要原地改写源文件（L17）。

### 3.4 重复行处理

| 场景 | 行为 |
|---|---|
| 同一文件内完全重复的打卡行 | 首次保留；后续行**拒收**，`rows_rejected` 增加，`QUAL-DUP`（`field_name='*'`） |
| 跨文件/改名重传同内容 | 内容唯一索引挡住二次入账；先入账行保留，后续行仍计 `rows_accepted`，但产生 `QUAL-DUP`（`field_name='(db-unique)'`） |
| 同一员工同一文件 `QUAL-DUP` 超过阈值 | 默认阈值 `WCA_QUAL_DUP_AGGREGATE_THRESHOLD=20`：存一条 summary，`detail` 含按天 `count`、前 3 个样本、前 5 个行号、`line_min/line_max` |
| `QUAL-DUP` 汇总后的结论 | 引擎按天展开 summary，`QUAL-01` 的 issue_count / 样本 / 行号与逐行存储一致；结论/指纹/摘要不变 |
| 阈值设为 0 | 关闭汇总，逐行存储 |
| 混有其他质量问题 | 该员工不汇总，保持逐行 QUAL-DUP；重复量很大时 issue 仍可能增长 |

- `quality_issues.csv` 对汇总组展示 summary 行，不是逐行明细（L10）。
- 汇总状态可从 `ingest_issue.detail` 的 `qual_dup_summary` 与 `days` 读取。

### 3.5 失败回滚与重跑

- 每个文件（`raw_file` 登记/purge + 派生行 + 质量记录 + 审计）在同一事务内；异常时 `punch`、`raw_file`、`punch_stage`/`punch_seen*`、`ingest_issue` 一并回滚。
- 同一 `(rel_path, sha256)` 文件重跑是幂等的：复用原 `file_id`，先清派生行再重插；`reimported=true`。
- 中断后重跑前确认源文件未被修改；同文件重跑的三元组应与正常导入一致。
- **不要**把“同名但内容不同”的文件直接当作重跑（L18）：新 sha 会登记为新文件，旧 sha 的事实不会自动删除。

### 3.6 批量写入模式（含 `auto` 说明）

| 模式 | 行为 | 适用 |
|---|---|---|
| `single`（默认） | 逐行校验/逐行 INSERT；内存与块无关 | SQLite / PG，默认 |
| `executemany` | 块内批量写临时 `punch_stage`，再统一 `INSERT ... ON CONFLICT` | 仅 PG |
| `copy` | 同 `executemany`，但用 `COPY ... FROM STDIN` 写 stage | 仅 PG |
| `auto` | **当前不存在**；不要配置，设置后会报未知写入方式 | — |

- `WCA_IMPORT_BATCH_SIZE` 默认 **5,000** 行/块，硬上限 **20,000**；超过会截断并 WARNING。
- SQLite 请求 `executemany/copy` 会自动降级 `single`，并输出 WARNING；CLI/网页响应/审计 payload 的 `write_mode`、`requested_write_mode`、`degraded_from`、`chunk_rows` 可见。
- 默认 **仍为 `single`**；不要为了让 COPY 生效而改默认值，除非走变更审批。
- 文件内重复检测使用 DB 临时唯一表 `punch_seen`；132,900 行约 21.8 MB、501,000 行约 84.0 MB 临时空间（实测，见 `docs/维护策略.md`）。

## 4. 审批台账使用流程

### 4.1 登录与角色

- 登录页 `/login`；账号来自 `config/users.json`（用第 2.4 节的 `users` 命令创建）。
- 登录后落地页：`OP/AD → /`；`RV → /review`；`AU → /approvals`；其他（EM）→ `/qa`。
- 审批台账角色：
  - **AD**：读 + 写（新建草稿、编辑 DRAFT、发布、CSV 批量导入）。
  - **AU**：只读（列表、详情、版本链、员工覆盖投影）；所有写入口服务端 403。
- 当前没有外部审批 HTTP API、审批工作流或消息通知（L13）。

### 4.2 新建草稿 → 编辑 → 发布

界面路径（AD）：

1. 打开 `/approvals`，点击“新建草稿”。
2. 打开 `/approvals/new`，填写：
   - `doc_no` 文号、`title` 标题、`issuer` 发文机关；
   - `regime` 工时制，审批台账只支持 `comprehensive_monthly / comprehensive_quarterly / comprehensive_yearly / flexible`，**不支持 standard**；
   - `version_no` 版本号（新批文从 1）；
   - `valid_from` / `valid_to` 生效期；
   - `job_codes`（JSON 数组字符串，例如 `["warehouse_shift"]`）；
   - `region_code`（员工所在城市码）；
   - `attachment_sha256`（附件哈希，不保存原件）；
   - `scope_type`（`employee` 或 `org`）、`scope_value`（员工 id 或组织 id，可逗号分隔多个）；
   - `change_note` 变更说明。
3. 提交后形成 `DRAFT` 版本；在 `/approvals/<doc_no>` 查看版本链。
4. 编辑草稿：`/approvals/<doc_no>/edit`；**只有 DRAFT 可编辑**，已发布/已替代版本改写会 409。
5. 发布：在详情页点击发布（或界面调用 `POST /api/approvals/<doc_no>/publish`）；发布前会做员工覆盖冲突检测，成功后生成 `employee_approval_coverage` 投影。
6. 查看覆盖：`/approvals/coverage?emp_id=<emp_id>`；未发布版本不会出现在覆盖投影里。

- 同一文号新增版本必须递增 `version_no`；不能覆盖已有版本。
- 发布冲突返回 **409**：通常是同一期间/员工已有已发布覆盖，或批文/版本状态不允许；需调整文号、版本、范围或期限，不能强行覆盖。

### 4.3 审批 CSV 批量导入（AD）

路径：`/approvals/import`。

- 表头字段：
  `doc_no,title,issuer,regime,version_no,valid_from,valid_to,job_codes,region_code,attachment_sha256,scope_type,scope_value,change_note`
- 同一 `doc_no + version_no` 可多行，每行一个 `scope_type/scope_value`；同一版本其他字段必须一致。
- 上限：**1 MiB / 2,000 行**；超过分别返回 **413 / 400**，明确拒绝，不截断、不分卷。
- 整批校验、整批提交；任一行失败不留半份数据。
- 发布仍要单独执行；导入只创建 DRAFT。

### 4.4 CSRF 与接口

- 所有会话写接口（导入/校验/复核/导出/问答/退出 + 审批四个入口）都要求 CSRF；唯一豁免是登录前 `POST /login`。
- 页面会通过 `wca_csrf` cookie 与 `<meta name="csrf-token">` 下发 token；界面自动带上。
- 直接调用接口时，带请求头 `X-CSRF-Token`（或 body `csrf_token`）；缺失/错误返回 **403**。
- 会话失效时先刷新页面/重新登录，再复制新 token；不要复用旧 token。

## 5. 校验与举证

### 5.1 复核台（OP 不能做，RV/AD 做）

1. 登录后打开 `/review`（RV/AD）；按 run、严重级、员工筛选待复核项。
2. 打开单条 finding，查看规则、条文、行级来源；选择复核结论：
   - `APPROVED`：确认现有解释/证据；
   - `REJECTED`：否定该条结论；
   - `NEEDS_MORE_DATA`：要求补证/继续核查。
3. 可填写复核说明；应付金额字段是**人工录入**的可选字段，引擎不产出金额（L1）。
4. 提交后写 `review.decision` 审计事件；`APPROVED` 的 finding 才进入对外结论集，未确认项保持 `unsigned_pending`。
5. 导出前建议先完成复核；没有人工结论时 `conclusions_final.csv` 为空，`findings.csv` 仍保留全部机器结论。

### 5.2 跑校验与异常报表

```powershell
uv run python -m src.cli check --start 2025-09-01 --end 2025-09-30 --notes "2025-09 月度校验"
# 只校验指定员工：
uv run python -m src.cli check --start 2025-09-01 --end 2025-09-30 --emp T-STD,T-CMP
```

- `--start/--end` 必填日期（默认值不代表试点范围）；`--emp` 逗号分隔；`--notes` 写入 run 记录。
- 输出包含 `run_id`、员工/天数、**发现（未签认）条数 / 已确认结论 0 条**、分级、输入指纹、
  发现摘要（conclusion_digest）、耗时。
- 生成异常报表：
  ```powershell
  uv run python -m src.cli report --run <run_id>
  ```
  默认输出到 `reports/异常报表-<run_id>.csv`（`WCA_REPORTS_DIR` 可改）。

### 5.3 导出自含举证包

```powershell
uv run python -m src.cli export --run <run_id> --record-delivery-as "HR负责人"
```

- 默认包含本次 run 引用的原始输入 CSV（自含包）；包路径通常是 `var/packages/<run_id>.zip`。
- `--record-delivery-as` 以 HR 负责人身份登记交付事件，向审计链追加 `evidence.sign`；**这不是密码学签名**，不改变结论。旧别名 `--sign-as` 仍可用，输出会标注迁移期旧别名。
- 只导出包、不打包输入：
  ```powershell
  uv run python -m src.cli export --run <run_id> --no-inputs
  ```
  该包不能离线 `replay`（L8）。
- 需要从“包内自洽”进入“可验签/公钥匹配”时，加 Ed25519 私钥导出 v3 签名包（见 5.5.2）；**公钥匹配不等于来源身份已核验**，来源身份需双方独立渠道核验 key_id：
  ```powershell
  uv run python -m src.cli export --run <run_id> --signing-key var/keys/ed25519.key
  ```
- 数据最小化：`responsibility.json` / `conclusions_final.csv` 不导出 `amount_cents_input`、`amount_entered_by`；库内与复核台保留金额/录入人。`question_log` 只导出本次 run 关联的问答，历史 NULL 行不导出。
- 受控裁剪（默认关）：`export --omit-fields leave:paid` 才裁剪 `leave.paid`；被裁字段写入 manifest 的 `omitted_fields`。当前仅支持该字段；投影字段会直接拒绝。
- 新版 manifest 增加 `producer` 版本指纹：`version`（`0.4.0`）、`commit`（完整 git commit）、`python`（导出时解释器）、`rule_pack_version`。它被 `manifest_checksum` 覆盖；v3 签名包因此间接受签。源码工作区按 `git rev-parse HEAD` 取值，发行 wheel 按构建时写入的 `src/_release_info.py` 取值。
- 升级/复核建议保留旧包：包的规则版本、输入指纹、结论摘要与审计链快照是历史证据；不要用新包覆盖旧包来“修补”历史。

### 5.4 独立验算：`wca-verify`（包内 `verify.py` 只是便利脚本）

**正式验收用发行 wheel 的 `wca-verify`**：它自己实现校验，**不执行**包内 `verify.py`。
包内 `verify.py` 只是解包后的便利脚本，不校验工件绑定与 findings 反算摘要，不能作为信任依据。

```powershell
# 在发行物目录安装 wheel + 锁定依赖后（见 docs/交付与验收SOP.md §5）
wca-verify var/packages/<run_id>.zip --public-key <固定公钥文件> --expect-anchor "<四/五段>" `
  --expect-package-sha256 <包SHA256> --expect-artifacts-digest <artifacts_digest>
```

- 期望输出含 `MANIFEST CHECKSUM OK`、`ARTIFACTS OK`、`VERIFY SCRIPT OK`、`FINDINGS DIGEST OK`、
  `COUNTS 发现（未签认）... / 已确认结论 ...`、`CHAIN OK`、`INPUTS DIGEST OK`、
  `SIGNATURE OK / pinned (key matches supplied pin; independent key_id verification not done)`、
  `PACKAGE SHA256 ... / external=OK`、`ANCHOR CHECK OK`、`RESULT OK`。
- **`RESULT OK` 门禁（0.4.0）**：必须同时有外部公钥 pin 命中、外部锚点通过、外部
  `--expect-package-sha256` 通过、外部 `--expect-artifacts-digest` 通过；缺一为
  `RESULT PARTIAL`（exit 2），不是完整验收；任一项不匹配为 `RESULT FAIL`（exit 1）。
  `--anchor-file <单包 anchor.json>` 可一次提供锚点、包 SHA 与 artifacts_digest，
  显式参数优先、文件兜底。
- **逐项状态**：每行独立标 `OK` / `FAIL` / `NOT CHECKED`。早退时未走到的检查标
  `NOT CHECKED（早退，尚未走到…）`，不会写成 FAIL；`ANCHOR NOT CHECKED` 不等于锚点不符。
  `ARTIFACTS DIGEST` 只打一行 `manifest-internal OK / external FAIL|OK|NOT CHECKED`；
  外部失败会同时给出 `expected=` 与 `actual=`。
- 包内 `verify.py` 被替换：`VERIFY SCRIPT FAIL`，独立验算器不会执行替换后的脚本。
- 额外文件（包根或 `inputs/` 未声明）：`EXTRA FILE FAIL`，失败关闭，没有放行开关。
- 工件逐文件哈希（`artifact_sha256`）与清单摘要（`artifacts_digest`）不一致：`ARTIFACT FAIL` /
  `ARTIFACT BINDING FAIL`。
- **不传 `--expect-anchor`**：输出 `ANCHOR NOT CHECKED` + `RESULT PARTIAL`（exit 2），
  不能当验收通过；`--expect-triple` 只是 legacy 比对，也不给 `RESULT OK`。
- `--expect-package-sha256` 只对 zip 有效；目录包传它按失败关闭。`--expect-artifacts-digest`
  比对 manifest 的包根工件清单摘要。
- 五段：最后一段是 `projection_fingerprint`，必须与包内相等；未裁剪包传五段会
  `ANCHOR FAIL 包内无 projection_fingerprint，第五段无法校验`。
- `manifest_checksum` 只防“字段被改但校验和未同步重算”，不是签名；`RESULT OK` 只表示内容检查与
  外部 pin/锚点/包 SHA/artifacts_digest 匹配，**不等于来源身份已核验**；来源身份需双方独立渠道核验
  `key_id` 并留存记录。
- 按 `manifest.schema` 分档：新 schema（`wca-evidence-package-v2` 及以后）缺少
  `manifest_checksum`/工件绑定字段会失败；v1 旧包只保留历史回放，独立验算器拒收。

包内便利脚本仍可解包后运行（仅作人工排查）：

```powershell
Expand-Archive var/packages/<run_id>.zip -DestinationPath var/verify-<run_id>
Set-Location var/verify-<run_id>
python verify.py --expect-anchor "<四/五段>"
```

它只证明**字节层**（逐文件哈希、`inputs_digest`、签名、结论集哈希），不跑引擎，也不校验工件绑定/发现反算摘要；
真正的独立验收以 `wca-verify` 为准。

- **交付时把锚点记录在包外**（邮件、台账、工单均可）：普通包记四段
  `schema_version,rule_pack_version,input_fingerprint,conclusion_digest`；裁剪包记五段
  （末尾加 `projection_fingerprint`）。同时记录 `package_sha256` 与 `artifacts_digest`。
- `--expect-triple` / `WCA_EXPECT_TRIPLE` 仍可用，但**不约束 schema**；若交付需要防“伪装成 v1 旧包”，必须用四/五段锚点。

### 5.5 `replay` 独立复算

```powershell
uv run python -m src.cli replay var/packages/<run_id>.zip
# 机器可读：
uv run python -m src.cli replay var/packages/<run_id>.zip --json
# 用交付时记录在包外的锚点做外部比对（普通包四段；裁剪包五段）：
uv run python -m src.cli replay var/packages/<run_id>.zip --expect-anchor 3,rp,...,<digest>[,<projection>]
# 等价环境变量：
$env:WCA_EXPECT_ANCHOR = "3,rp,...,<digest>[,<projection>]"
uv run python -m src.cli replay var/packages/<run_id>.zip
```

- 重放会解包 → 校验工件绑定/findings 反算摘要 → 在临时库重导输入 → 重跑引擎 → 比三元组；不会写活动库。
- 退出码 0 表示完整通过（pin + 锚点 + 外部包 SHA 均已通过）；1 表示无法重放/不一致；
  2 表示 `RESULT PARTIAL`（内容与重放通过，但缺外部 pin/锚点/包 SHA 之一，不能算完整验收）。
- 输出把 **发现（未签认）** 与 **已确认结论（包内）** 分开：findings 条数来自引擎重跑与 `findings.csv`；
  已确认结论只核对 `conclusions_final.csv` 行数与 manifest `counts.final_conclusions`，不重建人工确认。
- 传 `--expect-anchor` 时先比对 `schema_version` 与包内三元组；五段时再比 `projection_fingerprint`。
  锚点不符输出 `ANCHOR FAIL`；早退时输出 `ANCHOR NOT CHECKED（早退，尚未走到锚点校验）`，
  不把“没走到”写成“断裂”或“不符”。不传 `--expect-anchor` 时输出
  `ANCHOR NOT CHECKED（未传外部锚点）` + `RESULT PARTIAL`（exit 2）。
- `--expect-triple` 仍保留，但只比三元组、**不约束 schema**；它不给 `RESULT OK`，交付验收普通包用四段、裁剪包用五段。
- `--expect-package-sha256` / `--expect-artifacts-digest` 与 `wca-verify` 同义，不匹配失败关闭。
- `manifest_checksum` 不一致会以 `MANIFEST FAIL` 失败；新 schema 缺工件绑定字段直接失败；v1 旧包只保留历史回放。
- 包里没有输入（`--no-inputs`）时只能验证链/输入清单，不能复算。

### 5.5.1 交付验收：两条命令必须一起跑

- `wca-verify`：独立校验**包体完整性**（manifest 自校验和）、工件逐文件哈希/清单摘要、包内 `verify.py` 哈希、
  findings 反算 `conclusion_digest`、审计链、输入逐文件哈希、`inputs_digest`、签名，以及外部四/五段锚点/包 SHA/工件摘要；
  它**不执行包内代码**，也不重算引擎结论。
- `wca replay`：独立重导输入、重跑引擎，得到**实算三元组**、`projection_fingerprint` 与**发现（未签认）条数**，
  并与包内比对；裁剪包只要求投影指纹 + 结论摘要一致，`input_fingerprint` 会明确标记为“已变化/重新计算”。
- **只跑 `wca-verify`**：能证明包没被单点改写、工件绑定/发现摘要自洽、链/输入自洽、包内三元组与包外记录一致，
  但不能证明“这些结论是这批输入算出来的”。
- **只跑 `wca replay`**：能证明实算三元组一致，但不覆盖 manifest 自校验和、外部锚点与包体完整性。
- 因此交付验收必须 `wca-verify` + `wca replay` 两条一起跑；自校验和不是签名，能重算的人仍可让
  manifest 自洽。信任根包括包外四/五段锚点、包 SHA-256、`artifacts_digest` 与 Ed25519 外部 pin
  （防换签名者；见 5.5.2）。锚点里的 `schema_version` 必须与交付时记录一致，
  否则“伪装成 v1 旧包”的降级会被拦下。包内 `verify.py` 不是信任依据。

### 5.5.2 Ed25519 签名与外部公钥 pin（v3）

签名不替代 replay；它把“这份 manifest、`inputs/` 文件与链头由谁生成”变成接收方可用固定公钥验证的事实。

1. 生成密钥（私钥不进包、不覆盖）：

```powershell
uv run python -m src.cli keygen --out var/keys/ed25519.key --public-out var/keys/ed25519.pub
```

- 私钥是单行 Base64 seed；Windows 用 `icacls` 收紧到当前用户，POSIX 为 `0600`。
- 文件已存在时拒绝覆盖，必须显式 `--force`；公钥可公开，私钥不要提交/外发。
- `key_id` = `ed25519:` + 公钥 SHA-256。轮换时保留旧 `.pub`，旧包仍可用旧公钥验证。
- 私钥来源优先级：`export --signing-key <file>` > `WCA_SIGNING_KEY_FILE` > `WCA_SIGNING_KEY_B64`。

2. 导出签名包：

```powershell
uv run python -m src.cli export --run <run_id> --signing-key var/keys/ed25519.key --record-delivery-as "HR负责人"
```

- 有私钥时 schema 为 `wca-evidence-package-v3`，manifest 含 `signature`、
  `inputs_digest`、`conclusions_sha256` 与 `producer`；无私钥仍是 v2（新导出也带
  `producer`，但无签名）。`inputs_digest` 覆盖包根 `inputs/` 下实际所有文件
  （含 `inputs/manifest.json`）。
- Web `/api/export` 在服务端配置了私钥时同样导出 v3；响应新增 `signed`、
  `signature_key_id` 两个增量字段，既有字段语义不变。

3. 复核方验签（发行 wheel 的独立验算器）：

```powershell
wca-verify <包>.zip --public-key fixed.pub --expect-anchor "<四/五段>"
wca-verify <包>.zip --public-key old.pub --public-key new.pub --expect-anchor "<四/五段>"   # 轮换期
wca-verify <包>.zip --public-key fixed.pub --require-signature --expect-anchor "<四/五段>"
```

包内 `verify.py` 仍可解包后运行，但只是便利脚本，不是信任依据；正式验收用 `wca-verify`。

- `SIGNATURE OK / pinned (key matches supplied pin; independent key_id verification not done)`：只表示与供给公钥匹配；来源身份需独立渠道核验 key_id。
- `SIGNATURE OK / package self-check（NOT source trust）`：只证明包内自洽，**不证明来源**；不能当 pinned。
- `SIGNATURE FAIL`：签名无效、v3 缺签名、pin 不匹配、签名字段/Base64 非法或未安装 PyNaCl；
  一律非 0 退出，不降级成旧包路径。
- `ARTIFACTS OK/FAIL`：逐文件哈希 + `artifacts_digest` + `verify_script_sha256`；改
  `findings.csv` / `quality_issues.csv` / `input_files.csv` / `responsibility.json` /
  `not_covered.json` / `未覆盖清单.md` / `verify.py` 都会被拦下；额外文件 `EXTRA FILE FAIL`。
- `FINDINGS DIGEST OK/FAIL`：从 `findings.csv` 反算 `conclusion_digest`；即使同步重算工件哈希并重签，
  改 severity/摘要语义仍会失败。
- `INPUTS DIGEST OK`：重算 `inputs_digest` 与 `manifest.inputs_digest` 一致；
  `INPUTS FAIL`：换输入 CSV/只改 `inputs/manifest.json`/增删 `inputs/` 文件都会被拦下。
- `INPUTS SIGNED OK`：输入摘要与有效签名一致；`INPUTS SELF-CHECK OK`：只有包内自洽，不能当来源身份已核验。
- 不传 `--expect-anchor`：`ANCHOR NOT CHECKED` + `RESULT PARTIAL`（exit 2），不是完整验收。
- `PROJECTION FAIL`：`replay` 重算的规则字段投影与 `manifest.projection_fingerprint` 不一致（或包声明了 `omitted_fields` 却缺投影）；这是字段层失败，不能用旧 `input_fingerprint` 掩盖。
- `replay --public-key ... --require-signature` 语义相同；`--json` 结果新增
  `signature_present / signature_ok / signature_trust / signature_key_id / signature_reason`、
  `inputs_digest / inputs_digest_ok`、`projection_fingerprint / projection_ok / omitted_fields`、
  `producer / producer_ok / producer_reason`、`artifact / findings_binding`、
  `anchor_checked / partial`、`package_sha256_ok / artifacts_digest_ok`。
- `replay` 人类可读输出会打印“`导出代码：version=... commit=... python=... rule_pack=...`”。
  包内 `producer.version/commit/rule_pack_version` 与当前验算代码不一致时直接
  `PRODUCER FAIL`（失败关闭）；`producer.python` 只记录、不参与失败判定。没有 `producer`
  的旧包会打印“无法核对导出代码版本”，不能当成同版本已核对。
- 第三方不拿源码复算用发行物（`dist/wca-replay-<版本>/`），安装与版本核对步骤见
  `docs/交付与验收SOP.md` §5；该发行物包含 wheel、带哈希锁定清单、`SHA256SUMS`、
  `RELEASE.json` 与一页验收说明。

**签名能证明什么**：manifest 关键字段（schema/三元组/checksum，含输入摘要、工件逐文件哈希/清单摘要/
包内脚本哈希、投影指纹与结论集哈希）、`inputs/` 实际文件字节与审计链头由一个持有私钥的实体签过；
用包外固定公钥 pin 时，能识别换包或换签名者。
**不能证明什么**：结论本身正确（仍需 replay 复算）；不能防私钥持有人作恶；不能证明这些
输入能复算出签名中的结论摘要；不能防包外 pin 记录被同时改写；`inputs_digest` 只覆盖
包根 `inputs/` 下的文件，`inputs/` 之外的文件不属于输入证据。

### 5.6 三元组是什么、为什么要保留旧包

- **三元组** = `rule_pack_version` + `input_fingerprint` + `conclusion_digest`。
- `input_fingerprint` 由本次实际引用的输入文件集合（rel_path/sha256/rows/kind）与范围/口径参数计算；`conclusion_digest` 由结论规范字段计算。
- 同一个三元组重跑必须得到同一结论；换规则包、换范围、换输入文件都会改变三元组。
- 裁剪包另外使用 `projection_fingerprint` + `conclusion_digest` 判定；旧 `input_fingerprint` 会显示为“重新计算”，这是预期，不应当作旧包回归。
- 旧包用于历史举证与独立复算；发布新规则包/新代码后，旧包仍应按旧包内的版本取证，不能静默改判据。

### 5.7 导出预算与同 run 并发

- `10.5 MiB`：warning（接近上限，仍导出）。
- `11.5 MiB`：critical（接近硬上限，需人工确认，仍导出）。
- `12 MiB`：硬上限；超过直接拒绝，不截断、不分卷。
- 无输入需求可用 `--no-inputs` 规避输入预算，但不可 replay（L8）。
- 同一 run 已有导出在跑：第二个请求立即返回 **409 “该 run 正在导出”**；不要同时用两个终端导出同一 run。若使用 SQLite 且进程崩溃留下 `.export-*.lock`，确认没有导出进程后再清理锁文件。

### 5.8 包解包资源上限（zip 与目录两种形态）

`replay` 的 `unpacked` 对 zip 与已解压目录复用同一套 `ZipLimits`：

| 限额 | 默认值 | 说明 |
|---|---:|---|
| 条目数 | **256** | 文件 + 目录条目；真实 v6 包 17 条目，约 15×余量 |
| 单文件实际字节 | **32 MiB** | 真实包最大成员约 5.64 MiB；按实际读取字节计数 |
| 总实际字节 | **64 MiB** | 真实包解压合计约 16.56 MiB；按实际读取字节计数 |
| zip 压缩比 | **100:1** | 真实包最大约 32.31:1；仅 zip 形态检查 |
| 路径嵌套深度 | **8** | 当前布局 `inputs/<file>` 深度 2；留 6 层余量 |

- 目录形态不信任 `stat` 声称值：遍历时逐块读取文件内容并计数，同时拒绝**符号链接、Windows 重解析点、硬链接、设备/非普通文件**；不跟随链接到包外。
- 超限失败关闭，错误前缀可辨识：`TOO_MANY_ENTRIES` / `MEMBER_TOO_LARGE` / `TOTAL_TOO_LARGE` / `DEPTH_TOO_DEEP` / `SYMLINK_REJECTED` / `REPARSE_POINT_REJECTED` / `HARDLINK_REJECTED` / `NOT_REGULAR_FILE` / zip 的 `RATIO_TOO_HIGH`。
- 恰好等于上限放行，超过 1 字节即拒绝；失败不会 `yield` 部分包。
- 库调用可通过 `replay(..., limits=ZipLimits(...))` 调整；CLI 使用默认值，暂未暴露独立参数。
- `verify.py` 运行在**已解压目录**上，无法约束外部解压工具本身；不可信包仍应优先让 `replay` 处理 zip 形态。

## 7. 常见问题

**Q1：导出接近 12 MiB / 越过 10.5、11.5 怎么办？**
- <10.5 MiB：正常。
- 10.5–11.5 MiB：warning，导出照常；记录并关注包大小。
- 11.5–12 MiB：critical，导出照常但需人工确认/记录；不要把它当 SLA。
- >12 MiB：拒绝（`ValueError`/CLI 非 0），不截断、不分卷；只能减少输入（如 `--no-inputs`，但不可 replay）或另做数据治理。见 L7/L8。

**Q2：同一 run 导出返回 409 怎么办？**
- 说明另一个导出正在写同一 run 的 work/zip；等待其完成后再导出。当前实现不排队等待（L11）。
- 不要删除最终 zip 或锁文件来“抢跑”；先确认没有导出进程。SQLite 锁文件残留处理见 5.6。

**Q3：导入中断/进程崩溃后怎么重跑？**
- 同文件（同 `rel_path + sha256`）重跑是幂等的：会复用 `file_id`、清派生行再重插；事务回滚会清掉 `punch/raw_file/punch_stage/punch_seen*/ingest_issue`。
- 重跑前确认源文件没有被改写；同文件重跑的三元组应与正常导入一致。
- 不要用“同名但内容变了”的文件直接重跑（L18）。

**Q4：`raw_file.row_count` 为什么不是数据行数？**
- 当前 CSV 路径登记的是**表头列数**（例如 `employee.csv` 的 8），不是数据行数；`input_fingerprint` 的 `rows` 因此不能用于行数核对（L9）。这是已知旧问题，未在本轮修改；不要据此计算导入行数。

**Q5：为什么同一个员工重复导入后 `QUAL-DUP` 不是 132,900 条？**
- 超过阈值（默认 20）时按员工/文件汇总为 summary；`quality_issues.csv` 展示 summary 行，detail 里有按天 count/样本/行号；结论仍由引擎展开，保持 `QUAL-01` 计数/样本/行号一致（L10）。

**Q6：Web 上传/审批 CSV 的上限是什么？**
- 普通导入页面上传单文件 **4 MiB**；审批台账 CSV **1 MiB / 2,000 行**，超限分别 413/400，明确拒绝、不截断（L13）。
- CLI 本机 `ingest` 没有 4 MiB 前端上限，但仍受内存/临时空间约束。

**Q7：登录失败/账号看不到员工怎么办？**
- 账号必须绑定已导入的员工；先确认 `employee.csv` 已导入，再用 `uv run python -m src.cli users ...` 重建账号。
- 账号文件 `config/users.json` 缺失或为空时登录一律拒绝；不要手写明文口令。

**Q8：为什么默认写入是 `single`，能不能设 `auto`？**
- 当前实现只支持 `single/executemany/copy`；`auto` 未实现，设置会报错（L5）。
- SQLite 上 `executemany/copy` 会自动降级 `single` 并 WARNING；默认仍是 `single`。

**Q9：审批发布 409 是什么？**
- 同一期间/员工已有已发布覆盖，或版本/批文状态冲突；需要换文号、递增版本、调整范围/期限，不能覆盖历史。见 4.2。

**Q10：Web 能开放到局域网/公网吗？**
- 当前只绑 `127.0.0.1:9763`，没有 HTTPS/反向代理/SSO/API token；不支持直接开放（L12）。试点访问请用本机或受控跳板，不要改绑定。

### 8.3 维护与容量

- 监控指标（dead tuple、表大小、`temp_bytes`、autovacuum、人工 VACUUM 条件）见 **`docs/维护策略.md`**。
- 本手册不复制参数细节，也不修改数据库参数；不要直接套用建议值，按试点硬件与变更审批执行。
- 关键容量事实：`punch_seen` 501,000 行实测约 **80 MiB** 临时空间；132,900 行约 **21.8 MB**；百万行未测（L16）。

### 8.4 前端维护约定（模板 / CSP nonce）

- 所有 HTTP 响应经 `SecurityHeadersMiddleware` 下发 CSP：`script-src 'self' 'nonce-<每请求随机值>'`、`style-src 'self' 'nonce-<每请求随机值>'`，**不含 `unsafe-inline`**。
- **新增内联 `<script>` 或 `<style>` 必须带 `nonce="{{ csp_nonce }}"`**。`csp_nonce` 由 `src/web/routes.py` 的 `page()` 注入模板上下文，每个请求重新生成；漏写会被浏览器按 CSP 拦截。
- 外部脚本（`/static/app.js`）与外部样式表走 `'self'`，不需要 nonce；不要新增 `onclick` 等内联事件属性或 `style="..."` 内联样式属性，CSP 同样会拦截。
- 模板保持 Jinja2 默认 autoescape；不要用 `|safe`/`Markup` 渲染用户可控内容（上传文件名、审批文号、问答文本等）。
- 改动后至少跑 `tests/test_web_security_headers.py`（CSP 指令、nonce 是否出现、安全头覆盖页面与 401/403/404）；请求层 503 的安全头由 `tests/test_startup_guard.py` 覆盖。
