## 一、同文件重复“保留行”缺 `line_no`（P2）

### 实现（实测）

- `finding.evidence` 新增可选字段 `retained_refs`，值为被保留首次出现行的 `rel_path:line_no`；
  **不写入** `Finding.canonical()` 九字段，也不写入 `metric`。
- 数据来源是 punch 事实表按 `(emp_id, event_ts, punch_type, device_id)` 查首条，
  而非 `metric.sources`（后者只含重复行本身，不含被保留行）。
- `evidence_digest` 的 canonical 形式仅在原块出现 `retained_refs` 时才写该字段，
  因此**旧包重算 `evidence_digest` 不变**。
- 实测 engine-only：`findings.csv` 115 行中仅 1 行变化——
  `evidence_json` 由 `{}` 变为 `{"retained_refs": ["punch.csv:349"]}`；
  canonical 九字段逐行比对零差异。

### 验收（实测）

- `conclusion_digest = 5dc46558…`（与 0.4.8 相同）。
- `inputs_digest = aad527d1…`、`input_fingerprint = 8b3b54a0…`（与 0.4.8 相同）。
- `evidence_digest` / `artifacts_digest` 变化，见上表。
- 回归：`tests/test_round10_batch_semantics.py` 断言
  `finding.evidence == {"retained_refs": ["punch.csv:2"]}`，且
  `"retained_refs" not in finding.canonical()` 与 `not in canonical()["metric"]`。

### 推断/边界

- 同一文件内多条重复时，“保留行”定义为文件内最小行号；跨文件重复时沿用 0.4.5 的
  canonical 归属规则（按 `rel_path` 字典序）。
- 未改 `RULE-PACK.md` 的声明来“迁就”实现；选择改代码，因为举证要求就是可定位。

## 三、新建库不写 `rule_pack_epoch`（P3）

### 选择与理由

采用 **(a) 新库初始化即写入 epoch 记录**，而不是保留 `legacy`：

- 新库若没有纪元记录，旧包回放判断缺少“当时生效版本”的依据；
- `legacy` 只应描述**既有历史库**的迁移来源，不应成为新库的默认起点。

### 实现（实测）

- `_seed_genesis_epoch`：仅当库内**既无审计事件、也无任何纪元行**，且当前为 v5/v6 时写入：
  `rule_pack_version=<当前包>`、`prev_rule_pack_version='genesis'`、
  `activation_event_seq=0`、`segment_start_seq=1`、
  `segment_start_prev_hash=<genesis 哈希>`、`switched_at=<当前时刻 +08:00>`；
  同时写 `audit_genesis`。
- 不追加额外审计事件；首个 run 事件仍从 `seq=1`、`prev=genesis 哈希`开始，
  `verify_chain` 通过。
- PG 咨询锁 + 事务内二次检查，避免并发重复写。

### 实测回归与修正

- 带 PG 全量首轮出现 1 个失败：
  `test_postgres_v6_self_contained_package` 先用 v6 配置导入、再跑 v5 基线；
  新库首次使用已写 v6 genesis，v5 被 `set_genesis` 正确拒绝。
- 修正**测试前置顺序**（不是放宽拒绝逻辑）：改为 **v5 导入 + v5 基线 → v6 批文发布
  触发真实纪元切换 → v6 校验/导出**。该用例随后通过，PG 全量 613 passed / 2 skipped。
- 新增测试：`tests/test_evidence_epoch.py` 覆盖 genesis 字段与幂等、首个 run 事件入段且
  链校验通过。

### 推断/边界

- 新库“首次使用”包括首次导入；若先用 v6 导入，库即进入 v6 纪元，之后 v5 运行被拒绝，
  这是单一事实的预期行为，不是回归。

## 四、跨版本可比性（必须改）

### 五条落地（实测）

1. **可比性声明**：`README.md`、`docs/签名方案.md` §4.1、发行 README 模板均写明：
   摘要只在**同 `rule_pack_version` + 同 evidence schema** 下可比。
2. **`anchor.json` 增 `comparability_scope`**：顶层有定义/支持的 schema/版本集合；
   每个包条目各带 `{"rule_pack_version", "schema"}`。
3. **`INCOMPARABLE`（exit 3）**：`wca-verify`、`wca replay`、包内 `verify.py` 三处一致；
   同版本同 schema 摘要不符仍 `FAIL`（exit 1）；缺字段/缺签名仍失败关闭。
   退出码为 `0 OK / 1 FAIL / 2 PARTIAL / 3 INCOMPARABLE`。
4. **旧锚点按版本命名、不覆盖**：本轮单包锚点为 `anchor-0.4.9-<role>.json`；
   0.4.8 的 `anchor.json` 原样保留，并复制为 `anchor-0.4.8.json` 供对照（`OLD-ANCHORS.md`）。
5. **`PRODUCER FAIL` ≠ 篡改**：`README.md`、交接 README/KEY-NOTE 写明新版 wheel 验旧包会先
   `PRODUCER FAIL` 并早退签名检查，应改用对应版本旧 wheel。

### 三情形测试（实测，`tests/test_anchor_projection.py` / `test_manifest_anchor.py`）

| 情形 | 期望 | 实测 |
| --- | --- | --- |
| 同版本同 schema、摘要不符 | `FAIL` / exit 1 | `test_same_version_digest_mismatch_still_fails` 通过；干净 venv 故意传错 `evidence_digest` → `RESULT FAIL` exit 1 |
| 跨版本或跨 schema | `INCOMPARABLE` / exit 3 | `test_cross_version_anchor_is_incomparable_not_fail` 通过；`test_disguised_v1_triple_passes_but_anchor_fails` 断言 schema 降级 exit 3；干净 venv 用 v6 锚点验 v5 包 → `RESULT INCOMPARABLE` exit 3 |
| 缺字段/缺签名 | 按原规则失败关闭 | `test_new_schema_missing_checksum_fails_closed`、`test_missing_schema_fails_closed`、`test_unknown_schema_fails_closed` 通过；缺外部 `artifacts_digest` → `RESULT PARTIAL` exit 2，不放宽 |

### `PRODUCER FAIL` 实测

干净 venv（仅 0.4.9 wheel）验 0.4.8 `engine-only.zip`：返回非零并报 `PRODUCER FAIL`，
签名检查早退为 `SIGNATURE NOT CHECKED`。这不是篡改，也不是验签失败。

### 推断/边界

- `INCOMPARABLE` 只在**基础检查（链/工件/输入/签名）全部通过**时输出；
  基础检查失败仍 `FAIL`，不会因引入新分档而放宽任何真失败。
- 四段锚点（不含 projection fingerprint）行为保持原样；五段锚点仅在版本/schema 不一致时
  转 `INCOMPARABLE`。

### 审计方复算 `batch_id` 入口

对任一重复批次 finding，取其 `metric.sources` 的 `rel_path:line_no` 集合，按 UTF-8
字节序排序后以 `\n` 拼接再算 SHA-256：

```python
import hashlib, json
texts = sorted({f"{s['rel_path']}:{s['line_no']}" for s in metric["sources"]},
               key=lambda t: t.encode("utf-8"))
assert hashlib.sha256("\n".join(texts).encode("utf-8")).hexdigest() == metric["batch_id"]
```
