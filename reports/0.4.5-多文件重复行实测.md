# 0.4.5 多文件重复行实测与修复

- 日期：2026-11-04
- 代码提交：`8ca8a0e44ec597865b92745842c71f3a2565bdc4`（本地提交，未 push）
- 发行物：`dist/wca-replay-0.4.5/`（7 文件 361,131 字节）
- 交接包：`handoff/20261104-第七轮整改/`（22 文件 695,411 字节；`交付清单.txt` 覆盖 21 个非自身文件 / 693,258 字节）
- 测试：离线 **549 passed / 8 skipped / 1 deselected**；带 PG **572 passed / 1 skipped / 1 deselected**

## 0. 结论

1. **跨文件重复行确实会破坏摘要可复现性。** 同一行内容同时出现在 `punch-a.csv` 与
   `punch-b.csv`，按 a→b 与 b→a 导入，修前 `conclusion_digest` 不同
   （`c08b25ea…` vs `53769e3e…`），`QUAL-01` 的 `line_refs` 分别在
   `punch-b.csv:2` 与 `punch-a.csv:2`。
2. 已修：重复行归属按 `(rel_path,line_no)` 字典序确定 canonical 引用，全部来源写入
   `detail` 并纳入包内输入；两种顺序实测四联值全部相同，`line_refs` 都是
   `punch-a.csv:2`。
3. **单 `punch.csv` 的 0.4.4 四联值没有变化**，仍是
   `b9cc6fd0… / 01cb5aeb… / aad527d1… / 8b3b54a0…`，由测试与 0.4.5 四包实测双重守住。
4. `source_refs` 的 DB `file_id` 已评估，**本轮未改**；建议推迟到独立变更，理由见 §5。

## 1. 测量场景

```
punch-a.csv:  DUP（09:00 in, DEV-DUP）+ OUT（18:00 out, DEV-DUP）
punch-b.csv:  DUP（与 punch-a 的 DUP 逐字节相同）
schedule.csv: E-DUP 2025-09-02 09:00–18:00，休息 60 分钟
data/raw 其余文件不参与本测量
```

- 两次独立建库：`a-then-b`（a 先 b 后）与 `b-then-a`（b 先 a 后）。
- 两次均导出完整签名包，读 `manifest.triple`、`evidence_digest`、`inputs_digest`、
  `findings.csv` 的 `metric_json` 与 `quality_issues.csv`。
- 测量脚本：`var/measure_cross_file_dup.py`（不入库，仅本地复现用）。

### 1.1 第一次尝试：只放重复行，未复现

只用 `punch-a.csv=[DUP]`、`punch-b.csv=[DUP]`（没有 out 卡）时：

```
a-then-b: conclusion 3a9980b3d4155e8d11df1b5f310aa0d4fa1847596d80efb6e27df21a0380bd4a
b-then-a: conclusion 3a9980b3d4155e8d11df1b5f310aa0d4fa1847596d80efb6e27df21a0380bd4a
QUAL-01 metric: {"day_type":"workday","minutes_worked":0,"punch_count":1}
quality_issues.csv rel_path: punch-b.csv / punch-a.csv
```

两包结论相同，**但 QUAL-01 的 metric 没有 `line_refs`**：该日只有一张 in 卡，
`rule_scope` 先产出 QUAL-01（PUNCH-MISSING，metric 是 punch_count/minutes_worked），
`rule_quality` 同日同规则、同 severity 的 QUAL-01 在 `_dedupe_findings` 中被先到者覆盖。
所以这个最小场景只能证明 `quality_issues.csv` 的 `rel_path` 翻转，**不能证明
`conclusion_digest` 翻转**。要测到 canonical，必须让当天打卡闭合（有 out 卡），
使 QUAL-01 由 `rule_quality` 产出。

### 1.2 第二次尝试：补 out 卡，复现

修前（同一测量脚本，`punch-a.csv=[DUP, OUT]`、`punch-b.csv=[DUP]`）：

| 顺序 | conclusion_digest | evidence_digest | inputs_digest | input_fingerprint | QUAL-01 line_refs |

| a→b | `c08b25ea9c8b7bbd260a1952322acb44e8392c499a6e5a9be60586902ceb26c9` | `a1ac2359c43acab71037a57408d8d0875e4d21dc32fec11b29580df49002279a` | `d9ce53ae0007b3b1454f8d2020bc95feffc284b8fb0e7c71fd8b2de889be94c3` | `1a408f43d4b2b10cdc4dec12dd5cb0b5c46e317b94edbea6c00a6897de0755f2` | `[{"rel_path":"punch-b.csv","line_no":2}]` |
| b→a | `53769e3e040b5d042183389e428fce2e07560c6f7a90f40625546aa7e188ae1e` | 同上 | 同上 | 同上 | `[{"rel_path":"punch-a.csv","line_no":2}]` |

`quality_issues.csv` 的 `rel_path` 也分别是 `punch-b.csv` 与 `punch-a.csv`。
这说明：**`input_fingerprint` 与 `inputs_digest` 相同，仍不足以说明结论稳定；
`QUAL-01` 的 `line_refs` 在 canonical 内翻转，`conclusion_digest` 随之改变。**

修后（0.4.5）：

| 顺序 | conclusion_digest | evidence_digest | inputs_digest | input_fingerprint | QUAL-01 line_refs |
|---|---|---|---|---|---|
| a→b | `53769e3e040b5d042183389e428fce2e07560c6f7a90f40625546aa7e188ae1e` | `a1ac2359c43acab71037a57408d8d0875e4d21dc32fec11b29580df49002279a` | `d9ce53ae0007b3b1454f8d2020bc95feffc284b8fb0e7c71fd8b2de889be94c3` | `1a408f43d4b2b10cdc4dec12dd5cb0b5c46e317b94edbea6c00a6897de0755f2` | `[{"rel_path":"punch-a.csv","line_no":2}]` |

`quality_issues.csv` 两包都是 `punch-a.csv:2`；`detail` 保留两个来源，例如
`来源: punch-a.csv:2, punch-b.csv:2（按 rel_path 字典序取首个为行级引用）`，
并带 `related_file_ids=4,5`。本场景没有 QUAL-02（没有整行拒收）。

### 1.3 超过汇总阈值（>20）的路径

用 25 个不同时间的重复 in + 1 个 out，两个文件内容相同，触发
`qual_dup_aggregate_threshold=20` 的汇总路径。修前中间态曾出现：

- a→b `conclusion_digest=d65073bd3c8caebdc48b01557b6694208baf305ecfcaa604597673e2da2fc0a8`
  且 `quality_issues.csv` 同时有 26 条逐行 QUAL-DUP 与 1 条汇总；
- b→a `conclusion_digest=a22ed9fb75fa606a973af156de398098e8b6bb4592d0bd905fd093481551e71c`。

根因：canonical 引用把逐行 issue 的 `file_id` 改成了另一个来源文件，
但旧删除逻辑仍按“当前导入文件 id”删除，导致汇总没删掉逐行行。已改为按
`_DupGroup.canonical_file_ids` 删除；测试
`test_cross_file_duplicate_aggregate_import_order_stable` 现在两种顺序同摘要。

## 2. 修法与取舍

选择“按 `rel_path` 字典序确定唯一归属”，理由：

- 只改重复行归属，不改“重复行只保留一条事实”的业务语义；
- `line_refs` 仍是单个 `rel_path+line_no`，与 0.4.4 的字段结构一致，
  下游 `FINDING DIGEST`/`replay` 不需要新格式；
- 全部来源写进 `detail`，人工仍可看到另一个文件；
- 单文件/单来源场景不触发该路径，四联值不受影响。

实现点：

- `src/ingest.py::_duplicate_punch_issue`：查已存在 punch 行，取
  `(rel_path,line_no)` 排序后的第一个作为 canonical；`file_id_override`
  写入 `ingest_issue`，`related_file_ids` 记录全部来源；
- `_DupGroup`：聚合时按 canonical refs 排序；删除按 canonical file ids，
  不按当前导入文件 id；
- `src/engine.py::_issue_related_file_ids`：从 `detail` 解析全部来源文件，
  加入 `referenced_files`，使 `input_fingerprint` 与 `inputs_digest` 同时包含两个 punch 文件；
- `related_file_ids` 只用于输入选择，不进入 `Finding.canonical()`。

## 5. `source_refs` 的 DB `file_id`：评估（本轮不改）

### 5.1 先纠正一个事实

**0.4.4/0.4.5 的 `findings.csv` 不包含 `source_refs` 字段。** 实测列头是：

```
rule_id, rule_version, emp_id, work_date, period_key, severity, severity_label,
citations, metric_json, evidence_json, source_rel_path, source_line_no, explanation
```

`file_id` 不在 `findings.csv`；`source_rel_path` 和 `source_line_no` 已经是相对路径与行号。
DB `finding.source_refs`（JSON）和 Web 视图里仍有 `file_id`。

### 5.2 客户可见位置

| 位置 | 是否含 DB `file_id` | 说明 |
|---|---|---|
| `findings.csv` | **否** | 只有 `source_rel_path/source_line_no` |
| `quality_issues.csv` | **否** | 列为 `rel_path/line_no/...` |
| Web 异常表 | **是** | `src/web/templates/index.html` 显示 `ref.file_id:line_no` |
| Web 质量问题表 | **是** | 模板直接显示 `i.file_id` |
| Web API JSON（若直接序列化 anomaly） | **是** | `AnomalyItem.source_refs` 含 `file_id`；需另行确认路由是否返回 |
| DB / 内部查询 | 是 | 行级反查、输入选择、审计定位 |

所以如果目标是“客户可见处不出现 DB ID”，**优先改展示层**（模板两处 + 路由输出裁剪），
不必重设计 DB 存储。

### 5.3 若彻底把 `source_refs` 改成 `rel_path+line_no`

改动范围（按现有调用链）：

| 文件 | 改动 |
|---|---|
| `src/rules/dayfacts.py` | 5 处 `source_refs` 构造：punch/correction/plan/leave/trip；已持有 `file_paths`，可加 `rel_path` |
| `src/engine.py` | `_dedupe_refs`、`_unattributed_findings`；`referenced_files` 改为按 `rel_path` 找 `file_id`（否则 `input_fingerprint` 可能漏文件） |
| `src/rules/rulepack.py` | `_merge_refs`（COMP-C01）按 `rel_path` 去重排序 |
| `src/anomaly.py` | `_with_rel_path` 改为直接读 `rel_path`；输出可不再带 `file_id` |
| `src/evidence.py` | `_source_loc` 优先 `rel_path`；`findings.csv` 输出预计不变 |
| `src/schema.sql` / `src/projection.py` | 注释/字段口径说明同步 |
| `src/web/templates/index.html` | 显示 `rel_path`（本来就有 `ref.rel_path`） |
| `tests/` | `test_ingest_quality.py` 的 `ref["file_id"]` 断言、`test_rules_v5.py` 的手工 `source_refs` fixture、anomaly/web 用例需同步 |

### 5.4 影响判断

- **对 `artifacts_digest`**：`findings.csv` 只输出 `source_rel_path/source_line_no`，
  如果 rel_path 映射不变，工件字节预计不变；但这只是推算，**必须重建包实测**才能确认，
  不能先写“无影响”。
- **对 `input_fingerprint`/`inputs_digest`**：若只删 `file_id` 而不做 rel_path→file_id 映射，
  会漏掉输入文件，四联值会变；必须保留映射或同时保留 `file_id`。
- **对行级反查链**：DB `source_refs -> raw_file.file_id` 是单值精确链；改成 `rel_path` 后，
  需用 `(rel_path, sha256)` 或 `(rel_path,line_no)` 反查。`raw_file` 允许同 `rel_path` 不同
  sha，单靠 `rel_path+line_no` 不保证唯一，链的正确性会变弱。
- **测试代价**：至少 5–8 处 fixture/断言改动，需重跑全量离线+PG，并重建四包比对四联值；
  不是“小改动”。

### 5.5 推荐

1. **0.4.5 不动 DB `source_refs`**。它不进 canonical、不影响四联值；`findings.csv` 已无 ID。
2. 若审计方要求客户可见处去 ID，先做**展示层修复**（Web 模板显示 `ref.rel_path`、
   `rel_path` 列替代 `file_id`；API 输出裁剪），这是低风险改动，可放 0.4.6。
3. 若要彻底移除 DB `source_refs.file_id`，另开变更，保留兼容读取旧 `file_id` 的路径，
   并明确 `input_fingerprint`、行级反查唯一性与旧包回放边界；不要和 0.4.5 混在一起。

## 7. `confirmed` 包 `artifacts_digest` 0.4.4→0.4.5 差异（实测）

### 7.1 现象与逐文件比对

| 项 | 0.4.4 confirmed | 0.4.5 confirmed |
|---|---|---|
| run | `run-20261104T084900-a6515ca8` | `run-20261104T092915-565b941e` |
| 包字节 | 73,787 | 73,791 |
| `artifacts_digest` | `cc125430548ec5f1fa6881f2e95199d73013434a8274b7c9107360a261fcb3ce` | `fcbeb0efd2a22517e3603ac2b23fffc478d6e4adf5b0c36b6cdf43ff9aed7cf7` |

`artifact_sha256` 的 14 个 key 完全相同；逐文件对照后，**只有两个文件字节不同**，
其余 12 个（含 `findings.csv`、`quality_issues.csv`、`input_files.csv`、
`policies/CONFIDENCE.md`、`未覆盖清单.md`、`not_covered.json`、README/verify/policies）
全部相同。

| 文件 | 旧 sha256 | 新 sha256 | 字节差 | 具体差异 |
|---|---|---|---|---|
| `conclusions_final.csv` | `7c0574284785bce5af928668666ed6a94412db388e8485b062d9d8d8b8ba7409` | `489ae7d3248b494b56949abce0dad38cfcd606b4152d4ac22881f200f4fff13a` | 0（339→339） | 两行 `confirmed_at` 从 `2026-11-04T08:49:00.731414+08:00 / .726783` 变为 `09:29:15.807816 / .806713` |
| `responsibility.json` | `e44b124fa5a19e4746e1f71f454d2e6347c53eb6a245b99ed5698df7331a82e9` | `c541d18cf2af3e5afe3cbe678b03e6016bdee06d40069616ae9987e6f2a69d71` | 0（2924→2924） | `human_confirmations[0/1].confirmed_at` 与 `signed_by[0].ts` 随确认/交付事件时间变化 |

`policies/CONFIDENCE.md` 两包同哈希 `d42e3f69…0b3d`，**不是计数渲染漂移**；
`findings.csv` 同哈希 `f63a0967…e380`，**不是重复行修复波及**。

### 7.2 成因

- `conclusions_final.csv` 的 `confirmed_at` 来自 `review_item.decided_at`，是人工确认时的
  真实时间戳（`decide_review` 写入）；
- `responsibility.json` 的 `human_confirmations[].confirmed_at` 同源；
  `signed_by[0].ts` 来自交付登记事件（`record_delivery_event`）；
- 0.4.4 与 0.4.5 confirmed 是**两次独立建库/独立确认**，时间戳必然不同；
- 0.4.5 的重复行修复只改 `QUAL-DUP` 归属和输入选择，未改确认记录、`CONFIDENCE.md` 计数
  或其他 12 个工件；`findings.csv` 哈希相同就是直接证据。

### 7.3 是否“每次导出都不同”？——不是

同一 run、同一 DB、**连续导出两次**（脚本 `var/measure_confirmed_stability.py`）：

```
RUN run-20261104T092915-565b941e
FIRST  artifacts_digest fcbeb0efd2a22517e3603ac2b23fffc478d6e4adf5b0c36b6cdf43ff9aed7cf7
SECOND artifacts_digest fcbeb0efd2a22517e3603ac2b23fffc478d6e4adf5b0c36b6cdf43ff9aed7cf7
SAME artifacts_digest True
SAME signature False
SAME zip sha False
```

- `artifacts_digest` 与 `artifact_sha256` 两次完全相同；
- 但 manifest 的 `audit_window.max_seq` 从 13→16、`chain_verification.head_hash` 变化，
  `manifest_checksum`/`signature_b64`/包 SHA 随之变化：**导出本身会追加审计事件**，
  这是包 SHA 每次导出不同的原因，不是 `artifacts_digest` 漂移；
- 同一 run 已确认后再次对同一 `review_id` 调 `decide_review` 被拒绝
  （`已有复核结论，不得覆盖`），拒绝后重导 `artifacts_digest` 仍为 `fcbeb0ef…`。

### 7.4 结论与边界

- `confirmed` 的 `artifacts_digest` **在同一 run 内可复现**；跨独立 run 会因真实确认/交付
  时间戳变化而不同。这不是 0.4.5 重复行修复的副作用，也不是“每次导出都漂移”。
- 外部锚定必须按包记录：`artifacts_digest` 随该 run 的确认事件确定；不能把 0.4.4 的
  `cc125430…` 跨 run 复用到 0.4.5，也不能期望两次独立人工确认得到同一 artifacts。
- 如果验收方要求“跨独立确认 run 的 confirmed artifacts_digest 也相同”，只能把
  `confirmed_at`/`signed_by.ts` 从工件中移除或规范化——这会丢失真实确认时间证据，
  属于语义变更，本轮未做，需另行确认。
- 新增测试：同 run 两次导出 `artifacts_digest` 稳定；同一 review 重复确认被拒绝后
  `artifacts_digest` 稳定（`tests/test_evidence_digest.py` 两项）。
