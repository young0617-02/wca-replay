## 3. 高危

### H-01 举证包与审计链可被整体伪造，`verify.py` 仍输出 `CHAIN OK`

**级别：高**
**引入情况：既有**（`VERIFY_SNIPPET` 在 `HEAD` 中已存在；本次改动新增审批台账输入，但没有改变“只做自洽校验”的信任模型）

**位置**

- `src/evidence.py:93-98`：`entry_hash = sha256(prev|seq|actor|action|ts|payload_sha256)`，公式完全公开，不含密钥/HMAC/签名。
- `src/evidence.py:236-255`：`append_audit` 只追加 hash 链；`GENESES` 是固定常量。
- `src/evidence.py:972-1039`：`manifest` 由导出方填写；`manifest_sha256` 在写完 `manifest.json` **之后**才计算，且只放进函数返回值，未写回包内 manifest。
- `src/evidence.py:1044-1052`：zip 内写入 `manifest.json`、`audit_chain.jsonl`、`verify.py`。
- `src/evidence.py:1120-1188`：`verify.py` 从 manifest 自带的 `engine_version` / `triple` / `audit_segment` 推导 genesis；只校验链内哈希自洽和 `inputs/manifest.json` 中登记的文件哈希；不检查 `manifest_sha256`、不比对独立可信三元组、不检查事件数/`run_id`。
- `src/schema.sql:275-288`：`audit_event` 没有签名/HMAC 列；`evidence_package.manifest_sha256` 只是数据库内的一列，可被同权限写者改写（`src/schema.sql:303-313`）。

**已证实的利用条件**

- 攻击者能生成或替换一个举证包（例如作为外部提交方发来一个包），或能写 `audit_event` / `rule_pack_epoch` / `meta`。
- 不需要数据库口令、服务器私钥或任何项目密钥。

**影响**

- 只改一条事件会被链校验发现；但攻击者可以从任意伪造的 genesis/segment 起点**重算整条链**，`verify.py` 会输出 `CHAIN OK`。我在内存中按同一公式伪造了 2 条事件（任意 `engine_version`、`triple`、`actor`），校验结果为 `True`。
- 现有包 `var/v6-3000/packages/run-20261102T225122-b335a25d.zip` 的 `manifest.json` 不含 `manifest_sha256`；包内 `verify.py` 不含 `manifest_sha256` 检查，也不含 `expected_triple` 检查。
- 因此“链与输入哈希一致说明包没被改写”“不可篡改审计日志”的对外承诺，在恶意包作者/恶意写库者面前不成立；它只能证明“自洽”，不能证明“来源可信”。

**修复建议**

1. 引入非对称签名（如 Ed25519）：导出时对 `manifest.json` + 链头 + `inputs/manifest.json` 的统一摘要签名；私钥放在数据库/仓库之外；`verify.py` 内置公钥并强制验签。
2. `manifest.json` 内增加 `manifest_sha256`、`chain_head`、`signature`、`key_id`；`verify.py` 强制校验签名、事件数/`run_id` 与 manifest 一致；拒绝“空 inputs 仍 OK”。
3. 把链头发布到外部只追加存储或可信时间戳服务，否则只能称“自洽哈希链”，不能称“不可篡改”。
4. 更新 `PACKAGE_README` 与 README 的措辞，明确威胁模型：能发现无意修改，不能抵御拥有写权限的攻击者。
5. 若短期不做签名，至少在 manifest 中写 `trust_model: self-consistency-only`，并在 `verify.py` 输出中明确“未验签”。

## 5. 低危

### L-01 `POST /login` 无 CSRF/无速率限制

- **位置**：`src/web/routes.py:141-169`。
- **已证实**：登录 POST 从 urlencoded 表单取用户名/口令，直接 `start_session`；没有 Origin/Referer 校验，也没有失败计数/锁定/限速。
- **影响**：登录 CSRF（攻击者诱导受害者登录攻击者账号）与口令暴力/资源消耗；当前绑定 `127.0.0.1`、账号数少、scrypt 有成本，风险有限。
- **建议**：校验 `Origin`/`Referer` 或使用登录页一次性 token；按 IP/账号做失败限速；对 `start_session` 的 scrypt 计算做并发限制。

### L-02 无防框架/安全响应头；会话 Cookie 无 `Secure`

- **位置**：`src/web/routes.py:104-120,167-168`；`src/api.py:225-230` 只挂静态目录与 Web 路由，没有安全头中间件。
- **已证实（补充动态，§10.3）**：临时 SQLite 库 + 端口 19763 启动后，`curl` 取 `/login`（200）与 `/`（401）响应头；两者只有 `server: uvicorn`、`date`、`content-length`、`content-type`，**未设置** `X-Frame-Options`、`Content-Security-Policy: frame-ancestors`、`X-Content-Type-Options`、`Referrer-Policy`、HSTS。
- **静态已证实**：`set_cookie` 只有 `httponly=True, samesite="strict"`，没有 `secure=True`（`src/web/routes.py:118,167`）。
- **影响**：AD 的“发布审批/导出”按钮可能被第三方页面 iframe 点击劫持；若服务通过 HTTP 暴露，会话 Cookie 可被嗅探；缺少 `nosniff`/Referrer 策略增加 MIME 混淆与 Referer 泄露面。点击劫持在真实浏览器/PNA 下是否可利用列在 P-04。
- **建议**：加 `X-Frame-Options: DENY` 或 CSP；HTTPS 部署时 `secure=True`、考虑 `__Host-` 前缀；加 `X-Content-Type-Options: nosniff`、`Referrer-Policy`、`Cache-Control: no-store`（敏感页面）。

### L-03 改口令不撤销旧会话

- **位置**：`src/auth.py:111-115` 更新 `pw_hash`/`roles`，但没有删除该用户的 `app_session`；`end_session` 仅删除当前 token（`src/auth.py:229-235`）。
- **影响**：管理员改口令/降权后，旧会话最长仍可用 120 分钟（`SESSION_TTL_MINUTES=120`，`src/auth.py:33`）；降权角色在下次请求会重新读取，但口令失效不会即时生效。
- **建议**：口令/角色变更时删除该用户全部 `app_session` 与 `app_csrf`，或给账号加 `session_epoch` 并在 `resolve_session` 校验。

### L-04 状态变更 GET（`/qa`、`/ask`）无 CSRF

- **位置**：`src/web/routes.py:522-527` 的 `GET /qa` 调用 `_ask`；`src/api.py:147-186` 的 `GET /ask` 调用 `agent.ask`；`agent._persist` 会写 `question_log`、`span`、可能 `review_item`、`audit_event`（`src/agent.py:309-352`）。
- **已证实**：这些 GET 不需要 CSRF token；第三方页面可用 `<img>`/`<iframe>` 触发带 `q` 的请求，造成日志/复核单/审计事件写入。
- **影响**：观测表污染、日志膨胀、资源消耗；不是业务数据写入。
- **建议**：把有副作用的问答改为 POST + CSRF，或把日志写入拆到独立异步事件并加频率限制；文档不要把它列为“纯读接口”。

### L-05 上传 JSON 先解析后限额；主 CSV 无行数上限；`csv.Error` 未兜底

- **位置**：`src/web/routes.py:207-224`（`body: dict` 由 FastAPI 先完整解析，随后才检查 `len(text.encode()) > 4MB`）；`src/web/routes.py:480-513` 审批 CSV 也是先解析 JSON 再查 1MiB/2000 行。
- **已证实**：主 CSV 只有 4MiB 字节上限，没有行数上限；`src/ingest.py:215` 的 `csv.DictReader` 在遇到 `csv` 字段超限（默认 128KiB）时抛 `csv.Error`，`_ingest_rows` 的 `chunk = list(islice(...))` 不在 per-row try 内，路由只捕获 `ValueError`，会 500。
- **影响**：已登录 OP/AD 可用超大 JSON 触发内存消耗；4MiB 单字段可触发未捕获异常；主 CSV 行数无上限会放大 CPU/DB 负载。
- **建议**：在读取 body 前限制 `Content-Length`/流式读取；主 CSV 增加行数上限（与审批一致或明确更高）；捕获 `csv.Error` 并返回 400；对 `content` 字段大小做前置校验。

### L-06 校验区间、问题长度、审批字段无上限

- **位置**：`src/web/routes.py:243-257` 只解析 `start/end` 不限制跨度；`src/engine.py:201-239` 对区间内每天每员工计算；`src/web/routes.py:522-536` 与 `src/api.py:150` 的问题只校验非空；审批 `title/issuer/doc_no/note` 无长度上限。
- **影响**：已登录 OP/RV/AD 可发起超长区间校验或超长问题/审批字段，造成 CPU/DB/存储消耗；属于认证用户 DoS 面。
- **建议**：限制最大区间（如 366 天）、员工数、问题长度（如 2,000 字符）、审批字段长度；超限返回 400。

### L-07 `Config.raw`/`repr` 含云 API key（当前无落盘路径）

- **位置**：`src/config.py:23` 的 `_DB_SECRET_KEYS` 只过滤 `WCA_DATABASE_URL`/`WCA_TEST_POSTGRES_URL`；`src/config.py:193` 的 `raw_values` 因此仍含 `WCA_CLOUD_API_KEY`；`src/config.py:141` 的 `cloud_api_key` 没有 `repr=False`。
- **已证实**：用假 key 做内存验证，`repr(cfg)` 与 `cfg.raw` 都包含该值；`src/service_cli.py:49` 把 `app_cfg.raw` 传给 `ServiceManager`。

### L-08 错误信息回显服务器路径；审批详情未捕获 `ValueError` 导致 500

- **位置**：`src/api.py:207-210` 在包文件缺失时把 `zip_path` 放进 410 detail；`src/web/routes.py:322` 的 `/api/export` 返回 `package_zip`（服务器路径）；`src/web/routes.py:403-410` 的 `/approvals/{doc_no}` 与 `/edit` 直接调用 `version_chain`，后者在批文不存在时抛 `ValueError`（`src/rules/approval_docs.py:533-538`），路由未捕获，返回 500 并写 uvicorn 堆栈日志。

### L-09 `verify.py` 对空 inputs 打印 `INPUTS OK`

- **位置**：`src/evidence.py:1170-1186`。
- **已证实**：`bad=[]` 且 `checked=0` 时，`print("INPUTS", "OK" if not bad else "FAIL", ...)` 会输出 `INPUTS OK checked=0 packed=0`；`--no-inputs` 导出仍会写 `inputs/manifest.json`（`src/evidence.py:937-957`），因此会走到这里。

- `uv 0.11.31` 在 `%TEMP%\wca-security-review-20261103\audit-venv` 创建隔离 venv；安装 `pip-audit 2.10.1`。
- 用 `uv export --frozen --format requirements.txt --all-groups --no-hashes --no-emit-project -o %TEMP%\...\requirements.txt` 从 `uv.lock` 导出 **27 个锁定依赖**；`--frozen` 不更新 `uv.lock`。
- 执行 `pip-audit -r %TEMP%\...\requirements.txt --no-deps --format json -o %TEMP%\...\pip-audit.json`；退出码 **1**（有发现），并输出 `Found 3 known vulnerabilities in 2 packages`。
- 原始 JSON 保留在 `%TEMP%\wca-security-review-20261103\pip-audit.json`（15,542 字节）。

**实际发现（唯一记录 2 条；JSON 中 `certifi` 重复，合计 3 条记录）**

| 包 | 版本 | Advisory | 可用修复版本 |
|---|---|---|---|
| `certifi` | `2026.7.22` | `PYSEC-2026-4320` / `GHSA-6q48-6c7w-9gw2` | `2026.10.18`（公告描述建议 `2026.10.19+`） |
| `opentelemetry-api` | `1.45.0` | `CVE-2026-114603` / `GHSA-xcq7-p3pf-p88h` | `1.45.1` |

**影响与可达性判断**

- `certifi` 由 `httpx`/`httpcore` 传递；CVE 涉及 eMudhra/emSign 根证书，需要攻击者持有已泄露 CA 私钥且位于 TLS 链上。源码中未发现 `import httpx` 的直接调用；项目云调用走 `urllib`（系统 CA），因此当前实际 TLS 暴露面有限，但依赖确实存在于锁定集合。
- `opentelemetry-api` 由 `fastapi` 传递；源码中未发现 `opentelemetry` 导入。CVE 需要 OTel ASGI instrumentation/默认传播器处理超长 `tracestate` 头；uvicorn 默认 `h11` 对头部有 16 KiB 限制，当前未见直接可达路径。
- 结论：**依赖风险从“人工目测无高风险”升级为“2 个唯一 CVE 已证实存在”**；由于未升级、未启用到相关调用面，实际可利用性有限，但不能标记为“无风险”。这是新增 **M-07**。

### 10.2 路径穿越（M-03 动态证实）

**构造方式**

- 包目录/zip：`%TEMP%\wca-security-review-20261103\pkg_relative`、`pkg_relative.zip`、`pkg_absolute`、`pkg_unc`；包内 `verify.py` 取自现有举证包（只读复制）。
- 包外目标文件：`%TEMP%\wca-security-review-20261103\outside_org.csv`（内容 `org_id,org_name` + 1 行，43 字节，sha256 `e0fac355...`）。
- `inputs/manifest.json` 的 `arcname` 分别设为：
  - 相对上级：`..\outside_org.csv`；
  - 绝对路径：`%TEMP%\wca-security-review-20261103\outside_org.csv`；
  - UNC：`\\127.0.0.1\wca-no-such-share\outside_org.csv`。
- 三个包的 `manifest.json` 均为伪造但自洽的 v5 三元组，`audit_chain.jsonl` 为空；这同时复现 H-01 的“空链也能 OK”。

**实际观察**

| 场景 | 工具 | 实际输出 | 结果 |
|---|---|---|---|
| 相对 `..\outside_org.csv` | `python verify.py`（cwd=pkg_relative） | `EPOCH OK` / `CHAIN OK events=0` / `INPUTS OK checked=1 packed=1`；RC=0 | **读取了包外文件**，sha256 与包外一致 |
| 绝对路径 | `python verify.py`（cwd=pkg_absolute） | 同上，RC=0 | **读取了包外文件** |
| 相对/绝对 | `python -m src.cli replay <目录> --json` | `imports` 出现 `rel_path=outside_org.csv`、`rows_seen=1`、`sha256=e0fac355...`；`ok=false`（伪造三元组不一致） | **读取并导入包外文件**；导入行被拒（`accepted=0`） |
| zip 相对 | `python -m src.cli replay <pkg_relative.zip> --json` | `imports` 中 `sha256` 为 `%TEMP%\outside_org.csv` 的哈希 `f1c287ff...`；`rows_seen=1` | **zip 解包后仍读取包外文件** |
| UNC | `python verify.py`（cwd=pkg_unc，20s 超时） | `INPUTS FAIL checked=0 packed=1`，`BAD \\127.0.0.1\wca-no-such-share\outside_org.csv (缺失)`；RC=0 | 未读到 UNC 目标；未观察到网络认证/凭据泄露 |

**结论**

- M-03 由“代码可证实”升级为 **动态证实**：相对/绝对 `arcname` 都能让 `verify.py`/`replay` 打开包目录之外的文件；`replay` 会将其导入临时库；`verify.py` 只算哈希、不回显内容。
- UNC 仅得到“缺失”，**不能证伪也不能证实** NTLM 泄露/中继；P-03 保留待验证。
- `verify.py` 在 `INPUTS FAIL` 情况下仍返回 0，是新增 **M-06**。

### 10.3 浏览器侧响应头（L-02 动态确认）

- 用临时 SQLite 库 `%TEMP%\wca-security-review-20261103\headers.sqlite3`、端口 `19763`、host `127.0.0.1` 启动 `python -m src.api_server`；停止文件 `%TEMP%\...\headers-run\api.stop` 触发优雅退出；日志显示连接 opened 3 / closed 3、`WAL checkpoint=ok`。
- `curl` 实测：
  - `GET /login` → `HTTP/1.1 200 OK`，响应头只有 `date`、`server: uvicorn`、`content-length`、`content-type`。
  - `GET /`（未登录）→ `HTTP/1.1 401 Unauthorized`，响应头同样只有上述四项。
- 因此确认缺失：
  - `X-Frame-Options`
  - `Content-Security-Policy: frame-ancestors`
  - `X-Content-Type-Options`
  - `Referrer-Policy`
  - `Strict-Transport-Security`（本服务 HTTP；仅在 HTTPS 场景有意义）
  - `Set-Cookie` 上的 `Secure`（静态代码：`src/web/routes.py:118,167` 未设置）
- 影响：AD 的发布/导出动作存在点击劫持面；缺少 `nosniff`/Referrer 策略；`server: uvicorn` 暴露服务软件。P-06 的浏览器/PNA 实际可利用性仍未实测。

### 10.4 多租户 IDOR（P-04，原报告 P-01）

- 当前文档明确不做多租户：`README.md:197`、`docs/项目定义-一页.md:61,66`、`docs/操作手册.md:52,163`。
