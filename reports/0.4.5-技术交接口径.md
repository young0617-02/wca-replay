## 1. 本轮验收判据（稳定性不变量）

**不要求** `conclusion_digest` 等于任何历史值。验收判据是：

1. 同一批 CSV、同一规则包、同一扫描范围，**换新库重导** → 四联值相同；
2. 同一批 CSV、同一规则包，**punch 与 schedule 反向导入顺序** → 四联值相同；
3. 同一批 CSV、同一规则包，**跨库重导** → 四联值相同；
4. 单 `punch.csv` 场景的四联值保持 0.4.4 的
   `b9cc6fd0… / 01cb5aeb… / aad527d1… / 8b3b54a0…` 不变。

四联值定义：

```text
conclusion_digest  = Finding.canonical() 九字段的 SHA-256
evidence_digest    = 全部 finding.evidence 的规范化 SHA-256
inputs_digest      = 包内 inputs/ 实际文件字节的 SHA-256
input_fingerprint  = 输入文件内容/范围/规则参数的 SHA-256
```

历史值 `01bd4403…` 属于仍含 DB `file_id` 的 0.4.3 及更早包，**旧包不回改、旧签名仍有效，
但不得把旧摘要当成本轮验收目标**。0.4.4 已记录该纪元变更；0.4.5 不重新定义它。

## 2. 本轮修了什么

### 2.1 多文件 punch 重复行

同一行打卡内容同时出现在 `punch-a.csv` 与 `punch-b.csv` 时：

- 修前：`QUAL-DUP` 只保留“后导入文件的幸存行”，`line_refs` 随导入顺序在
  `punch-b.csv:2` / `punch-a.csv:2` 间翻转，`conclusion_digest` 不同；
- 修后：按 `(rel_path,line_no)` 字典序确定 canonical 引用；全部来源写进 `detail`，
  两个 punch 文件都纳入包内输入；
- 结果：a→b 与 b→a 的 `conclusion_digest`/`evidence_digest`/`inputs_digest`/
  `input_fingerprint` 全部相同，`line_refs` 都是 `punch-a.csv:2`。

复现：

```powershell
uv run python var/measure_cross_file_dup.py
```

脚本构造两个 punch CSV（同一行逐字节相同 + 一个唯一 out 卡），分别按 a→b / b→a
建库导包，输出两包四联值与 QUAL-01 `line_refs`。实测细节见
`reports/0.4.5-多文件重复行实测.md`。

## 4. `source_refs` 的 DB `file_id`（只评估，未动代码）

- **事实**：0.4.4/0.4.5 `findings.csv` **不含** `source_refs`；列头只有
  `source_rel_path/source_line_no`。因此“客户手里的 findings.csv 出现 file_id”这一前提
  对当前版本不成立。
- 仍出现 DB ID 的客户可见位置：Web 异常表与质量问题表（模板显示 `file_id`）。
- 若只需客户可见处去 ID，优先改展示层（模板显示 `rel_path`、API 裁剪），低风险。
- 若要彻底改 DB `source_refs` 为 `rel_path+line_no`：涉及 `dayfacts`/`engine`/
  `rulepack`/`anomaly`/`evidence`/Web/测试，且 `raw_file` 允许同 `rel_path` 不同 sha，
  单靠 `rel_path+line_no` 会削弱行级反查唯一性；`input_fingerprint` 需额外
  rel_path→file_id 映射，否则会漏输入。**推荐另开变更，不并入 0.4.5。**
- `artifacts_digest` 是否变化必须重建包实测，不能先断言无影响。

## 5. `confirmed` 的 `artifacts_digest` 跨版本差异（已解释；详见实测报告 §7）

0.4.4 confirmed `artifacts_digest=cc125430…`，0.4.5 `fcbeb0ef…`，包 73,787→73,791 字节。
逐文件比对 14 个 `artifact_sha256`：**只有两个成员变化**：

| 文件 | 旧 sha256 | 新 sha256 | 差异 |
|---|---|---|---|
| `conclusions_final.csv` | `7c057428…ba7409` | `489ae7d3…fff13a` | 两行 `confirmed_at` 时间戳 |
| `responsibility.json` | `e44b124f…1a82e9` | `c541d18c…a69d71` | `human_confirmations[].confirmed_at`、`signed_by[0].ts` |

其余 12 个同哈希，包括 `policies/CONFIDENCE.md`、`findings.csv`、`quality_issues.csv`、
`未覆盖清单.md`、`not_covered.json`、`input_files.csv` 与全部 policies。
所以不是本轮重复行修复的副作用，也不是计数渲染漂移；是两个独立 run 的真实确认/交付
时间戳不同。

同一 run 连续导出两次：`artifacts_digest` 与逐文件哈希稳定；但导出会追加审计事件，
`audit_window.max_seq`、`chain_verification.head_hash`、`manifest_checksum`、签名与包 SHA
会变（这是包 SHA 每次导出不同的原因，不是 `artifacts_digest` 漂移）。同一 review 重复确认
被 `decide_review` 拒绝，拒绝后 artifacts 仍稳定。新增测试覆盖这两点。

**边界**：若要求“两次独立人工确认 run”的 confirmed artifacts 也相同，只能移除或规范化
`confirmed_at`/`signed_by.ts`，会丢失真实确认时间证据，属语义变更，本轮未做，需另行确认。
外部锚定必须按 run 记录 confirmed 的 artifacts，不能跨 run 复用 `cc125430…`。
