# 0.4.15 文档事实单一来源（机制整改报告）

本报告说明第四轮盲验 14 条问题为何不能靠继续改句子收敛，以及 0.4.15 用哪三个机制、
哪些测试与生成器来防止复发。**本报告的事实以产物与测试为准**；本文只做索引，不复制
计数与哈希（唯一计数口径见 `round17-techcheck.txt`）。

## 一、根因

同一事实（文件数、哈希、四联摘要、包清单、目录层级、门禁条数）被手写在多处。抄写者
知道答案，就不会去核实物；逐句修补只会把错误搬到另一处。四轮盲验均未收敛，因此本轮
不再逐句改，而是让事实只有一个来源：**程序从产物算**，文档只承载生成区。

## 二、三个机制

| 机制 | 实现 | 生成/校验方式 |
| --- | --- | --- |
| 1 事实由程序生成 | `scripts/docfacts.py` 只读产物；`scripts/build_release.py` 填发行 README §0；`scripts/build_handoff.py` 填交接 README/包表/清单/旧物/章节号/目录 | 生成区用 `<!-- GENERATED:START key -->` / `<!-- GENERATED:END key -->` 标记；`tests/test_doc_facts_guard.py` 反向核对 |
| 2 示例命令必须真跑 | `tests/test_doc_commands.py` 抽取 `docs/` 与 README 的 ```powershell 命令，逐条执行 | 断言退出码与 `RESULT OK/PARTIAL/FAIL/INCOMPARABLE` 标签；OK/rc=0 命令必须给全五项门禁 |
| 3 什么变了由 diff 生成 | `scripts/diff_packages.py` 逐 zip 成员比字节，逐字段分类 | 输出逐包逐文件表 + 三类原因（版本号文本/真实时间戳/文档与派生哈希） |

锚点 JSON、`SHA256SUMS` 与实际文件字节。

## 五、护栏覆盖不到什么（诚实回答）

如果下一轮盲验仍查出“文档与实物不符”，最可能来自以下位置，而不是本轮已生成的区域：

1. **生成区之外的散文结论**。本轮把“表格、清单、章节号、哈希”变成了生成区，但 README
   的 §十二“可独立复现边界”、§一“结论”、`docs/安全与证据链现状.md` 的叙述性判断仍是人写的。
   它们与生成表今天一致，但不是从产物推导；只要引擎行为或规则包语义变化，就会重新漂移。
2. **中文数词与定性表述**。护栏只审阿拉伯数字；“五项”“八包”“两把钥”这类中文数词不在
   比对范围，写错不会被抓。
3. **语义正确性，而非事实一致性**。测试能证明“这条命令确实 exit 0”，但不能证明文档对该命令
   **为什么**成立的解释是对的（例如 `NOT CHECKED` 与 `SKIPPED` 的适用条件、`PRODUCER FAIL`
   与篡改的区别）。
4. **历史声明**。0.4.1–0.4.2 曾是四项门禁、旧 wheel 不做 scope 判定等历史事实，无法从当前
   产物验证，只能靠人工记忆；护栏对这类“当时如此”的句子没有证据源。
5. **护栏自身的白名单与豁免**。数字审计跳过归档 `reports/`、剥离反引号路径、登记了一批
   常量（如 18/40/8601/0600）；哈希审计对 `requirements*.lock.txt` 跳过。任何一条豁免都可能
   被误用成新的藏身处。
6. **生成区被手工改过但恰好与事实相符**。护栏验证“值对不对”，不验证“这一行是不是生成器写的”。
7. **非 .md/.txt 载体**。JSON、`.ps1`、`.sig` 与二进制不在文本护栏内；它们只能靠各自的结构校验。

下一轮若要进一步收敛，优先把 §一/§十二与安全文档的判断句也改成“由测试结论引用”，而不是
继续手写结论；同时把中文数词纳入生成区。
