## 二、A5：包内 CSV 不再含 DB 主键

### 2.1 问题与根因（实测）

0.4.5 为修跨文件重复行，把“全部来源”的 DB `file_id` 写进 `ingest_issue.detail`
（`related_file_ids=4,5`）；`evidence.py` 导出 `quality_issues.csv` 时原样带出，
因此 README 的“包内不含 `file_id`”声明与交付事实冲突。

### 2.2 修复（实测）

- 新增 `src/package_inputs.py: redact_issue_detail`：对 detail 做 JSON 解析或正则剥离，
  删除 `related_file_ids`，保留 `来源: a/punch.csv:2, b/punch.csv:2` 的可读形式。
- `src/evidence.py` 只在**导出** `quality_issues.csv` 时调用清洗；`ingest_issue.detail`
  在库内保持原值，继续用于跨文件重复的输入选择。
- 包内不再出现任何 DB 主键，包括 `quality_issues.csv`、`findings.csv`、`anomaly` 列表等。

### 2.3 验证（实测）

- 八个交付包逐 CSV 扫描：`file_id`/`related_file_ids`/`run_id`/`segment_id`
  作为**数据值**出现 0 次；仅 README 类说明文字可出现这些词。
- `dup-subdir-a-then-b` 的 `quality_issues.csv` 实际内容：
  `来源: a/punch.csv:2, b/punch.csv:2`（两份包内 CSV 的真实相对路径 + 行号）。
- 测试覆盖两条路径：扫描全部包 CSV；单独断言 detail 的清洗结果不含 `related_file_ids`。

### 2.4 README 口径统一（实测）

第八轮 README L30 与 L124–125 相互矛盾（前者说“不含 `file_id`”，后者说“`source_refs`
仍保留 `file_id`”）。第九轮统一为：

> 包内所有 CSV 的**数据值**不含 `file_id`/`related_file_ids`/`run_id`/`segment_id`；
> 这些列仅保留在数据库中用于输入选择与行级反查，**不进入任何导出工件**。

该声明不是凭愿望书写：本轮以实际八个包扫描验证，结果见 §2.3，并在 README 中注明
“本轮口径取代第六/七/八轮 README 的旧表述（旧 handoff 不改写）”。

## 四、A13：导入期 `rel_path` 契约

### 4.1 决策（选择“拒绝”，不是“允许 cwd 外”）

理由：举证包的 `inputs/` 需要按 `rel_path` 原样重建；若允许 cwd 外输入而又不丢目录段，
就必须引入“相对哪个根”的额外约定，跨操作系统/跨机器无法稳定还原，反而制造新的
不可验证路径。因此选择**明确拒绝**：凡会丢失目录信息的路径一律非零退出、中文报错。

### 4.2 实测（本地复现，退出码均为 2）

| 输入 | 报错（节选） |
| --- | --- |
| `--dir ../outside/data` | 导入路径不允许包含 `..`（无法在包内还原）：../outside/data；请把文件放在当前工作目录内，用相对路径导入 |
| `--dir C:\outside\data` | 导入路径不允许绝对路径（无法在包内还原）：C:\outside\data；请使用当前工作目录内的相对路径，或 cd 到数据根目录后再导入 |
| `--dir \\server\share\data` | 导入路径不允许 UNC/网络路径（无法在包内还原）：\\server\share\data；请先把文件复制到当前工作目录下再导入 |
| `--dir data/../outside` | 导入路径不允许包含 `..`（无法在包内还原）：data/../outside；请把文件放在当前工作目录内，用相对路径导入 |

- 单文件导入同样走 `src/ingest.py:_reject_unreconstructable_path`，不是只拦目录。
- `_rel_path` 不再返回 basename：删除“静默压平”分支，无法还原就报错。
- 测试：`test_ingest_rejects_non_contract_paths` 四参数各断言非零退出与错误文案关键字。

## 五、A7：发行物签名钥静默轮换

### 5.1 实测事实

| 版本 | 构建时间（+08:00） | `SHA256SUMS.sig` key_id |
| --- | --- | --- |
| 0.4.5 | 2026-11-04T09:29:04 | `ed25519:5e797e1842cf49c7043ba238f2a085b08c87d0a49663440f989cdc7df9ee5bb6` |
| 0.4.6 | 2026-11-04T15:51:45 | `ed25519:b07741b2e0bbcb9a3a37dd09a7348c717497145f7cbbdd580b18e7e80e7a9555` |
| 0.4.7 | 2026-11-04T20:17:30 | `ed25519:5e797e1842cf49c7043ba238f2a085b08c87d0a49663440f989cdc7df9ee5bb6` |

包签名钥（另一把，持久于 `var/handoff-keys/ed25519.key`）：
0.4.4 `ec2081…`；0.4.5/0.4.6/0.4.7 均为 `b07741b2…9555`。

### 5.2 根因（推断，高置信）

0.4.6 构建时把 `var/handoff-keys/ed25519.key`（包签名私钥）传给了
`scripts/build_release.py --signing-key`；旧脚本不校验 key_id，因此没有报错或记录。
依据：0.4.6 发行物 key_id 与包钥完全相同，且两把私钥都是持久文件（非每次 keygen）。
**不是**“每次构建重新生成密钥”的流程缺陷；是**用途混用 + 缺少守卫**。

### 5.3 修复（实测）

- `scripts/build_release.py` 固定 `EXPECTED_RELEASE_KEY_ID = "ed25519:5e797e18"`；
  非预期钥默认拒绝构建，只有显式 `--allow-key-rotation <理由>` 才放行。
- `docs/签名方案.md` §5 与 `docs/安全与证据链现状.md` 增加轮换记录：原因、生效版本、
  旧钥处置、旧包/旧 wheel 配对要求。
- `KEY-NOTE.txt` 同时记录发行钥与包钥两条链，避免再次混用。
- 旧发行物不重签、不改写；交接目录附 `release/旧发行物-SHA256清单.md`，覆盖
  0.4.1–0.4.6 发行目录逐文件 SHA-256 与历史包 SHA-256，旧发行物仍可独立核验。

### 5.4 README 事实修正（实测）

- 包计数由“六个”改为“八个”（七个常规包 + 一个干净 wheel 默认流程包）。
- 引用 `docs/安全与证据链现状.md` 的路径已随交接目录补齐，不再指向未交付文件。

## 六、附带缺陷

### 6.1 `wca gen` 从发行 wheel 跑不起来（实测）

- 0.4.6 wheel 文件列表**不含** `data/generator/make_synthetic.py`，因此
  `ModuleNotFoundError: make_synthetic`。
- 0.4.7 `pyproject.toml` 用 force-include 打入该模块；wheel 文件列表已确认包含。
- 干净 venv（仓库外 `C:\Users\wesley\wca-clean-047`，锁定依赖 + 仅装 wheel）实测：
  `wca gen → ingest → check → export → verify → replay` 全部 exit 0，
  `wca-verify`/`wca replay` 输出 `RESULT OK`；产出第八个包
  `clean-wheel-default-flow.zip`（SHA-256 `225d851d…d3bd`）。
- 该包与源码默认流程包三元组一致：`b884c337…b993` / `82084b03…f69d`，
  `evidence_digest=01cb5aeb…a904`。

### 6.2 审批台账规范化未披露（实测）

包内 `approval_ledger.csv` 为数据库确定性重导出（UTF-8 无 BOM、LF，97→93 字节），
不是上传原始字节。顶层 `manifest.json` 的 `inputs.approval_export` 已披露：

```json
{"mode":"db_export","encoding":"utf-8","bom":false,"line_endings":"LF",
 "original_bytes_retained":false,
 "note":"approval_ledger.csv / approval_coverage.csv 由数据库确定性重导出，不是原始上传字节；原始字节未随包保留，重放以包内重导出文件为准。"}
```

该字段刻意只放顶层 manifest，不放进 `inputs/manifest.json`，否则 `inputs_digest`
会从 `aad527d1…30a7` 漂移（已实测并回退）。

### 6.3 重复导出覆盖同名 zip（实测）

- 导出名改为 `<run_id>-<YYYYmmddTHHMMSS>-<hex6>.zip`；目标已存在直接拒绝，
  不覆盖旧包。
- 同一 run 连续导出实测得到三个不同文件名（如 `…T201802-f5e1ee.zip` 等），
  内容 SHA 因审计事件追加而不同（已知性质），但不会覆盖任何既有包。
- 测试 `test_zip_exports_are_unique_and_never_overwrite` 断言唯一命名与拒绝覆盖。
