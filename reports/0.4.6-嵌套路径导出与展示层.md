## 1. F1：默认流程实测（修复前）

在仓库根目录执行：

```powershell
uv run python -m src.cli gen --seed 20260106
uv run python -m src.cli ingest --dir data/raw
uv run python -m src.cli check --start 2025-09-01 --end 2026-04-30
uv run python -m src.cli export
```

**实测**：`gen` 前后 `git status data/raw` 无变化；`ingest` 写入 `rel_path=data/raw/*.csv`；
`export` 报：

```text
FileNotFoundError: ...\packages\run-...\inputs\data\raw\correction.csv
```

exit 1，暂存目录留下 16 个根工件与 `inputs/manifest.json`，没有 zip。与审计方报法一致。

**根因（实测）**：`input_arcnames` 已正确生成 `inputs/data/raw/punch.csv`；失败点是
`_export_package_locked` 的正常复制分支直接 `shutil.copyfile(source, work/arcname)`，
未创建父目录。`_trim_input_entry` 分支反而已有 `mkdir(parents=True)`，说明是遗漏而非契约问题。

**修复**：复制前 `target.parent.mkdir(parents=True, exist_ok=True)`；`_resolve_input_path`
增加 `cfg.data_dir / rel_path` 候选，保证 `data/raw/*` 在默认数据目录下可解析。

## 2. F2：重跑不自愈实测（修复前）

在失败暂存目录中手工创建 `inputs/data/` 后重跑 `export`：

```text
File "src\evidence.py", line 1116, in _export_package_locked
PermissionError: [WinError 5] 拒绝访问。: ...\inputs\data
```

exit 1，重跑仍失败。

**根因（实测）**：旧逻辑 `for stale in inputs_dir.glob("*"): stale.unlink()` 只处理文件，
目录调用 `unlink()` 在 Windows 直接拒绝访问；暂存目录跨次复用。

**修复**：每次导出先整体删除 `packages/<run_id>` 再重建；失败路径由 `export_package`
外层 `except` 清理暂存目录。0.4.6 测试 `test_reexport_self_heals_nested_inputs_dir` 覆盖。

## 3. F3/F4：当前行为与失败关闭

**实测（修复前）**：

| 场景 | 本机实测 | 与审计方描述的差异 |
|---|---|---|
| 绝对路径 `rel_path=D:\...` | 导出抛 `OSError`（`inputs/D:/...` 非法路径），exit 1，留暂存目录 | 审计方在另一平台见“缺项 4、exit 0、verify OK / replay FAIL”；平台路径规则不同，但都属未失败关闭 |
| 含 `..` 的 `rel_path` | 导出 `missing=4`（本机把 4 个输入都判缺失），exit 0，`verify` 内容检查 OK，`replay` FAIL | 审计方见“缺项 1”；缺项数取决于文件实际位置，性质相同：静默残缺 |

**修复**：

- `validate_input_rel_path`：拒绝空路径、以 `/` 开头、盘符 `X:`、任何 `..` 段；
  `inline://` 保留既有临时输入契约。`import_csv_file` 与 `import_rows` 入口调用。
- `export` 在 `collect_package_inputs` 后检查 `missing`，非 `inline://` 缺项直接
  `ValueError`，消息含“拒绝生成残缺包”；外层清理暂存目录，不产出 zip。
- `_resolve_input_path` 补 `cfg.data_dir / rel_path`，避免把可解析的嵌套文件误判缺失。

## 4. 验算补洞：`INPUTS COMPLETENESS`

**现状（修复前）**：`wca-verify` 只校验 `inputs_digest`；`check_artifacts` 只拒绝“包内多出未声明文件”，
不检查“声明了但包内没有”。因此 F3 的“少 4 个输入”仍能 `INPUTS DIGEST OK`，直到 replay 才失败。

**0.4.6**：新增 `check_inputs_completeness`，在 `INPUTS DIGEST` 之前执行：

- 读 `input_files.csv`（本 run 引用输入，受 `input_fingerprint` 覆盖）；
- 读 `inputs/manifest.json` 的 `entries`；
- 双向多重集对账 `(rel_path, sha256, kind)`：少项、多项、sha/kind 不符都 FAIL；
- 按 `input_arcnames` 推导包内路径，文件必须存在且实际 sha256 一致；
- 失败标签：`INPUTS COMPLETENESS FAIL 输入清单列了 N 个，包内 inputs 缺少 M 个：...`。

**实测**：从有效包中删除 `inputs/a/punch.csv` 后，verify 先报该失败标签，不再以摘要命中掩盖。
测试 `test_verify_detects_missing_input_member` 覆盖；`NOT CHECKED` 不计入内部 OK（schema < 3 旧包除外）。

## 9. 密钥轮换（P3）

**实测证据**：

- 0.4.4 包 `key_id=ed25519:ec2081…08d6`；工作区找不到匹配私钥；
- 0.4.5 私钥 `var/handoff-packages/keys/ed25519.key` 创建于 2026-11-04 09:29:15，
  `key_id=ed25519:b07741b2…9555`；
- `var/handoff_packages.py` 每次构建先整体删除 `var/handoff-packages`，再 `generate_keypair()`；
- 旧公钥保留在 `handoff/20261104-第六轮整改/trusted-public-key.pub`。

**判定**：属于**意外覆盖/私钥丢失**，不是计划内轮换。已按安全事件写入
`docs/安全与证据链现状.md`。处置：0.4.4 私钥作废；旧包仍可用 0.4.4 wheel + 旧公钥验签；
0.4.6 复用 `b07741b2…9555`，不再轮换。

**实测**：旧包用 0.4.5 wheel 是 `PRODUCER FAIL` + `SIGNATURE NOT CHECKED（早退）`，
不是验签失败。交接包 `OLD-WHEELS.md` 与 `release/old-wheels/` 给出配套旧 wheel。

## 10. 聚合形状（P4，只回答）

**实测**：25 行重复（同一日）触发 `QUAL-DUP` 汇总后，引擎按日展开为 **1 条** `QUAL-01`
（`issue_count=26`，含唯一 out 卡）；没有额外“逐日 1”条。

**判断**：审计看到的“1 条聚合 `issue_count=48` + 1 条逐日 `issue_count=1`”是**两天**的
两条 `QUAL-01`：两天各有自己的行引用与 `issue_count`。`QUAL-01` 的 canonical 粒度是
`(emp_id, work_date, period_key)`，按日保留是为了给出具体日期定位；汇总层只吸收原始
`QUAL-DUP` 行，不应把跨日结论压成一条。**设计有意，不建议改**；若强行合并会改变规则语义与
`conclusion_digest`，需另行确认。
