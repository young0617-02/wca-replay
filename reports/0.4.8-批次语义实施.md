## 1. 复测四项逐条对应

### 1.1 `artifacts_digest` 依赖数据库后端（阻断项）

**0.4.7 复测现象**：同输入、同规则包，PG 重导出 `artifacts_digest = 5914034d…`，而锚点是
`8af419ec…`。根因是 49 条空 `work_date` 的期间汇总行在 `findings.csv` 中的行序由 SQL
`ORDER BY` 决定：SQLite 升序把 NULL 排在前，PostgreSQL 升序把 NULL 排在后。

**0.4.8 是否已消除该路径：是，且不是靠推断。**

证据 1（路径消失）：0.4.8 的 QUAL-01 不再产出空 `work_date` 的期间汇总条。对 engine-only
包实测：`QUAL-01` 空 `work_date` 条数 = **0**；包内仅存的空日期 finding 共 13 条，全部是
非聚合类（见 §6.2），不存在“空日期重复汇总”路径。

证据 2（导出排序不再依赖后端）：所有进入包内工件的 `ORDER BY` 已改为先取数、再用 Python
显式排序；SQL 仅保留对非空整数代理键的排序，或仅用于网页/代理交互、不进入工件。

证据 3（真实双后端回归）：新增
`tests/test_postgres_integration.py::test_sqlite_and_postgres_export_five_digests_identical`。
同一批输入（含 50 条同内容打卡，即 49 条重复）分别导入 SQLite 与 PostgreSQL 18，分别跑
`run_check` 与 `export_package`，断言：

- `manifest["triple"]` 完全相同（含 `conclusion_digest` / `input_fingerprint` / `rule_pack_version`）；
- `evidence_digest`、`inputs_digest`、`artifacts_digest`、`artifact_sha256` 逐字节相同；
- `manifest["counts"]` 完全相同；
- 两个包内 `QUAL-01` 均无空 `work_date`，`quality_issues.csv` 均只有 1 行 `QUAL-DUP`。

该用例在带 PG 的全量测试中通过（见 §7）。因此 0.4.7 的 PG `5914034d…` 差异在 0.4.8 中不再出现。

## 2. 方案 A：单批 finding 的形状

### 2.1 形状

- 同一员工、同一实际发生日的重复行合并成 **1 条** `QUAL-01` finding。
- `work_date = period_key = 实际发生日`（如 `2025-09-01`），不再出现空日期汇总条。
- `metric` 字段：
  - `batch_id`：内容派生（见 §3）；
  - `batch_size`：该批重复行条数（示例 49）；
  - `sources`：该批**全部重复行**，逐项 `{"rel_path", "line_no"}`，不截断；
  - `issue_rule_ids`、`raw_value` 等原有字段保留。
- **首次出现行不进批次**：它仍是事实表保留的那一条。`quality_issues.csv` 的 detail 同时列出
  “重复行来源”和“首次出现行（不重复计）”，两处都是 `rel_path:line_no`。
- `quality_issues.csv` 每个批次只输出 **1 行**；`batch_size`、`batch_id` 与 findings 完全同源。

### 2.2 49 条重复的实测证据

测试 `test_single_batch_finding_shape_with_49_sources`：1 条首次出现 + 49 条文件内重复 + 1 条下班卡。

- `len(out.findings) == 1`；
- `work_date == period_key == "2025-09-01"`；
- `batch_size == 49`；
- `len(sources) == 49`，首项 `punch.csv:3`，末项 `punch.csv:51`；
- `batch_id == 37caeef60f2f9fe5574c92242644b5c3e74f7a4270b9175e1ef499c534c798db`；
- `quality_issues.csv` 仅 1 行 `QUAL-DUP`，detail 含 `batch_size=49` 与 `punch.csv:3`…`punch.csv:51` 全部行。

### 2.3 跨文件重复的来源修正

0.4.8 开发中实测发现一个边界：跨文件重复时，数据库行存的是“按 `rel_path` 字典序的首个来源”，
若直接拿库行当来源，会把**首次出现行**算进批次，并丢掉后导入文件的真实行号（正是复测说的
“只留首条”）。已修正：

- 从 detail 解析全部物理来源；首个来源是首次出现行，**其余才进批次**；
- 聚合摘要（`qual_dup_summary`）同时保存 `line_refs`（重复行）与 `first_refs`（首次出现行）；
- 双目录包实测：`a-then-b` 与 `b-then-a` 的 `sources` 都是
  `[{"rel_path":"b/punch-b.csv","line_no":2}, {"rel_path":"b/punch-b.csv","line_no":3}]`，
  `batch_size=2`，`batch_id=89775c5e…`；两序 `conclusion_digest` 同为 `924c5e01…`。

### 2.4 其他“期间汇总”形状的核对

- `QUAL-02`（被拒收行）：**有意保留空 `work_date`/`period_key`**。被拒收的原始行没有可解析
  日期；凭空补一个日期会篡改事实。它不是“重复行期间汇总”，而是事实缺口清单。
  包内共 3 条。
- `REG-01`（5 条）、`SCOPE-02`（4 条）、`SCOPE-03`（1 条）：员工级范围/资质结论，本身不绑定
  某一天，空日期是**规则语义**，不是聚合遗漏。
- 其余周/月/周期规则（`WK-W02`、`WK-W01`、`CAP-W01`、`CAP-M01`、`CAP-M02`、`COMP-C01`）：
  `work_date` 为空但 `period_key` 非空（ISO 周/月/周期），不是空日期汇总条。
- `QUAL-01`：**已无任何空日期记录**（实测 0 条）。

## 3. `batch_id`：内容派生与审计方独立复算

### 3.1 派生公式（规范）

输入：该 finding 的 `metric.sources` 列表，每项含 `rel_path` 与 `line_no`。

1. 对每个来源生成规范字符串：**`rel_path + ":" + 十进制整数 line_no`**（`rel_path` 使用包内
   相对路径，正斜杠；`line_no` 不加前导零、不加空白）。
2. 去重（相同字符串只保留一次）。
3. 按字符串的 **UTF-8 字节序**升序排序（`sorted(key=lambda s: s.encode("utf-8"))`）。
4. 用 **LF（`\n`，U+000A）** 连接。
5. 对整个字符串做 **SHA-256**，输出 **64 位小写十六进制**。

即：

```
batch_id = sha256( "\n".join( sorted_unique( f"{rel_path}:{line_no}" ) ) )
```

禁止使用数据库自增、运行序号、计数器、时间戳、`run_id`、`file_id`、`segment_id`。

### 3.2 审计方无需读源码的复算步骤

1. 从包内 `findings.csv` 取 `rule_id == "QUAL-01"` 且 `metric_json` 含 `batch_id` 的行；
2. 解析 `metric_json["sources"]`；
3. 按 §3.1 的 5 步计算；
4. 与 `metric_json["batch_id"]` 比较，必须逐字符相同；
5. 再与 `quality_issues.csv` 中对应 `QUAL-DUP` 行的 detail 内 `batch_id=` 比较，必须相同。

可直接运行的独立复算脚本（不依赖本项目代码）：

```python
import hashlib, json, zipfile

with zipfile.ZipFile("handoff/20261104-第十轮整改/package/engine-only.zip") as zf:
    import csv, io
    rows = list(csv.DictReader(io.StringIO(zf.read("findings.csv").decode("utf-8-sig"),
                                           newline="")))
for row in rows:
    metric = json.loads(row["metric_json"])
    if "batch_id" not in metric:
        continue
    texts = sorted({f"{s['rel_path']}:{s['line_no']}" for s in metric["sources"]},
                   key=lambda t: t.encode("utf-8"))
    recomputed = hashlib.sha256("\n".join(texts).encode("utf-8")).hexdigest()
    assert recomputed == metric["batch_id"], (recomputed, metric["batch_id"])
    print(row["rule_id"], metric["batch_size"], recomputed)
```

## 6. 下游计数口径

### 6.1 三字段与关系

`manifest.counts` 新增：

| 字段 | 含义 |
|---|---|
| `findings_total` | finding 条数（包内 `findings.csv` 的数据行数） |
| `findings_batched` | 其中批次 finding 条数（每批 1 条） |
| `issues_total` | 按问题条数计：`findings_total - findings_batched + Σ batch_size` |
| `quality_issues` | `quality_issues.csv` 数据行数（批后每批 1 行） |

三处口径必须一致：`manifest.counts`、`policies/CONFIDENCE.md`、`未覆盖清单.md`。

### 6.2 实测一致证据

49 条重复的合成场景（`test_counts_three_places_agree_after_batching`）：

- `manifest.counts`：`findings_total=1`、`findings_batched=1`、`issues_total=49`、`quality_issues=1`；
- `CONFIDENCE.md`：`发现（未签认）：1 条` / `其中批次 finding：1 条` / `按问题条数计：49 条`；
- `未覆盖清单.md`：`发现（未签认）1 条 … 批次 finding 1 条，按问题条数计 49 条`。

默认 engine-only 包（v5，1 条重复行）：

- manifest：`findings_total=115`、`findings_batched=1`、`issues_total=115`、`quality_issues=7`；
- CONFIDENCE：`发现（未签认）：115 条` / `其中批次 finding：1 条` / `按问题条数计：115 条`；
- 未覆盖清单：`发现（未签认）115 条 … 批次 finding 1 条，按问题条数计 115 条`。

clean-wheel v6 包同样是 115 / 1 / 115 / 7，三处一致。

README 已新增“如何正确统计重复类问题”：**不要用 finding 条数直接当问题条数**；先读
`findings_batched` 与各批 `batch_size`，再按 `issues_total` 汇总。示例：1 条批次 finding、
`batch_size=49` → `findings_total=1`、`issues_total=49`，不是 1 条。
