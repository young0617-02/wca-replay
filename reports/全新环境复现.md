> 目的：在一个**全新的 PostgreSQL 18 数据库**上，从零跑 `init → ingest → kb → check → export → replay → verify.py`，找出“只在当前开发环境成立”的隐含依赖。
> 约束：不改代码、不改默认配置、不提交 Git、不写活动库 `wca_worktime`、不删除任何临时库或备份；仓库内只新建本报告与新库，临时包/解压目录/venv 放在 `%TEMP%`。


定位：`src/anomaly.py:116-123` 的 `rule_hit_counts()` 查询是

```sql
SELECT rule_id, rule_version, severity, COUNT(*) AS c
FROM finding WHERE run_id = ?
GROUP BY rule_id, severity
```

SQLite 对“SELECT 列不在 GROUP BY”的写法通常更宽松，PostgreSQL 18 明确拒绝。离线测试默认 SQLite，未在 PG 上覆盖该命令；本轮没有改代码，**缺陷保留**（SQLite 下的实际行为本轮未重跑，见 §5.2）。

影响链：`src/cli.py:570` 的 `ALL_STEPS = ("init","gen","ingest","kb","check","report","export")` 包含 `report`。因此**按 README/操作手册在 PG 上跑 `python -m src.cli all`，会在 report 步 rc=1 并停止**（这是由代码顺序 + report 实测 rc=1 推出的，未实际运行 `all`，因为 `all` 会先 `gen` 重写 `data/raw`）。异常 CSV 已经写出 101 行，属于“部分成功”，不能只看 rc 判断“没有产物”。

它不在 `data/raw` 的 7 个 CSV里，也不在 `docs/演示脚本-30分钟.md` 的命令里；文号形态与 `tests/test_evidence_epoch.py` 的 EPOCH 夹具同款，**疑似 v5 纪元演练时手工插入**。本轮按约束未复刻该行。

### 3.4 为什么指纹/摘要必然不同

- **指纹不同不是“算法不稳定”**：新库与活动库的 `scope_json` 13 个键逐项相同，只有 `approval_ledger_sha256` 不同；空台账 digest 为 `29847f…`，活动库 1 行台账 digest 为 `f4369c…`。v5 把审批台账纳入输入指纹，所以这是**正确感知输入差异**，不是随机。
- **摘要不同不是“引擎漂移”**：两库 115 条 finding 逐行相同，只多 `REG-01 / E006` 一条；`conclusion_digest` 因此不同。
- **与 v4 基线的关系**：v4 单次 101；新库 v5 116 = 101 + 14（v5 新增 REG-01 4 + COMP-C01 10）+ **1（缺台账导致的 E006 REG-01）**。若活动库那行台账在，按规则应回到 115。此 115 是**推算**，未通过补数据验证。

### 3.5 活动库不是“当前代码的干净副本”

- `wca_worktime.meta.schema_digest = adfaa3d0…`，当前代码 `src/schema.sql` 摘要 = `02a007b2…`，新库初始化后也是 `02a007b2…`。说明活动库是在旧 schema 上初始化的；下次对活动库执行 `init` 会因摘要不一致重跑 DDL（本轮**没有**执行）。
- 活动库有 v4→v5 的 `rule_pack_epoch`，审计 169 条；新库 0 个 epoch、审计 10 条。活动库的“115 条 + epoch 包”是**历史状态**，不是从零可复现的状态。

### 4.4 最容易踩的坑（按严重度）

1. **【致命】identity 标记把新 URL 拉回活动库。** `src/db.py:339-397` 的 `ensure_database` 会优先信任 `var/db_target.json` 里的 host/port/user/database；当前该文件就是 `wca_worktime`。实测：配置 URL 已改成 `wca_clean_v5_20261103`，但把 identity 指向活动库后，`ensure_database` 返回 **`wca_worktime`**，配置 URL 被改写；活动库 `run` 计数仍为 2（因为只做了只读探测，没有写入）。本次全流程因此显式把 `WCA_DB_IDENTITY_PATH` 指向 `%TEMP%`。**只改 URL 不改 identity 是高风险操作。**
2. **【高】`.env.example` 默认 SQLite，README 的 `cp` 路径不会给你 PG。** 示例 `WCA_DB_BACKEND=sqlite`、`WCA_DATABASE_URL=`；而项目规则要求 PostgreSQL 18。新机器按 README 第一段做，会得到 SQLite 离线库；要 PG 必须照操作手册改 `.env`。
3. **【高】工作区有 9 MB 旧 SQLite 库。** `var/worktime.sqlite3`（2026-10-09，4 次 v4 run、404 findings、806 audit）。当 `--env` 指向不存在文件且没有 `WCA_*` 注入时，一次 `covers` 实际读了它（显示 v4 规则、REG-01/COMP-C01 未命中），而不是新 PG 库。新机器没有这个文件则不会复现，但“当前环境”会。
4. **【高】仓库演示数据不含 E006 审批台账。** `data/raw` 只有 7 个 CSV，没有 `approval_ledger.csv`；`docs/演示脚本-30分钟.md` 也没有 `approval` 命令。全新库因此 116 条，活动库 115 条。**这不是判据错，是输入少一行。**
5. **【高】`report` 在 PG 上会失败。** `src/anomaly.py:116-123` 的 `GROUP BY` 缺 `rule_version`；PG 实测报 `GroupingError`（SQLite 侧未重跑）。操作手册 5.2 和 README 的 `all` 都会受影响；本轮 rc=1，CSV 部分写出。未改代码。
6. **【中高】`config/not_covered.json` 是 CWD 相对路径。** `src/evidence.py:447` 用 `Path("config/not_covered.json")`，不是 `PROJECT_ROOT`。实测：仓库根目录调用 `not_covered_block` 返回 3 个城市；`os.chdir(%TEMP%)` 后抛 **`KeyError: 'scope'`**。`export` 从非仓库根目录运行会失败；`replay`/`verify.py` 不受这条影响。
7. **【中】`216` 被误当单次基线。** 216 = v4 101 + v5 115 累计；新库单次 116。直接比会得到“少 100 条”的假差异。`wca_worktime_v5` 的 347（116+116+115）也是累计。
8. **【中】`EPOCH OK` 不等于有纪元。** 新库包 `CHAIN OK … segment= legacy`；`verify.py` 在没有 activation event 时仍打印 `EPOCH OK`。活动库包才是 `segment= epoch-rp-…v5-19`。
9. **【中】当前 `.env` 是 cloud 档，不是离线 stub。** `WCA_LLM_PROVIDER=openai`（`build_provider` 映射为 `cloud`）、`WCA_LLM_MODEL=Qwen/Qwen3.8-27B`、`WCA_CLOUD_BASE_URL/KEY` 已填、`WCA_EMBEDDING_MODEL=BAAI/bge-m3`。本轮强制 `stub`；如果直接按当前 `.env` 跑 `ask`，会外发云 API（有费用/隐私影响），本轮**未运行**。
10. **【中】活动库 schema 已过期。** `meta.schema_digest=adfaa3d0…` vs 当前 `02a007b2…`。下次 `init` 活动库会重跑 DDL；新库是当前 schema。基线不是“当前代码从零建”的库。
